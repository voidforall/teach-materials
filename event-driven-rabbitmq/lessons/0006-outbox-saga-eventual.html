No Distributed Transactions. Design Accordingly.

The outbox makes "commit + publish" atomic; sagas make multi-service processes recoverable; UX absorbs the rest.

Lesson 3 planted the dual-write problem and promised the outbox. But the outbox is one instance of a bigger truth: across a database and a broker — or across several services — there is no atomic commit. Nobody runs two-phase commit across service boundaries (2PC couples availability: one participant down, everything stalls). Everything in this lesson is what systems do instead.1

The transactional outbox, concretely

The state change and its event commit together, or not at all. Publishing becomes a separate, retryable job — with confirms (L3) and idempotent marks, since the relay can crash between publish and mark.

Moving parts: an outbox table (event payload, aggregate ID, sequence), a relay that publishes pending rows with publisher confirms and marks them sent. Relay implementations range from a 50-line poller to change-data-capture (Debezium) reading the transaction log. Consumers still must be idempotent — the relay itself can double-publish — so the L3 dedup key stays load-bearing.

Keystone A saga is a sequence of local transactions, each with its own outbox, where every step knows how to undo the ones before it. No step spans two systems — atomicity is always local; what's distributed is recovery. Failures aren't prevented, they're designed for: each forward action gets a compensating action (reserve ↔ release, charge ↔ refund, create ↔ cancel).

Sagas: choreography vs orchestration

Forward path in green, compensation path in red. A saga failing at step 3 of 4 unwinds only the completed steps, in reverse.

Two ways to wire the steps together — this is a topology decision (L5):

  • Choreography: services react to each other's events — inventory hears order.placed, emits stock.reserved; payment hears that, emits card.charged… No coordinator; the flow emerges from bindings. Wins on coupling and startup cost; loses track of the plot as steps grow — "who reacts to what?" becomes archaeology. Use for 2–3 steps.
  • Orchestration: a saga state machine (own service or library) sends commands and consumes results: reserve.stock, then charge.card, and on failure it issues the compensations in order. The process lives in one readable place, with explicit failure branches. Use when steps ≥ 4, branch, or need timeouts. Watch the failure mode: an orchestrator that grows into a god service.

Naming carries the model (glossary): steps are commands — imperative, addressed, one logical consumer (charge.card); announcements are events — factual, broadcast (card.charged). Sagas speak commands forward, often emit events for the world.

Eventual consistency: it's a UX problem now

"Order confirmed" will be true in the payments service seconds after it's true in the order service. Technically fine (L3's guards handle stale reads); the user-facing part is yours to design:

  • Model the pending state — "payment processing…" is a real state in your domain, not a spinner hiding one. Expose it in the API and UI.
  • Don't fake synchronous answers over async plumbing — if the caller needs the result now, that's a request/response (HTTP) call. Request/reply over RabbitMQ exists (correlation IDs, reply queues) and is legitimate for genuinely async request-response, but a sync façade over a saga just moves the timeout.
  • Make lag a metric — queue depth and consumer lag (L5) are your "how eventual?" dashboard. Eventual with a 30-second tail isn't a consistency policy; it's an outage you haven't declared yet.

Check yourself

Q1. Why can't a DB commit and a publish ever be one transaction?

The database and the broker share no transaction coordinator.

2PC could theoretically span them but couples availability — one system down stalls all commits. Hence the outbox: local atomicity, distributed retry.

Q2. A saga fails at step 3 of 4. What exactly runs next?

Compensating transactions for the completed steps, reversed.

Undo is for what happened — steps 1–2. The failed step leaves nothing to undo. Compensations are themselves saga steps: retryable, idempotent.

Q3. Choreography or orchestration for a five-step branching flow?

Orchestration — a branching flow needs one visible home.

Five subscribers chained by bindings buries the process logic. Rule of thumb: choreography to ~3 steps, orchestration beyond or with branches/timeouts.

Q4. The UI must acknowledge payment instantly. What does it show?

A pending state immediately, confirmed when the event lands.

Pending is a real domain state, not a spinner. Faking certainty ("paid!") before the saga confirms it is the classic eventual-consistency bug.

Now you drive

Design it — before you reveal

Refund flow for the food-delivery platform (L5's capstone): customer requests refund after delivery. Steps: (1) verify order was delivered, (2) refund the payment, (3) claw back the restaurant's payout, (4) notify the customer. The payment provider is eventually consistent itself (refund accepted ≠ refund completed). Choose choreography or orchestration, list the messages (commands vs events), define compensations if any, and say what the customer's app shows at t=0.

Reveal one good answer

Orchestration — 4 steps, an external eventually-consistent provider, and refunds are money: you want the state machine auditable in one place.

  • Messages: commands verify.delivery, refund.payment, clawback.payout, notify.customer; the world hears the fact refund.completed.
  • The provider's async completion comes back as event refund.provider_completed (or a webhook → outbox); the orchestrator advances on it, not on "accepted".
  • Compensations: verify-fail → nothing to undo, emit refund.rejected. Payment refund fails → terminate + notify (no clawback). Clawback fails → retry ladder (L4); it is not compensated by re-charging the customer — money asymmetries go to humans (parking lot), not automation.
  • Outboxes: every step's state change + next message commit together (the orchestrator's own DB, the payment service's DB). Consumers idempotent throughout.
  • UI at t=0: "refund requested" — pending is a real state; confirm on refund.completed.

The three hard-won points: orchestrator waits on completion events, not acknowledgements; some steps are terminal-for-humans rather than compensable; the outbox recurses — it's the same pattern at every service boundary.
