The Topology Is an API

Durability, ordering, scaling, and schema evolution — the four decisions every production topology makes, deliberately or not.

Lessons 1–4 gave you the mechanics. Now the design work: the exchanges, queues, and bindings you lay down are a public contract — services you don't own will publish to your exchanges and consume from your queues. Treat naming, durability, ordering, and versioning as API-design decisions, because after launch, that's what they are.1

First, make durability real: the trinity

Lesson 3's confirms promise "accepted and persisted" — but only if the storage beneath cooperates. A message survives a broker restart only when all three hold:

  1. durable exchange — survives restart;
  2. durable queue — survives restart (use quorum queues for anything that matters: replicated, the modern default);
  3. persistent message (delivery_mode=2) — the message itself is written to disk.
The silent lie Defaults are not the durable combination. A confirmed publish to a non-durable queue is confirmed into a queue that evaporates on restart. Nothing errors; the confirm just told you the wrong thing. Checklist the trinity once, in topology-as-code, and never think per-message again.

Ordering: the guarantee you don't have

Here is the precise claim, and it's weaker than people assume: RabbitMQ delivers FIFO per queue, per publishing channel. But with competing consumers (Lesson 1), message A delivered before B can still finish after B — the slow consumer's message lands second. Add retries (Lesson 4) and A can fail, cycle through a TTL queue, and process a minute later. Cross-message order is best-effort, always.2

Keystone Don't design for global order — scope ordering to where it matters: per entity. Two tools: (1) shard by routing key — a consistent-hash exchange spreads messages across N queues by hashing the key, so all events for customer-42 land on one queue with one consumer: ordered and parallel (Kafka's partition trick, in RabbitMQ). (2) make consumers order-independent — carry state versions and let the state guard from Lesson 3 ignore stale events. Most real systems want a mix: sharding where sequences matter (per-account ledger), version guards everywhere else.

Scaling: when one queue is not enough

  • First lever — more consumers on the queue (competing consumers). Gets you far: a single queue handles tens of thousands of messages/sec.
  • Second lever — shard the queue with the consistent-hash exchange when you need ordered parallelism or exceed one queue's throughput.
  • Watch, don't guess: queue depth and consumer acknowledgement rate tell you when to pull a lever. Depth growing while consumers sit idle → prefetch too low; depth growing with consumers busy → add or shard.

Schema evolution: events will change

Your order.created payload will grow fields, and one day it will break shape. Two layers of defense:

  • Tolerant readers as the default: consumers must ignore unknown fields and treat missing optional fields as defaults. Additive change then needs no coordination at all.
  • Versioned routing keys for breaking change: publish order.created.v2. Old consumers stay bound to order.created.v1 — wait, the pattern: bind order.created.* only if you tolerate both, or bind the exact version you support. Run both versions side by side, migrate consumers, then retire the old binding. Nobody updates in lockstep.

Same discipline as REST versioning, with one gift: unlike a request/response API, the old version keeps working while you migrate — the broker holds both traffic streams without conflict.

House style — a default topology

A starting point that serves most domains well, deviating only with reason:

  • One durable topic exchange per domain (orders, payments) — not one global exchange, not one per service.
  • One durable quorum queue per consumer group, named <service>.<purpose> (email.retries, analytics.orders): the owner is visible in the name.
  • Routing keys are events with versions: order.created.v1 — dot-separated, name-what-happened (events, not commands, when the fact is what matters).
  • Declared as code, centrally — definitions in the repo, applied declaratively; client-side ad-hoc declares are for dev only.
  • Retry ladder + parking lot per domain (Lesson 4), attached to each work queue.

Check yourself

Q1. Which three settings make a confirmed message survive restart?

Durable exchange, durable quorum queue, persistent delivery mode.

Any one missing and the confirm is technically honest but practically a lie — the queue or message vanishes on restart.

Q2. Two competing consumers: A delivered before B. Which finishes first?

Either one — delivery order never binds processing completion order.

The slow consumer's message lands last regardless of delivery. Retries widen the gap further.

Q3. How do you keep per-customer ordering while scaling out consumers?

Hash the routing key across sharded queues, one consumer each.

Same customer → same queue → same consumer → ordered; different customers still parallelize. This is Kafka-partition behavior.

Q4. A breaking payload change ships. How do old consumers survive it?

Publish under a new versioned key; consumers bind selectively.

Both streams flow side by side during migration. No lockstep updates, no big-bang cutover.

Now you drive — the capstone

Design the whole thing — before you reveal

A food-delivery platform. Events: order.placed, order.accepted, order.delivered, restaurant.menu_changed. Consumers: (a) a payment worker pool (exactly-one processing, flaky PSP — transient 500s); (b) a courier-dispatch service that needs per-order event ordering, scaled to 3 instances; (c) analytics wanting every order event; (d) a menu-cache service that must not miss menu_changed but tolerates delay. Design exchanges, queues, bindings, durability, retry, and how you'd version order.placed later.

Reveal one good answer

Exchanges: orders (topic, durable) for order events; restaurants (topic, durable) for menu events; one retry + parking lot per domain.

  • (a) payments.orders quorum queue bound order.placed, worker pool as competing consumers, retry ladder from L4 (PSP 500s = transient). Exactly-one processing = work-queue shape + idempotent handler (L3).
  • (b) consistent-hash exchange in front of 3 queues dispatch.shard-0/1/2, hashing on order_id in the routing key (order.<event>.<order-id>) — each order's events hit one shard with one consumer: ordered per order, parallel across orders. All 3 order events bound in.
  • (c) analytics.orders quorum queue bound order.# — its own copy, its own pace (pub/sub).
  • (d) menu.cache quorum queue on restaurants bound restaurant.menu_changed; if a refresh fails, retry ladder with long TTLs — delay tolerated, loss not (durable everything + parking lot on exhaustion).
  • Versioning: when order.placed breaks shape, add order.placed.v2; tolerant readers for additive fields meanwhile.

Notice every requirement maps to exactly one lesson: (a) = L1 work queues + L3 idempotency + L4 ladders; (b) = today's ordering section; (c) = L1 pub/sub; (d) = durability trinity. If your sketch has those four shapes, you've internalized the course so far.
