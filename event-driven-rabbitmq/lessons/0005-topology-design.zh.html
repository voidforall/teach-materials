拓扑即 API

持久性、顺序、扩容与 schema 演进 —— 每个生产拓扑都要做的四个决定，主动或被动。

第 1–4 课给了你机制。现在是设计工作：你铺下的 exchange、queue 和 binding 是一份公共契约 —— 你不拥有的服务会向你的 exchange 发布、从你的 queue 消费。把命名、持久性、顺序、版本化当作 API 设计决定来对待，因为上线之后它们就是。1

先把持久性做实：三件套

第 3 课的 confirm 承诺"已接受并已持久化" —— 但前提是底下的存储配合。一条消息要挺过 broker 重启，三者缺一不可：

  1. durable exchange —— 挺过重启；
  2. durable queue —— 挺过重启（重要的东西用 quorum queue：带复制，现代默认）；
  3. persistent message（delivery_mode=2）—— 消息本身写盘。
无声的谎言 默认值不是持久组合。向非 durable 队列发布并得到 confirm，确认的是一条重启即蒸发的队列。什么都不会报错；confirm 只是告诉了你错误的东西。把三件套一次性写进 topology-as-code 的清单里，之后就不用再按消息操心了。

顺序：你没有的保证

精确的陈述如下，比人们以为的弱：RabbitMQ 按 FIFO 投递，按队列、按发布 channel。但配上竞争消费者（第 1 课），先投递的 A 仍可能后于 B 完成 —— 慢消费者的消息最后落定。再加上重试（第 4 课），A 可能失败、在 TTL 队列里转一圈、一分钟后才被处理。跨消息的顺序永远是 best-effort。2

关键点 不要为全局顺序设计 —— 把顺序限定到真正要紧的粒度：按实体。两个工具：(1) 按 routing key 分片 —— consistent-hash exchange 对 key 做哈希、把消息摊到 N 条队列，于是 customer-42 的所有事件都落到同一条队列、同一个消费者：既有序又并行（Kafka 的 partition 套路，RabbitMQ 版）。(2) 让消费者与顺序无关 —— 事件携带状态版本，用第 3 课的状态守卫忽略过期事件。多数真实系统两者混用：序列要紧的地方分片（每账户账本），其余处处版本守卫。

扩容：一条队列不够时

  • 第一档杠杆 —— 给队列加消费者（竞争消费者）。能走很远：单队列每秒几万条消息。
  • 第二档 —— consistent-hash exchange 分片队列，当你需要有序并行或超出单队列吞吐时。
  • 看指标，别靠猜：队列深度和消费者 ack 速率告诉你何时拉杆。深度涨而消费者闲着 → prefetch 太小；深度涨且消费者全忙 → 加消费者或分片。

Schema 演进：事件一定会变

你的 order.created 载荷会加字段，总有一天会破坏形状。两层防御：

  • 宽容读者（tolerant reader）为默认：消费者必须忽略未知字段、把缺失的可选字段当默认值。这样增量变更完全无需协调。
  • 破坏性变更用带版本的 routing key：发布 order.created.v2。老消费者继续绑 order.created.v1 —— 两个版本并行跑，迁移消费者，然后撤掉旧 binding。没人需要步调一致地升级。

和 REST 版本化同一套纪律，还多一份礼物：不像请求/响应 API，旧版本在你迁移期间一直可用 —— broker 同时扛两股流量，互不冲突。

门面样式 —— 一套默认拓扑

一个多数领域都够用的起点，偏离要有理由：

  • 每个领域一个 durable topic exchange（orders、payments）—— 不要全局一个大 exchange，也不要每个服务一个。
  • 每个消费者组一条 durable quorum queue，命名 <service>.<purpose>（email.retries、analytics.orders）：所有者一目了然。
  • routing key 是带版本的事件：order.created.v1 —— 点分隔、命名发生了什么（该用事实的地方用事件，不用命令）。
  • 拓扑即代码、集中声明 —— 定义放仓库里、声明式应用；客户端临时 declare 只限开发环境。
  • 每个领域一套重试阶梯 + 停车场（第 4 课），挂在每条工作队列上。

自测

Q1. 哪三个设置让一条被 confirm 的消息挺过重启？

Durable exchange、durable quorum queue、persistent 投递模式。

缺任何一个，confirm 在技术上诚实、实际上撒谎 —— 队列或消息重启即消失。

Q2. 两个竞争消费者：A 先于 B 投递。谁先完成？

都行 —— 投递顺序从不绑定完成顺序。

慢消费者的消息无论投递多早都最后落定。重试会把差距拉得更大。

Q3. 扩容消费者的同时怎么保住"每客户"的顺序？

对 routing key 做哈希分片到多条队列，各配一个消费者。

同一客户 → 同一队列 → 同一消费者 → 有序；不同客户仍然并行。这就是 Kafka 的 partition 行为。

Q4. 一次破坏性载荷变更上线。老消费者怎么活下来？

发布到新的带版本 key；消费者按版本绑定。

迁移期间两股流量并行。没有步调一致的升级，没有一刀切的切换。

现在你来开车 —— 毕业设计

把整套设计画出来 —— 先别展开

外卖平台。事件：order.placed、order.accepted、order.delivered、restaurant.menu_changed。消费者：(a) 支付 worker 池（恰好一次处理、不稳定的 PSP —— 暂时性 500）；(b) 骑手调度服务，要求按订单有序，扩到 3 个实例；(c) 分析服务要所有订单事件；(d) 菜单缓存服务，menu_changed 绝不能丢但可以延迟。设计 exchange、队列、binding、持久性、重试，以及日后如何给 order.placed 做版本化。

展开一个好答案

exchange：订单事件一个 orders（topic、durable）；菜单事件一个 restaurants（topic、durable）；每个领域一套 retry + 停车场。

  • (a) payments.orders quorum 队列绑 order.placed，worker 池做竞争消费者，挂第 4 课的重试阶梯（PSP 500 = 暂时性）。恰好一次 = work-queue 形状 + 幂等 handler（第 3 课）。
  • (b) 前面放 consistent-hash exchange，3 条队列 dispatch.shard-0/1/2，对 routing key 里的 order_id 做哈希（order.<event>.<order-id>）—— 每个订单的事件进同一分片、同一消费者：按订单有序、跨订单并行。三种订单事件都绑上。
  • (c) analytics.orders quorum 队列绑 order.# —— 自己的拷贝、自己的节奏（pub/sub）。
  • (d) restaurants 上的 menu.cache quorum 队列绑 restaurant.menu_changed；刷新失败就走长 TTL 的重试阶梯 —— 延迟可接受、丢失不可接受（全套持久化三件套 + 耗尽后进停车场）。
  • 版本化：当 order.placed 破坏形状时，加 order.placed.v2；增量字段 meanwhile 靠宽容读者。

注意每个要求恰好对应一课：(a) = 第 1 课 work queue + 第 3 课幂等 + 第 4 课阶梯；(b) = 今天的顺序一节；(c) = 第 1 课 pub/sub；(d) = 持久性三件套。你的草图里若有这四种形状，前五课就都内化了。
