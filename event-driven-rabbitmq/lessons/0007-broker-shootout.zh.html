任务队列，还是记录日志？

选 broker 是一个问题，不是一张功能矩阵 —— 而答案经常是"都要"。

你真正需要的比较不是功能清单。三个工具，对"消息被处理之后怎么办"这个问题给出三种答案 —— 其余一切都从这个设计承诺推导出来。1

决定一切的那根轴

关键点 —— 决策流程 按顺序问：(1) 是工作还是历史？做完即弃的工作 → RabbitMQ 或 SQS。要重读的历史 → Kafka。(2) 若是工作：要路由还是要省运维？丰富路由、重试阶梯、多协议、自己掌控基础设施 → RabbitMQ。没有运维团队、已在 AWS、就要简单队列 → SQS（fan-out 加 SNS）。(3) 若是历史：到此为止 —— Kafka，按实体 partition 保序（第 5 课的 consistent-hash 逻辑，原生版）。而规模化之后的成熟答案常常是两个都要：Kafka 做记录流，RabbitMQ 做它下游的工作队列。

杂交为什么会失败、又为什么会成功

两个经典错配 拿 Kafka 当任务队列：log 没有按消息的 ack —— 失败的任务没法"退回"；offset 是整个 partition 一起挪的，毒消息处理（第 4 课）全靠自己造，而为了解困跳过前面的消息等于把失败也确认掉了。幂等的大批量流水线勉强能用；逐条工作很难受。

拿 RabbitMQ 当事件存储：ack 掉的消息就没了；掉队的消费者重连也没法重放昨天的流；"把消息留住"意味着永不 ack —— 吞吐被卡死，还复刻了第 2 课的 unacked 洪水。保留根本不是队列干的事。

杂交成功时：Kafka 持有不可变的 orders 流，每个团队随意回放；其中一个消费者的工作很薄 —— 追 log、把工作项发布到 RabbitMQ 的 exchange，由路由、重试、停车场（第 1–5 课全套）接管。两个工具各自守住 at-least-once 契约的一半，接缝处用幂等缝合。

你的 RabbitMQ 课程知识对应到哪

  • Ack（第 2 课）：Kafka 的对应物是提交的 offset —— 按消费者组、不按消息。SQS 是 visibility timeout 过后的 DeleteMessage：忘了及时删，消息就回来 —— at-least-once 多了几步，幂等的账单（第 3 课）一样要付。
  • 竞争消费者（第 1 课）：Kafka 的消费者组原生自带 —— partition 数就是并行度上限。SQS 免费送；这是它最漂亮的一手。
  • 顺序（第 5 课）：Kafka 每个 partition 严格 —— 不管你有没有要求，consistent-hash 的设计直接给你；热点实体照样独占一个 partition。RabbitMQ 的 best-effort 无论如何都需要守卫模式兜底。
  • 重试阶梯（第 4 课）：纯 RabbitMQ 惯用法。Kafka 需要应用层 retry topic；SQS 有 redrive policy —— 内置停车场，其实是它最贴心的主张。

自测

Q1. 财务要在一个 bug 之后重处理所有订单事件。选哪个？

Kafka —— 保留的日志，offset 随便回。

回放是记录日志的定义能力。RabbitMQ 里 ack 掉的历史就没了，无保留的队列装不出这个能力。

Q2. AWS 上五人创业公司要一个任务队列。选哪个？

SQS —— 零运维、按请求付费、没有集群。

不需要路由花样，也没有运维团队去跑 RabbitMQ。等路由复杂度或自建需求真来了再换（广播用 SNS 补）。

Q3. Kafka 消费者在一个 partition 里失败了一条记录。缺什么？

按消息的 ack —— offset 是整批一起挪的。

整个 partition 的位置一起提交；失败那条要么靠应用层 retry topic，要么随批跳过或卡住。

Q4. SQS 为什么会把没删的消息再投一次？

visibility timeout 到期，消息重新可见。

就是换了件衣服的 at-least-once（第 2/3 课）：同样的重投、同样的幂等要求。

现在你来开车 —— 三个判断

把每个选择论证一遍 —— 先别展开

(a) 网约车公司：司机位置流（每秒 1 万条）喂 ETA 模型和实时地图，外加派单任务（"撮合这一单"）必须恰好执行一次。(b) 银行：支付事件归档，下游每个审计消费者独立回放，每季度新增消费者。(c) 你自己工作中的系统 —— 你现在正在做的那个。每个都给出：选哪个 broker、为什么、以及你的选择引入的那一个风险。

展开论证

(a) 两个都要。位置流是历史形状 —— Kafka，按 ride/driver ID partition；可回放的地图回填与模型训练正是 log 的强项。派单是工作 —— RabbitMQ：恰好一次撮合比回放重要，重试和停车场是惯用法。风险：两套 broker 要运维，接缝处要幂等。

(b) Kafka，毫无疑问 —— 这些需求就是记录日志的定义：保留、独立消费者组、新来者可回放。按账户 ID 作 key 保每账户顺序。风险：删除/GDPR 需要 log compaction 设计，而且 partition 数定得偏早（加 partition 会改变 key 的落位）。

(c) 诚实的答案用关键点的流程：先问工作还是历史，再问路由还是运维，而且第一版只有 RabbitMQ 完全没问题 —— 第 1–6 课全套都适用 —— 等真的出现"要回放的消费者"再加 Kafka，不提前。

这里练的技能是拒绝功能矩阵思维：上面每个需求都靠"处理之后怎么办"这个问题点名它的 broker，而不是靠吞吐数字或流行度。
