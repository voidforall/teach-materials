Your Publish Might Have Done Nothing

The publisher's half of the contract: confirms, returns, and why duplicates are guaranteed.

Lesson 2 made the consumer side safe: no ack, no deletion. But that's worthless if the message never made it into the broker — and a plain publish() is a fire into the dark. It's asynchronous and unacknowledged: a TCP send that succeeds tells you nothing about whether RabbitMQ accepted, routed, or persisted anything.1

Two failure modes, two features

Publisher-side failures and the RabbitMQ feature for each
FailureWhat goes wrongFeature
Broker never got itconnection died mid-publish; broker crashedpublisher confirms
Broker got it, routed nowhererouting key matched no binding (Lesson 1's silent drop)mandatory + returns

Confirms flip the ack relationship around: the broker sends you back an ack* for each publish that was accepted and — on a durable queue — persisted to disk. No confirm = you don't know it landed = you retry. That's the whole protocol: enable confirms, wait (or collect async), retry on failure/timeout.

Mandatory + returns close the Lesson 1 trap: publish with mandatory=true and an unroutable message comes back to you (a "basic.return") instead of vanishing. In production, unroutable messages are a topology bug — you want the alarm, not the silence.

Keystone Confirms + retries on the publisher, acks + redelivery on the consumer — put together, both ends can fail and no message is lost. The price: duplicates on both ends too. A retried publish after a lost confirm may have actually landed; a redelivered message was maybe already processed. At-least-once is a system-wide property, and it terminates in one place: the handler must be idempotent.

Duplicates are guaranteed — design for them

People treat duplicates as a rare corruption. In a confirmed, redelivering system they are a normal occurrence — the cost of never losing anything. Three idempotency strategies, in order of preference:

  1. Natural idempotency — the operation is already a no-op when repeated. user.email = x is idempotent; balance += 10 is not. Prefer setting end-state over applying deltas whenever you control the event schema.
  2. Deduplication key — give every message a unique ID at creation (order-4711-created, or a UUID) and record processed IDs in the consumer: INSERT INTO processed_messages … ON CONFLICT DO NOTHING; if the insert conflicts, you've seen it — ack and skip.
  3. Version/state guard — for state machines, gate on version: "only apply order.cancelled if state = PAID." Stale or duplicate transitions fall through harmlessly.
Anti-pattern — the dual write Commit the order to your DB, then publish order.created. Two systems, no shared transaction: the publish after a failed commit fires anyway (phantom event), or the process dies between commit and publish (lost event). You cannot atomically "write DB and publish." The fix is the transactional outbox — write the event into an outbox table in the same DB transaction, and relay it to the broker separately. Full treatment in Lesson 6.

Check yourself

Q1. Your publish call returned without error. Where is the message?

Unknown — a plain publish promises nothing.

Send success covers the socket, not the broker. Only a confirm proves acceptance (and persistence, for durable queues).

Q2. A confirm never arrives; you retry the publish. What can happen?

Both copies land — a duplicate message.

The original may have succeeded with the confirm lost on the way back. Retries make duplicates routine, never rare.

Q3. Handler does: email a gift card, then balance -= 10. Idempotent?

No — the email doubles and balance drops twice.

Side effect plus delta: the worst case. Needs a dedup key before the email, and balance guarded by it too.

Now you drive

Design it — before you reveal

Your service handles invoice.paid by: marking the invoice paid in the DB, adding 100 loyalty points (points += 100), and emailing a receipt. Redelivery just happened. (a) Which steps are already idempotent? (b) Which need guarding, and how? (c) Write the ordering of steps that makes the whole handler safe.

Reveal one good answer

(a) Marking paid — natural idempotency, if it's SET state='paid' WHERE id=? rather than a delta; state guard helps too (only apply if state was OPEN). (b) points += 100 — a delta; convert to dedup: insert (message_id → invoice_id) into a processed table ON CONFLICT DO NOTHING and award points only if the insert landed. The email — an external side effect; gate it on that same fresh insert. (c) Order: dedup-insert first (it's the once-only token), then mark paid + points in one DB transaction, then send the email, then ack — accepting the one residual window (email sent, ack lost, redelivered) where the dedup row now suppresses the duplicate email.

The dedup insert is the linchpin: it converts "did I already handle this?" into a single atomic DB question. Everything else hangs off that answer.
