Producers Never Touch Queues

The one diagram all of RabbitMQ hangs off — and the folk model it corrects.

You've published and consumed messages before, so you've used this model — but most people who "know RabbitMQ basics" actually carry a folk model closer to SQS: send message to queue, receive from queue. RabbitMQ's model is richer, and the richness is exactly what you'll exploit when designing real systems. This lesson installs the correct mental diagram.1

The canonical pathway

A message is published to an exchange, never to a queue. The exchange copies it into every queue whose binding matches the routing key.

Keystone Producers address exchanges; consumers read queues; bindings are the glue. Producer and consumer share no names — only the exchange's routing rules decide where a message lands. That indirection is the whole point: it's what lets you add a consumer (an audit log, a new service) without touching the producer's code.
Folk model to unlearn "I'll publish to the orders queue." In AMQP you publish to an exchange. The common escape hatch — a default exchange ("") that routes by queue name — is why the folk model survives: tutorials look like queue-to-queue messaging. It's a special case, not the model.

Message fate, decided at the exchange

A message that matches no binding is dropped — silently, unless the publisher asked otherwise (mandatory flag / publisher returns — Lesson 3). This is the number-one surprise in systems that "lose" messages: nothing crashed; the routing key just matched nothing.

The four exchange types you'd actually pick

Exchange types — what the binding matches against the routing key
TypeMatch ruleUse it for
directexact equalityone category of event (order.created)
fanoutignore key, copy to all bound queuesbroadcast (cache invalidation, config reload)
topicwildcard pattern: * = one word, # = zero+most real systems (order.*, #.failed)
headersmatch message headers, not keyrare; routing on structured attributes

Default to topic. It subsumes direct (exact key) and costs nothing extra. Most production topologies end up as one durable topic exchange per domain, with a queue per consumer group bound by the events it wants.2

Two shapes every system is made of

Same pathway, opposite queue-sharing discipline. Getting this distinction crisp is what Lesson 5's topology design builds on:

  • Work queue (competing consumers): several consumers share one queue; each message is handled by exactly one of them. For doing work — "process this payment." Scale by adding consumers.
  • Pub/sub: each consumer has its own queue bound to the exchange; every consumer gets a copy of every message. For reacting to facts — "order created: send email, update analytics, audit log."

The pattern lives in the topology, not the code: bind N queues for pub/sub, one queue with N consumers for work. Both can coexist against the same exchange.

Check yourself

Q1. A producer must deliver a copy of every order event to three services. What topology?

One exchange; one queue per service; each queue bound to it.

Three separate queues = pub/sub: each service consumes its own copy independently, at its own pace, with its own acks.

Q2. A message's routing key matches no binding on that exchange. What happens?

The broker discards the message outright, quietly.

No error reaches the producer by default. Publisher-side detection (mandatory/returns) comes in Lesson 3.

Q3. Bindings order.* and #.failed exist. Which matches order.failed?

Both match — the message reaches both queues.

Topic exchanges copy to every matching binding. * is exactly one dot-separated word; # is zero or more.

Now you drive

Design it — before you reveal

Your checkout service publishes order.created, order.paid, order.cancelled. Requirements: (a) payments must be processed by the worker pool (exactly one worker per order event); (b) the analytics service wants every order event; (c) a "failures" service wants only order.cancelled.

Sketch: exchange(s), type, queues, bindings. How many queues?

Reveal one good answer

Three queues, one topic exchange (say orders):

  • q.payments bound order.* → consumed by the worker pool sharing this one queue (competing consumers ⇒ exactly one worker per event, requirement a).
  • q.analytics bound order.# → analytics' private copy (b).
  • q.failures bound order.cancelled → only cancellations (c).

Notice the moves: requirement (a) is a work-queue, (b) and (c) are pub/sub — same exchange, different binding discipline per queue. Also notice what we did not do: no filter code anywhere; routing is declarative.
