生产者从不直接碰队列

RabbitMQ 全部挂在一张图上 —— 以及它要纠正的那个民间模型。

你已经发布和消费过消息，所以其实用过这个模型 —— 但大多数"懂 RabbitMQ 基础"的人脑中装的其实是一个更接近 SQS 的民间模型：把消息发到队列，再从队列收。RabbitMQ 的模型更丰富，而这层丰富性恰恰是你在设计真实系统时要利用的东西。本课装上正确的心智图。1

标准通路

消息是发布给 exchange（交换机）的，从不直接给 queue（队列）。exchange 把它复制进每一个 binding（绑定）匹配 routing key 的队列。

关键点 生产者寻址 exchange；消费者读取 queue；连接两者的是 binding。生产者和消费者之间不共享任何名字 —— 消息落在哪里完全由 exchange 的路由规则决定。这层间接性正是全部意义所在：它让你能在不动生产者代码的情况下新增一个消费者（审计日志、新服务）。
要抛弃的民间模型 "我把消息发到 orders 队列。" 在 AMQP 里你发布到一个 exchange。常见的逃生舱 —— 按队列名路由的 default exchange（""）—— 正是民间模型得以存活的原因：教程看起来就像"队列到队列"的消息传递。但那是特例，不是模型本身。

消息的命运，在 exchange 处决定

一条不匹配任何 binding 的消息会被直接丢弃 —— 默认悄无声息，除非发布者另有要求（mandatory 标志 / publisher returns，第 3 课）。这是"丢消息"系统里排名第一的意外：什么都没崩，只是 routing key 没匹配上任何东西。

四种你会真正用到的 exchange 类型

exchange 类型 —— binding 拿什么去匹配 routing key
类型匹配规则适用场景
direct完全相等单一类别的事件（order.created）
fanout忽略 key，复制到所有绑定的队列广播（缓存失效、配置刷新）
topic通配模式：* = 一个词，# = 零个或多个大多数真实系统（order.*、#.failed）
headers匹配消息 header 而非 key少见；按结构化属性路由时

默认选 topic。它涵盖了 direct（精确 key），又不额外付出什么代价。多数生产拓扑最终都是每个领域一个持久化的 topic exchange，每个消费者组一条队列，按自己关心的事件绑定。2

一切系统都由两种形状构成

同一条通路，相反的队列共享纪律。把这个区分弄清楚，正是第 5 课拓扑设计的基础：

  • work queue（竞争消费者 / competing consumers）：多个消费者共享一条队列；每条消息由其中恰好一个处理。用于干活 —— "处理这笔支付"。扩容 = 加消费者。
  • pub/sub（发布订阅）：每个消费者有自己的独立队列绑定到 exchange；每个消费者拿到每条消息的一份拷贝。用于对事实做反应 —— "订单创建了：发邮件、更新分析、记审计日志"。

模式长在拓扑里，不在代码里：绑 N 条队列就是 pub/sub，一条队列挂 N 个消费者就是 work queue。两者可以同时挂在同一个 exchange 上。

自测

Q1. 一个 producer 要把每条订单事件都复制给三个服务。用什么拓扑？

一个 exchange；每个服务一条队列；各自绑定上去。

三条独立队列 = pub/sub：每个服务按自己的节奏、带自己的 ack 消费自己的拷贝。

Q2. 一条消息的 routing key 在 exchange 上没匹配到任何 binding。会怎样？

broker 直接丢弃这条消息，无声无息。

默认不会有任何错误到达生产者。发布侧的检测（mandatory/returns）第 3 课讲。

Q3. 已有 order.* 和 #.failed 两个 binding。order.failed 匹配谁？

两个都匹配 —— 消息进入两条队列。

topic exchange 会复制到每一个匹配的 binding。* 恰好一个点分隔词；# 零个或多个。

现在你来开车

动手设计 —— 先别展开

你的结账服务发布 order.created、order.paid、order.cancelled。要求：(a) 支付必须由 worker 池处理（每条订单事件恰好一个 worker 处理）；(b) 分析服务想要所有订单事件；(c) 一个"失败"服务只要 order.cancelled。

画出：exchange（几个、什么类型）、队列、binding。一共几条队列？

展开一个好答案

三条队列，一个 topic exchange（比如 orders）：

  • q.payments 绑 order.* → worker 池共享这一条队列消费（竞争消费者 ⇒ 每条事件恰好一个 worker，要求 a）。
  • q.analytics 绑 order.# → 分析服务的私有拷贝（b）。
  • q.failures 绑 order.cancelled → 只收取消事件（c）。

注意这些手法：要求 (a) 是 work queue，(b) 和 (c) 是 pub/sub —— 同一个 exchange，每条队列不同的绑定纪律。还要注意我们没做的事：任何地方都没有过滤代码；路由是声明式的。
