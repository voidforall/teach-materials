体面地让一条消息失败

dead-letter exchange、带退避的重试阶梯，以及毒消息的停车场。

第 2 课给了你 nack，还有一个我当时按下不表的警告：nack(requeue=true) 会把消息直接塞回队列头部 —— 立刻重投、滚烫循环、同样的失败、永远如此。本课给出生产环境的答案：一条为"现在处理不了"的消息准备的机械化流水线。1

Dead-lettering：你配置的转发，不是你写的代码

一条队列可以声明 dead-letter exchange（DLX）—— "消息未经消费就离开本队列时，去哪里"。三种触发条件：2

什么会让一条消息从队列里被 dead-letter
触发时机
rejected消费者 nack/reject 且 requeue=false
expired消息 TTL 到期（按消息或按队列）
overflow队列达到最大长度 —— 最老的消息被挤掉

被 dead-letter 的消息会带着原始属性重新发布到 DLX，外加一个 x-death header（来自哪个队列、原因、次数、时间戳）。之后就是普通路由 —— 下面的一切都在利用这一点：DLX 可以路由回你自己的拓扑，而不只是进一个错误桶。

关键点 队列 TTL 到期会把消息 dead-letter；DLX 把它路由回工作队列。在转发前面放一条队列，你就造出了一个定时器 —— 延迟重试 —— 零代码。退避（backoff）只是一串 TTL 递增的这种队列。broker 负责睡；你的消费者只会看到"稍后再试"。

重试阶梯

失败路径：q.orders 把消息 dead-letter 进 retry exchange → 落进某条 TTL 队列 → 到期把它路由回工作队列。死太多次（x-death 计数）后，改道去停车场而不是继续转圈。

跟着一条消息走一遍：消费者处理失败 → nack(requeue=false) → q.orders 把它 dead-letter 到 retry exchange → 它在 retry.10s 里待十秒 → TTL 到期又 dead-letter 回 work → 消费者再试一次。第三次失败：retry exchange 看到 x-death.count ≥ 3，把它路由进 parking lot（停车场）—— 一条没有消费者的普通队列，它的职责就是被人看着：看板、告警、人工。

两个常见坑 (1) 在 handler 里 sleep —— 白白占住一个消费者槽位（prefetch，第 2 课）还什么都没干；负载一上来整个 worker 池都在睡觉。永远不要在 handler 里 sleep；让 broker 替你持有消息。(2) 在共享的 retry 队列里用按消息 TTL —— 到期只在队列头部检查，一条长 TTL 消息会把后面所有短 TTL 的都堵住（队头阻塞）。一条队列一个 TTL —— 所以才叫队列阶梯。

毒消息，与循环保护

毒消息（poison message）每次都失败 —— 载荷损坏、引用缺失、handler 有 bug。它永远不会成功，重试纯属浪费；更糟的是它堵住队列、饿死好消息。阶梯通过 x-death 计数自动处理它：重试有上限，然后进停车场。停车场不是 bug 追踪器 —— 把它接到一个上面（告警、落到表里、建 ticket），否则永远不会有人看。

RabbitMQ 还保护即时循环：一条消息被 dead-letter 回它已经待过的队列、且什么都没变时，会被丢弃而不是永远打转。你的阶梯本来也避开了循环 —— 每一跳都换了 TTL 队列、计数加一。

自测

Q1. 为什么是一串 TTL 队列，而不是一条 retry 队列？

到期只在队列头部检查。

一条队列里混着不同 TTL 会导致队头阻塞：一条 5 分钟的消息压住所有 10 秒的。一条队列一个 TTL 就避开了。

Q2. 哪个 nack 调用会把消息送上重试路径？

nack 且 requeue 为 false。

requeue=true 是第 2 课那个立即重投的滚烫循环；false 才触发队列的 dead-lettering。

Q3. 机械化上，可重试失败和毒消息的区别是什么？

反复失败之后的 x-death 计数。

你无法预知未来 —— 所以设尝试上限（计数 ≥ 3）然后停进停车场。暂时性错误在阶梯内恢复；毒消息永远不能。

Q4. 五分钟退避期间，是谁在"睡觉"？

没有人 —— 消息在 broker 的 retry 队列里等着。

消费者继续处理别的消息；在 handler 里睡会烧掉 prefetch 槽位并拖垮整个池。

现在你来开车

动手设计 —— 先别展开

你的发邮件消费者在 SMTP 供应商返回 500（暂时性，约一分钟恢复）时会失败，偶尔也会收到 nobody@invalid 这种地址（永久性）。设计失败路径：exchange、队列、TTL、binding，以及消费者在两种失败下分别做什么。提示：消费者能在 nack 之前区分这两种情况吗？

展开一个好答案

能 —— 先分类，再 nack。供应商的 5xx 是可重试的：nack(requeue=false) 送上阶梯（10s → 1m → 5m，然后停进停车场）。被拒的地址（4xx / 校验失败）是毒消息 —— 重试永远修不好它，所以别上阶梯：要么直接 publish 到 parking，要么保留一个两跳的迷你阶梯（重试一次求稳）。拓扑就是阶梯图：q.emails 挂 DLX → retry exchange → 按 routing key 绑定的 TTL 队列；TTL 到期路由回 work；x-death ≥ 3 → parking。

深层要点：重试策略按失败类别分，而消费者是唯一知道类别的地方。阶梯负责"再等等可能有救"；停车场负责"再等也没救"；分类是拓扑替你做不了的代码职责。
