Glossary

Authoritative vocabulary for the course. Lessons adhere to these definitions.

Producer (publisher)
The client that publishes messages to an exchange. It never addresses a queue directly (except via the default exchange's name-as-routing-key special case).
Exchange
A routing table inside the broker. Receives published messages plus a routing key, and copies each message into every queue whose binding matches. Types: direct, fanout, topic, headers.
Routing key
An arbitrary string the publisher attaches to a message. What it means is defined entirely by the exchange type's match rule; dot-separated words for topic (order.paid).
Binding
The rule attaching a queue to an exchange — for topic exchanges, a pattern with * (exactly one word) and # (zero or more words). A message matching no binding is dropped.
Queue
A durable-ish FIFO buffer holding messages until a consumer acknowledges them. Competing consumers share one queue; pub/sub gives each consumer its own.
Consumer
A client subscribed to a queue, receiving deliveries it must ack (Lesson 2).
Default exchange
The nameless direct exchange every broker has: routing key = queue name. The source of the "publish to a queue" folk model.
Competing consumers (work queue)
Many consumers on one queue; each message processed exactly once by one of them. Shape for doing work. EIP name: Competing Consumers.
Pub/sub
One exchange, one queue per consumer group, every group gets its own copy. Shape for reacting to facts. EIP name: Publish-Subscribe Channel.
Ack (basic.ack)
The consumer's verdict "handled — delete it." The only thing that deletes a message from a queue with manual acks. Placement of the ack call (after processing succeeds, not on receipt) is the consumer's durability policy.
Nack / reject
"Can't handle it." With requeue=true it goes back to the queue (careful: instant redelivery loop); with false it is dropped or dead-lettered (Lesson 4).
Unacked
Limbo state: delivered to a consumer, awaiting verdict. Hidden from competitors but not deleted. If the channel/connection dies, everything unacked requeues.
At-least-once delivery
The guarantee manual acks buy you: a message is delivered one-or-more times, never zero. Consequence: consumers must be idempotent (safe to run twice on the same message).
Auto-ack
Mode where the broker deletes messages as it sends them — at-most-once. Crash mid-processing loses work. Only for lossy traffic (metrics, ticks).
Prefetch (QoS)
Cap on unacked in-flight messages per consumer channel. Never 0 (unlimited) in production; 1 for strict fairness/order-sensitivity; 10–100 typical. Also the fairness mechanism for competing consumers.
Redelivered flag
Marker on a message the broker has delivered before. A signal for retry logic, not a substitute for idempotency.
Publisher confirms
Broker-side acks for publishes: the broker confirms each message it accepted (and persisted, if the queue is durable). No confirm → retry → duplicates possible. Complements consumer acks to make at-least-once a system-wide property.
Mandatory / returns
Publish flag making unroutable messages (no binding matched) come back to the publisher as a basic.return instead of being silently dropped. In production, treat an unroutable message as an alarm.
Idempotency
Handler property: running twice on the same message has the same effect as once. Achieved by natural idempotency (set state, don't apply deltas), a deduplication key (unique message ID + processed-table insert), or state/version guards.
Deduplication key
Unique ID assigned to a message at creation; consumers record processed IDs atomically (ON CONFLICT DO NOTHING) to detect redeliveries.
Dual-write problem
Writing to a DB and publishing to a broker in one code path — no shared transaction, so crashes produce phantom or lost events. Solved by the transactional outbox (write event + state in one transaction; relay separately).
Outbox (transactional outbox)
Pattern: persist the event in an outbox table inside the same DB transaction as the state change; a separate relay publishes it with confirms and marks rows sent. Full lesson: 6.
Dead-letter exchange (DLX)
A queue attribute naming an exchange that receives the queue's dead-lettered messages. Triggers: rejected (nack with requeue=false), expired (TTL ran out), overflow (max length hit). Dead-lettered messages gain an x-death header and are re-published through the DLX with normal routing.
x-death header
Array the broker attaches to dead-lettered messages: source queue, reason, count, timestamps. The count powers retry caps ("park after 3 deaths").
Retry ladder
Backoff pattern: a chain of TTL queues (10s → 1m → 5m …), each dead-lettering back to the work exchange on expiry. Broker holds the message during backoff; consumers never sleep. One TTL per queue — mixed per-message TTLs head-of-line block.
Poison message
A message that can never succeed (malformed, dangling reference, handler bug). Mechanically detected by capped x-death count; routed to a parking-lot queue for humans. Wire the parking lot to alerts/tickets or it's a black hole.
Parking lot
Terminal queue for exhausted retries. No consumer; monitored. Not a bug tracker — feed one.
TTL (time to live)
Per-queue (preferred) or per-message expiry. Expiry dead-letters the message — the mechanism that turns a TTL queue + DLX into a delay timer.
Durability trinity
Durable exchange + durable queue (quorum) + persistent message (delivery_mode=2) — all three, or a confirmed message still vanishes on broker restart. Defaults are not this combination.
Quorum queue
Replicated, consensus-based queue type; the modern default for data that matters. Application-code impact ~zero; it's a durability/ops upgrade over classic queues.
Consistent-hash exchange
Exchange type (bundled plugin) that routes by hashing the routing key across bound queues — entity-scoped ordering with parallelism. Kafka-partition behavior in RabbitMQ.
Tolerant reader
Consumer that ignores unknown fields and defaults missing optional ones — makes additive schema changes coordination-free. Paired with versioned routing keys (order.placed.v2) for breaking changes.
Transactional outbox (relay)
Pattern making "commit state + publish event" safe: both rows commit in one DB transaction; a separate relay publishes pending outbox rows with confirms and marks them sent. Relays may double-publish — consumers stay idempotent. Relay implementations: poller or CDC (Debezium).
Saga
A multi-service business process as a sequence of local transactions, each with its own outbox. No atomicity spans services; instead every forward step has a compensating action (reserve ↔ release, charge ↔ refund). Failures are recovered, not prevented.
Choreography
Saga coordination by events alone: services react to each other's facts; the flow emerges from bindings. Loose coupling, but process logic scatters as steps grow. Rule of thumb: ≤3 steps.
Orchestration
Saga coordination by a state machine that sends commands and consumes results, owning failure branches and compensations explicitly. The process is auditable in one place. Use for ≥4 steps, branching, timeouts, money. Failure mode: the god orchestrator.
Compensating action
The undo for a completed saga step (refund, release, cancel). Ordered reverse execution on failure. Some steps have no meaningful compensation — route them to humans, not automation.
Eventual consistency
Cross-service state converges asynchronously. Technically handled by idempotency + version guards; the remaining burden is UX — model pending states, don't fake synchronous answers, monitor lag as an SLA.
Log of record (vs task queue)
The broker-choice axis: what happens after handling? A task queue deletes on ack (work to do once — RabbitMQ, SQS); a log of record retains and is re-readable at any offset (history — Kafka). Mature systems often run both: Kafka stream of record + RabbitMQ work queues at the seam.
Offset (Kafka)
A consumer group's per-partition read position — the analogue of an ack, committed in batches, never per message. Failure handling and retries are application-level (retry topics).
Consumer group (Kafka)
Kafka's competing consumers: members share a group, partitions are assigned among them — parallelism capped at partition count, strict per-partition ordering. Independent groups each read the full log (pub/sub shape).
Visibility timeout (SQS)
SQS's ack analogue: a received message hides for N seconds; if not deleted in time it reappears. At-least-once with the same idempotency bill; timer tuning replaces prefetch tuning.
Redrive policy (SQS)
SQS's built-in parking lot: after maxReceiveCount, messages move to a dead-letter queue. The nicest opinionated version of Lesson 4's ladder.
Event (fact)
A notification that something already happened (order.created). Contrast with a command (charge.card), which asks something to happen. Drives who owns naming and payloads.
