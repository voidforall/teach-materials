Linux Sockets · 第 6 课实战 EN

select、poll、epoll

一个线程、一万客户端、零次无谓阻塞。诀窍不是魔法 —— 只是向内核问一个问题："这些 fd 里，现在哪些就绪了？"

第 5 课用"每连接一个进程/线程"换来并发。到一万条绝大多数时间闲着的连接（聊天、代理、物联网），就是一万个栈外加调度器抖动 —— 即C10K 问题。替代方案：多路复用。登记对一批 fd 的兴趣；睡到其中任何一个就绪；只处理那几个。

三个 API，同一个思想的效率三级跳

API你要传什么每次调用成本fd 上限
select三个 fd_set 位图，每次重建双向 O(全部 fd) + 整表拷贝FD_SETSIZE = 1024
pollstruct pollfd 数组O(全部 fd) 扫描，免重建位图实际无上限
epoll（Linux）常驻内核的注册表（epoll_ctl）O(就绪 fd) —— 内核保存兴趣表实际无上限

看趋势：select/poll 是无状态提问 —— 每次调用都要重新描述整个 fd 集合，内核全量扫。epoll 是常驻订阅 —— 内核记住你在乎什么，醒来时把就绪列表递给你。就这一处架构差异，解释了为什么 nginx、Redis 和 Linux 上一切现代高并发服务端都建在 epoll 之上（macOS/BSD 对应物：kqueue；跨平台封装：libuv、libevent）。

关键认知 select/poll：每次调用把监看名单推给内核。epoll：注册一次，内核把就绪事件推给你。一万连接、十个活跃时，select 扫一万，epoll 返回十。就绪驱动、绝不为单个 fd 阻塞 —— 这就是事件循环范式的全部。

epoll 服务端骨架

int ep = epoll_create1(0);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = s };
epoll_ctl(ep, EPOLL_CTL_ADD, s, &ev);          // 订阅：监听者

struct epoll_event ready[64];
for (;;) {
    int n = epoll_wait(ep, ready, 64, -1);       // 睡到"某个东西"就绪
    for (int i = 0; i < n; i++) {
        if (ready[i].data.fd == s) {             // 监听者就绪 → 新客户端
            int c = accept(s, NULL, NULL);
            set_nonblocking(c);                  // 第 8 课：此处必不可少
            ev.events = EPOLLIN; ev.data.fd = c;
            epoll_ctl(ep, EPOLL_CTL_ADD, c, &ev);
        } else {                                 // 客户端就绪 → 读一块
            int c = ready[i].data.fd;
            ssize_t r = read(c, buf, sizeof buf);
            if (r <= 0) { epoll_ctl(ep, EPOLL_CTL_DEL, c, NULL); close(c); }
            else append_to_conn_buffer(c, buf, r);   // 第 4 课分帧在此生效
        }
    }
}

注意这个循环从不做的事：等某一个客户端。慢客户端只花一次迭代；一万个闲连接不说话就不花钱。这个循环是单线程的 —— 状态都放在你的连接结构体里，而第 4 课的"每连接一缓冲"现在成了承重墙，不再是可选项。

回忆检索

select 为什么把 fd 卡在 1024？

位图是定长。

fd_set 是编译进 libc 的 FD_SETSIZE 位固定数组。调高它属于重编译碰运气；poll（动态数组）与 epoll（根本不传集合）彻底拆掉了天花板。

一万连接、5 个活跃。三种 API 每次醒来各查多少 fd？

一万、一万、5。

select 和 poll 每次调用都要全量扫注册集 —— 活不活跃都得扫。epoll 的就绪列表恰好只含变为就绪的 fd，成本跟着活跃度走，而不是跟着规模走。

事件循环的每连接缓冲区放在哪里？

用户态堆上。

"可读"只意味着"至少到了一个字节"。一个事件可能只带来半帧；一帧也可能横跨多次事件。重组是你自己的事 —— 内核只排队字节，从不排队消息。

epoll 服务端里客户端 fd 为什么必须非阻塞？

就绪不等于一直在。

EPOLLIN 只保证"当时有数据"；等你真去 read，可能已被别人读走 —— 阻塞 fd 会把整个循环睡死。写侧同理：发送缓冲一满，阻塞 write 就变成"所有人陪等"。细节在第 8 课。

亲手验证

动手 —— 体会 O(n) 对 O(活跃)，15 分钟（Linux/容器） 
# 一个 select 版服务端，每个循环打印自己扫了多少 fd
# （可直接替换第 1 课的服务端；strace 能看到系统调用风暴）
cc -Wall srv_select.c -o srv_select && strace -e trace=select,accept4,read ./srv_select

开 5 个 nc localhost 5000 会话，在其中一个发一个字节，看 strace：每次醒来前都有一场全量 select。再换成 epoll 骨架重演 —— epoll_wait 只返回那一个活跃 fd。行为相同，工作量天壤之别。macOS 用户请进 Linux 容器：docker run -it --rm -v $PWD:/w -w /w alpine sh，然后 apk add build-base strace。
