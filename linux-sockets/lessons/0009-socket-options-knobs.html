Socket Options & Kernel Knobs

setsockopt is where theory pays rent: restart a server without waiting, kill Nagle's latency tax, detect dead peers, and survive fd exhaustion.

Options come in two families, named by the level you pass: SOL_SOCKET (generic, any socket type) and IPPROTO_TCP (TCP-specific). The pattern never changes:

int one = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &one, sizeof one);

The options that matter, in order of how often they save you

  • SO_REUSEADDR (SOL_SOCKET, before bind). Lesson 2's TIME_WAIT remnant blocks rebinding. This option says "let me take this port anyway". Every server sets it; the only debate is whether to also allow two live listeners (SO_REUSEPORT — load-balancing across processes, kernel-aware).
  • TCP_NODELAY (IPPROTO_TCP). Nagle's algorithm delays small writes so they can coalesce — great for batch, terrible for request/response. Disabling it makes "write request, read reply" round-trips as fast as the wire allows. Set it on interactive connections; keep Nagle for bulk.
  • SO_KEEPALIVE (SOL_SOCKET). Kernel probes an idle connection every tcp_keepalive_time (default 7200s — useless!). Tune with TCP_KEEPIDLE/TCP_KEEPINTVL/TCP_KEEPCNT to ~60s/10s/3, or better: application-level heartbeats, which travel when the app is hung too, not just the OS.
  • SO_SNDBUF / SO_RCVBUF. Kernel buffer sizes. Default ~200KB; fat-pipe transfers or bursty receivers may need more — but bigger isn't free (memory per connection × 10k connections).
  • SO_LINGER. Changes close() semantics; the notorious l_onoff=1, timeout=0 variant aborts with RST instead of FIN — occasionally exactly the tool you need (discard unsent data now), usually a footgun.
Keystone Options are per-fd questions to the kernel, and timing matters: SO_REUSEADDR must precede bind, keepalive tunables must override the 2-hour default, and every option trades something (memory, coalescing, safety) for what it buys. Set options deliberately, and know which side of each trade you chose.

The fd-exhaustion survival kit

Lesson 5 leaked fds; here's the operational side. ulimit -n caps open fds per process (often 1024 — ancient). Raise it (setrlimit / systemd LimitNOFILE). And handle EMFILE from accept gracefully: the classic trick is a reserved "emergency fd" opened at startup, closed to make room for one more accept, which then gets closed immediately with the client told to retry — keeping the listener responsive instead of spinning.

Retrieve it

Your server can't rebind its port after a crash-restart. First move?

Set SO_REUSEADDR.

The old connection's TIME_WAIT lingers ~60s holding the port. SO_REUSEADDR (before bind) lets the new listener share the wildcard binding. Waiting, or killing TIME_WAIT via sysctl, is treating the symptom.

Why does a tiny request/response feel slow on default TCP over a fast LAN?

Nagle delays smalls.

Nagle holds a small write hoping to merge with the next one, and interacts with delayed ACK to add tens of ms. TCP_NODELAY sends immediately — for interactive protocols it's effectively free throughput-wise and halves perceived latency.

Default keepalive takes how long to notice a dead peer?

Two-plus hours.

tcp_keepalive_time defaults to 7200 seconds before the first probe. Production must tune TCP_KEEPIDLE & friends down, or — more robust — send application pings, which also detect an app that's hung while the kernel is fine.

SO_LINGER with timeout 0 — what does close() send?

RST, aborting.

It discards unsent data and slams the connection with a reset: peer sees ECONNRESET, no FIN handshake, no TIME_WAIT. Occasionally right (proxy shedding load, discarding backlogged writes); mostly a way to confuse peers and skip graceful shutdown.

Prove it to yourself

Try it — measure Nagle, 15 minutes 
# a server that answers each byte with a byte (no delay in app code)
nc -l 7006 -k            # macOS; on Linux use a 5-line loop server
python3 - <<'EOF'
import socket, time
s = socket.create_connection(('localhost', 7006))
for ndelay in (0, 1):
    s.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, ndelay)
    t0 = time.time()
    for _ in range(100):
        s.send(b'x'); s.recv(1)        # ping-pong
    print('TCP_NODELAY =', ndelay, '→', round((time.time()-t0)*10, 1), 'ms / 100 pongs')
EOF

Over loopback the gap may be small (everything's fast); over a real network or a tc netem delay 30ms-shaped link (Linux) it widens dramatically — that's Nagle+delayed-ACK interacting. Then inspect yourself: ss -tino shows nodelay, keepalive timers, and buffer sizes per live connection — every option you set is visible there. Set one, watch it appear.
