Concurrent Servers: fork & threads

Lesson 1's server serves one client at a time. The moment client #2 connects, it waits in the kernel's accept queue while you chat with client #1. Fix that.

The Lesson-1 loop is iterative: accept → serve → close → repeat. It is honest and correct, and it collapses the instant two clients overlap. The classic escalation, in order of historical appearance:

  • Process per connection — fork(). The child inherits every fd (that's Lesson 1's "sockets are files" dividend), serves its client, exits. Rock solid isolation; expensive (a full process image) at huge scale.
  • Thread per connection — pthread_create. Cheap stacks, shared address space (convenient and dangerous), same blocking style of code.
  • Event loop — one thread, many fds, never blocks. Lessons 6–8.
Keystone Concurrency comes from who owns the per-connection fd, and each model just answers that differently. fork: a copy of you owns it. Thread: a sibling of you owns it. Event loop: nobody owns anything — the loop borrows each fd when it's ready. Every design decision (isolation, shared state, scheduling) falls out of that one choice.

The fork pattern (shortest correct version)

for (;;) {
    int c = accept(s, NULL, NULL);
    if (c < 0) { perror("accept"); continue; }

    pid_t pid = fork();
    if (pid == 0) {              // child
        close(s);                //   doesn't need the listening door
        serve(c);                //   blocking reads/writes, Lesson 4 framing
        close(c);
        _exit(0);
    }
    close(c);                    // parent: hands the fd over, forgets it
}

The two close lines are the lesson. After fork both processes hold both fds — the listener and the connection. The child must close the listener (it's not accepting) and the parent must close the connection fd (the child owns it now). Miss either and fds leak per connection until the process limit kills your server. Also required, quietly: signal(SIGCHLD, SIG_IGN) (or a handler that waitpids) so finished children don't linger as zombies.

Same shape with threads: the spawned thread closes the listener copy conceptually (threads share fds — you just pass c), and — the part everyone forgets — the main thread does not close c, and the new thread detaches or is joined, or you leak thread objects instead of zombies.

Retrieve it

Right after fork(), how many connection fds exist for one client?

Two, one per process.

fork duplicates the fd table: parent and child each hold a descriptor pointing at the same kernel socket. The socket truly closes only when the last reference closes — hence both close()s matter.

What goes wrong if the parent forgets to close the accepted fd?

Server leaks fds.

Every connection leaves one live fd in the parent forever. After "ulimit -n" (often 1024) connections, accept fails with EMFILE and the server stops admitting anyone — a classic slow-death production bug.

Why SIG_IGN for SIGCHLD?

Prevents zombie children.

Finished children stay as zombies until the parent reaps them. SIG_IGN tells the kernel to auto-reap; the alternative is a waitpid(-1, ..., WNOHANG) loop in a handler. Zombies cost fd/PID resources, not memory — but they accumulate.

Two threads write() to the same socket. Interleaving risk?

Whole writes, shuffled.

A single write() is atomic with respect to the socket buffer (POSIX guarantees no byte-level interleaving for writes ≤ PIPE_BUF on pipes, and sockets serialize at the protocol layer), but the order of two threads' writes is a race. If order matters, use one writer thread or a lock — don't rely on luck.

Prove it to yourself

Try it — two clients at once, 20 minutes

Patch the Lesson-1 server's main loop with the fork pattern above, plus signal(SIGCHLD, SIG_IGN) (include <signal.h>). Then:

cc -Wall server5.c -o server5 && ./server5
# terminal 2 — a slow client: connect and just sit
nc localhost 5000        # type nothing; keep it open
# terminal 3 — proof of concurrency: this one is served instantly
printf 'still fast\n' | nc localhost 5000
# terminal 4 — watch the process tree while both are connected
ps -o pid,ppid,command | grep server5

Terminal 3 answered immediately while terminal 2 sat idle — that's concurrency. The ps output shows one parent (accepting) and one child per open client. Now delete each of the two close() lines in turn, reconnect in a loop, and watch lsof -p $(pgrep server5) fill with leaked fds. Break it on purpose once; never on accident again.
