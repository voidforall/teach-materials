UDP：数据报

TCP 是打电话；UDP 是寄明信片。消息保住了 —— 送达、顺序、连接，全没了。

一个标志改变世界：socket(AF_INET, SOCK_DGRAM, 0)。没有握手、没有 listen/accept、没有连接 —— 你把一个个自包含的数据报（datagram）发往地址，每个都自带回信地址。API 与模型同构：sendto(fd, buf, len, 0, &dest, dstlen) 与 recvfrom(fd, buf, len, 0, &src, &srclen) —— 发送者地址随每个包一起到达，因为根本没有"连接"来记住它。

明信片带什么、不带什么

  • 边界保留。一次 sendto = 一个数据报 = 一次 recvfrom。不需要分帧（第 4 课大部分作废 —— 注意：比你的读缓冲还大的数据报会被静默截断）。
  • 没有顺序。2 号包可能在网络上跑赢 1 号。
  • 没有送达。丢了就是丢了；没人重传，甚至没人通知。
  • 没有拥塞控制。UDP 从不退让 —— 这既是它快的原因，也是它反社会的危险。
关键认知 TCP 把复杂性外包给内核；UDP 把它外包给你的应用。在 UDP 上要有序、可靠，就得你自己造重传、序号、流控 —— QUIC 和各种游戏协议正是这样的定制可靠层。当单条消息价值低、延迟胜过完整性、或需要 multicast 时，选 UDP。

什么时候 UDP 是正确答案

  • DNS —— 一个查询装进一个数据报；丢了就重问。重问 60 字节，比握手便宜。
  • 游戏 / 直播媒体 —— 200 毫秒前的位置更新毫无价值，重传它反而污染现在。实时有损胜过迟到完美。
  • 本地发现 / 日志 —— 广播/组播、发完不管的 syslog、DHCP、mDNS。TCP 根本不能广播。
  • QUIC / HTTP/3 —— 现代变奏：在 UDP 之上的用户态可靠层，绕开中间盒和僵化的 TCP 栈。

回忆检索

两次 sendto 先后发出。第二次 recvfrom 会返回什么？

第二个整报。

UDP 保留消息边界：每次 recvfrom 恰好交出一个完整数据报，绝不两报混合。但"第二个发送"可能先到 —— 你丢掉的是顺序，不是分帧。

数据报比 recvfrom 缓冲还大会怎样？

静默截断。

内核拷贝装得下的部分，丢弃其余 —— 没有错误、没有重试标记（除非设了 MSG_TRUNC，Linux 会据此报告）。UDP 缓冲必须按协议最大报文来开。

UDP 代码为什么还常调 connect()？

钉住对端。

UDP 的 connect 不发任何包；它记录对端地址，于是可以只用 send/recv，且内核代为过滤 —— 别的来源的数据报直接丢弃。还解锁 ICMP 错误回传：对端不可达终于在下次 send 时以 ECONNREFUSED 现身。

你的 UDP 洪流灌满了链路。谁会退让？

谁也不退。

TCP 有拥塞控制（cwnd、丢包退避）；UDP 一无所有，会毫不客气地挤掉包括自己在内的一切。所以负责任的 UDP 应用要自己限速 —— 也是运营商限流重度 UDP 用户的原因。

亲手验证

动手 —— 10 分钟寄明信片 
# 终端 1：UDP 收件槽，给每个发送者+载荷盖戳
nc -ul 7003
# 终端 2：发两个数据报（每跑一次 nc = 一张独立明信片）
printf 'first\n'  | nc -u -w1 localhost 7003
printf 'second\n' | nc -u -w1 localhost 7003

再做 TCP 做不到的丢包实验：在容器里开 UDP 监听（docker run -it --rm -p 7004:7004/udp alpine sh，容器内：nc -ul 7004），宿主机用三行 Python 循环轰一万个微型数据报，数数到了几个。有丢的？很好 —— 你刚亲眼看到 UDP 在负载下丢流量，正是它又快又不可靠的那个性质。再用 TCP 重跑同样的计数对比。

然后用 C 写一遍 —— 就是第 1 课服务端减去 listen/accept，加上 recvfrom/sendto 和一个 sockaddr_storage 出参，原地址回发。
