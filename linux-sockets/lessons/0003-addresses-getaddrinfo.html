Addresses & getaddrinfo

sockaddr_in is a lie the kernel tolerates. The real address API is getaddrinfo: names, ports, IPv4-and-IPv6, resolved once and correctly.

Lesson 1 filled a sockaddr_in by hand — fine for learning, wrong for real code. Real programs take a host and a service ("example.com", "http") and must work whatever the IP version. That's getaddrinfo()'s job.

The struct zoo, tamed

  • struct sockaddr — the generic "address blob" every syscall takes. You never fill one; you cast.
  • struct sockaddr_in — IPv4: family, port (network order), 4-byte address.
  • struct sockaddr_in6 — IPv6: same idea, 16-byte address plus scope.
  • struct sockaddr_storage — a union big/aligned enough to hold either. Use it when you don't know which family arrives (e.g. accept).

And the byte-order rule that never goes away: anything crossing the sockets API in a struct field — ports, addresses — is big-endian network order. Convert every human integer with htons/htonl in, ntohs/ntohl out. Print real addresses with inet_ntop, parse strings with inet_pton — never inet_addr (obsolete, can't express failure).

Keystone sockaddr is the currency; sockaddr_in/_in6 are just two dialects; getaddrinfo is the translator that fills them for you. Your code says "connect me to this name and service"; the resolver returns a linked list of ready-to-use struct addrinfo — one per working address (possibly both IPv6 and IPv4) — and you try them in order.

The pattern (memorize this shape)

struct addrinfo hints = {0}, *res;
hints.ai_family   = AF_UNSPEC;      // IPv4 or IPv6 — let the resolver decide
hints.ai_socktype = SOCK_STREAM;    // TCP

if (getaddrinfo("example.com", "80", &hints, &res)) { /* fail */ }

for (struct addrinfo *p = res; p; p = p->ai_next) {
    int fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
    if (fd < 0) continue;
    if (connect(fd, p->ai_addr, p->ai_addrlen) == 0) break;  // connected
    close(fd);                                                    // try next
}
freeaddrinfo(res);   // the list is malloc'd — always free it

For a server, the same call with hints.ai_flags = AI_PASSIVE and host NULL yields a bindable address (the IPv6 :: wildcard that also takes IPv4, on Linux, is the modern default). The three calls that eat an addrinfo — socket, bind/connect — each take their family/protocol from the node itself, so one loop serves both IP versions. That's the whole point.

Retrieve it

Why does getaddrinfo return a linked list rather than one address?

Names map multiply.

A hostname can resolve to several addresses — IPv6 and IPv4, or multiple interfaces. The list is the resolver saying "try these in preference order"; your loop attempts each until socket+connect/bind succeeds.

Why must the port field go through htons()?

Wire order differs.

The struct field is copied onto the network as-is, and the network standard is big-endian — but your host (x86, ARM default) is little-endian. htons/htonl convert; forgetting it gives you a server on a very wrong port (5000 → 0x8813 → 34835).

Which struct do you pass to accept() when clients may be IPv4 or IPv6?

sockaddr_storage, cast.

It's sized and aligned for any family, and accept writes the real family into it; you then branch on ss.ss_family before treating it as sockaddr_in or _in6. A plain sockaddr_in would truncate IPv6.

What does AI_PASSIVE change, and who uses it?

Wildcards for bind.

It tells the resolver you want an address to listen on (INADDR_ANY / ::) rather than connect to. Servers set it; clients never do. Forgetting it is why getaddrinfo(NULL, port) sometimes returns unusable answers.

Prove it to yourself

Try it — rewrite the client, 15 minutes

Replace the hand-filled struct in your Lesson-1 toolkit with a real client:

// client.c — usage: ./client host port msg
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <netdb.h>

int main(int argc, char **argv) {
    struct addrinfo hints = {0}, *res;
    hints.ai_family = AF_UNSPEC; hints.ai_socktype = SOCK_STREAM;
    if (getaddrinfo(argv[1], argv[2], &hints, &res)) { perror("resolve"); return 1; }

    int fd = -1;
    for (struct addrinfo *p = res; p; p = p->ai_next) {
        fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
        if (fd < 0) continue;
        if (connect(fd, p->ai_addr, p->ai_addrlen) == 0) break;
        close(fd); fd = -1;
    }
    freeaddrinfo(res);
    if (fd < 0) { perror("connect"); return 1; }

    write(fd, argv[3], strlen(argv[3]));
    char buf[256];
    ssize_t n = read(fd, buf, sizeof buf - 1);
    buf[n > 0 ? n : 0] = 0;
    printf("echo: %s\n", buf);
    close(fd);
}
cc -Wall client.c -o client
./client localhost 5000 "via getaddrinfo"
# now against a real internet host — resolve + see what happens:
nc -l 7001 &   ./client ::1 7001 "ipv6 works too"

Print p->ai_family inside the loop and see which families come back for localhost on your machine — that's the list, live.
