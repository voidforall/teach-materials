TCP 到底承诺了什么

一条字节流：有序、不损坏、尽力最终送达 —— 仅此而已。没有时序、没有边界、没有送达期限。你的协议必须恰好围绕这些承诺来设计。

第 1 课给了你机制。这一课讲合同 —— 因为一半的 socket bug，都是因为代码以为 TCP 承诺了它没承诺过的东西。

承诺清单

  • 字节，不是消息。TCP 是一条双向流。它从不记录"这次 write 到此为止"。
  • 有序。字节按写入顺序到达。网络上重排随时发生（IP 对每个包独立路由）；TCP 负责重组。
  • 完整性。每个段都有校验和；损坏的段会被丢弃（并重传）。
  • 尽力而为的最终可靠。丢失的段会重传 —— 前提是连接还活着。如果对端或路径长时间失效，TCP 会放弃并报错。"可靠"不等于"保证送达"，只等于"失败时它会告诉你"。
关键认知 TCP 承诺的是字节流的有序与完整 —— 从不承诺时序、边界或送达期限。你在其上构建的任何协议都必须自己补上消息分帧（第 4 课）和自己的"对端还活着吗"判断（应用层超时/心跳）。

三个会咬到每个初学者的生命周期事实：

  • read() 返回 0 就是 EOF。它表示对端调用了 close()（或 shutdown()）。零是信号，不是错误，也不是"暂时没数据"。
  • 关闭分两个方向。close() 双向全断。shutdown(fd, SHUT_WR) 只关你的发送侧 —— 即"半关闭"：话说完了，但耳朵还开着。HTTP/1.0 和许多请求-响应协议正是这样结束请求的。
  • TIME_WAIT 属于先关闭的一方。它的存在让迟到的重传包不至于污染同端口对的未来连接。这就是被杀掉的服务端有时一分钟内无法重新 bind 的原因 —— 解药是 SO_REUSEADDR（第 9 课），而不是干等。

两军问题（为什么"保证送达"不可能）

两座山上的两支军队约好同时进攻，但信使可能被俘；无论确认链怎么加长都无法确知 —— 最后一次回执永远可能丢失。TCP 同构：最后的 FIN-ACK 也可能丢，所以干净的断开在根本上无法保证。真实系统接受这一点，在要紧处加上应用层确认。维基百科有经典论述。

回忆检索

read() 返回了 0。发生了什么？是错误吗？

对端关闭。非错误。

EOF 处的零字节是 TCP 设计好的信号：对端发了 FIN。把它当作"永无更多输入"处理，关掉你这侧、释放连接。真正的故障表现为 −1 加 errno。

客户端分两次 write 了 "A" 和 "B"。服务端会读到什么？

"AB"，或分开。

Nagle 可能把两次 write 合并成一个段（服务端一次读到 "AB"）；也可能网络分/重排让它们分开到达；也可能一次 read 只拿到 "A" 而 "B" 还在内核队列里。全部合法 —— 流没有边界。

拔掉对端的网线，你的 write() 什么时候失败？

不会立刻失败。

write() 只是把数据拷进本地内核发送缓冲 —— 远在送达之前就返回成功。重传会持续挣扎好几分钟（tcp_retries2），然后连接被复位。想快速发现死对端，要靠应用层超时或 keepalive，绝不能指望 write 报错。

TIME_WAIT 为什么存在？落在谁头上？

防止端口混淆。

主动关闭方逗留 2·MSL，使旧连接的迟到报文不会被误认成同一四元组上新连接的数据。服务端重启后 bind 不上，多半撞上了 TIME_WAIT 残留 —— 所以有 SO_REUSEADDR。

亲手验证

动手 —— 观察状态机，10 分钟 
# 终端 1：只收不发、永远读的服务端
nc -l 7000
# 终端 2：客户端，之后按 Ctrl-D（EOF）或 Ctrl-C
nc localhost 7000
# 终端 3：观察状态的诞生与消亡
watch -n1 'ss -tan | grep 7000'   # macOS: while true; do lsof -i :7000; sleep 1; done

然后在终端 2 输入 hello 回车，按 Ctrl-D（发送 EOF = 你的写侧半关闭），观察：客户端 socket 显示半关闭状态，而服务端仍能发数据。在终端 1 输入文字，看它到达一个已经"结束"的客户端 —— 半关闭，肉眼可见。

在 Linux（或容器）上，用第 1 课的服务端替换 nc，在连接中途杀掉它、重启它，亲自会见 EADDRINUSE —— TIME_WAIT 的一课落到实处。
