Debugging & Capstone

A socket bug is a claim about the system. Three tools let you check the claim at three layers: what your code asked for, what the kernel did, and what went on the wire.

The whole course in one sentence: your code talks to kernel queues; the kernel talks packets onto the wire. Debugging is just checking each layer in turn.

The three-lens method

  • What your code did — strace. strace -e trace=network -p PID shows every socket syscall, arguments, and errno. "We never called accept" and "read returns ECONNRESET, not 0" are both ten-second answers here.
  • What the kernel holds — ss / lsof. ss -tino: every connection's state, queues (Recv-Q/Send-Q — bytes waiting!), options, timers. "The data is stuck in Send-Q" means the peer isn't reading — Lesson 8's output buffer scenario, diagnosed from outside.
  • What actually shipped — tcpdump. tcpdump -i any -nn port 5000: SYNs, retransmissions (dup ACKs), RSTs, FINs, payload. The ground truth. When strace and ss disagree with reality, the wire settles it.
Keystone Diagnose top-down: symptom → ss (kernel state) → strace (your calls) → tcpdump (the wire). Most socket bugs are located, not guessed: a stuck Recv-Q indicts the reader; a retransmit storm indicts the path or the peer; an ECONNRESET on write indicts a closed peer you ignored. Read evidence before reading code.

The capstone: one server, everything earned

Build it from scratch, from memory, no lesson files open. Specification:

  • TCP server on an address from getaddrinfo (AI_PASSIVE), SO_REUSEADDR set before bind (Lessons 3, 9).
  • Single-threaded epoll loop, non-blocking fds (Lessons 6, 8).
  • Length-prefixed framing with a validated maximum (Lesson 4); per-connection input and output buffers (Lesson 8).
  • Behavior: echo each frame back reversed — a real round-trip you can verify by eye.
  • Graceful close: read()==0 → free the connection; write EAGAIN → EPOLLOUT queue (Lessons 2, 8).
  • Correct fd accounting under 100 simultaneous clients, three of which never read (Lesson 5's lesson, event-loop edition).

Acceptance test: 100 clients via a small Python asyncio script; slow readers connected and idle; all well-behaved clients still get correct reversed frames; ss -tn shows bounded queues; strace shows no busy accept loop. When that passes, you have written — with your own hands — the architecture inside Redis and nginx's core.

Retrieve it

Client says server "hangs". ss shows Recv-Q growing on the connection. Who's at fault?

The client, reading nothing.

Recv-Q is data the kernel holds for that connection's user — it arrived; nobody read it. The server's writes may also be blocked downstream by Send-Q backpressure. A growing queue indicts the reader, always.

tcpdump shows the same data segment sent 5 times. What's that?

Retransmit, missing ACK.

Duplicate segments mean the ACK never came back — packet loss, a broken return path, or a peer that received but stopped ACKing (hung app with full buffers). The count and spacing (backoff) tell you which story.

Which tool answers "did my code ever call connect() with the right port"?

strace, arguments shown.

strace prints each syscall's arguments and return: connect(3, {sa_family=AF_INET, sin_port=htons(5000)...}) — visible, checkable, with errno on failure. ss/tcpdump see consequences; strace sees intent.

Your capstone drops bytes when a client is slow. What did you forget?

The output buffer.

Partial writes leave unsent bytes that must live somewhere and retry on EPOLLOUT. Without that buffer, the leftover frame data is simply lost on the next loop iteration — the exact bug Lesson 8's graduation step exists to prevent.
