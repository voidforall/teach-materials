Framing & Short Reads

TCP gives you a pipe, not a mailbox. If your server does one read per request, it is already broken — it just hasn't met the packet split yet.

This is the lesson that turns "I can open a connection" into "I can write a correct protocol." Two facts from Lesson 2 now demand payment:

  • Short reads are legal. read() may return fewer bytes than you asked for — whatever arrived so far is yours.
  • No boundaries. Two write()s can merge into one read(), and one write can split across many reads.

Therefore: a protocol must define where each message ends — framing — and your code must buffer until a full frame is present. The three classic framings:

  • Delimiter: end on a marker byte (HTTP headers end at \r\n\r\n, Redis at \r\n, lines at \n). Simple; must escape the marker inside payloads.
  • Length-prefix: send uint32 len then that many bytes. Binary protocols' default (and our exercise). Must validate len — a corrupt or hostile length of 4 GB is a malloc bomb.
  • Fixed size: every message the same width. Trivial, rigid; fine for棋牌-style binary structs and sensor telemetry.
Keystone Never read "a message" — read "whatever came", append to a per-connection buffer, and extract whole frames when they've assembled. The loop is: fill buffer → scan for complete frame(s) → process → shift leftovers → repeat. A connection without a buffer is a protocol waiting to corrupt.

The shape of correct code

// read until buf holds at least need bytes; returns 0 on EOF, -1 on error
int read_full(int fd, void *dst, size_t need) {
    char *p = dst;
    while (need > 0) {
        ssize_t n = read(fd, p, need);
        if (n == 0) return 0;            // peer closed
        if (n < 0) { if (errno == EINTR) continue; return -1; }
        p += n; need -= n;               // partial read: keep looping
    }
    return 1;
}

// one framed message: [uint32 len (network order)][len bytes]
int recv_msg(int fd, char **out, uint32_t *len_out) {
    uint32_t net_len;
    if (read_full(fd, &net_len, 4) != 1) return -1;
    uint32_t len = ntohl(net_len);
    if (len == 0 || len > MAX_MSG) return -1;   // refuse absurd frames
    char *m = malloc(len);
    if (read_full(fd, m, len) != 1) { free(m); return -1; }
    *out = m; *len_out = len;
    return 0;
}

read_full is the atom; framing strategy is the molecule. In an event-driven server (Lesson 6) you don't block like this — you keep the per-connection buffer and re-check it every time the kernel says "readable" — but the frame-extraction logic is identical.

Retrieve it

Your protocol is "one line per request". Why does a single read() per request fail?

Lines arrive split.

A 200-byte line can arrive as 120 + 80 bytes; one read grabs 120, you process a torn "line", and the next 80 bytes poison the following request. You must accumulate until the \n actually appears in the buffer.

Why validate a length-prefix before malloc?

Hostile header kills.

The first 4 bytes are attacker-controlled until checked. Without a cap, a forged len = 0xFFFFFFFF turns your malloc into instant memory exhaustion. Check len ≤ MAX_MSG, then allocate.

Client write()s a 1 KB frame. Did one syscall send one segment?

Not necessarily one.

The kernel may split it across segments (MSS ~1400 bytes), Nagle may hold small writes to coalesce, and the peer's reads are independent of segment boundaries anyway. write() size tells you nothing about read() sizes — only invariants do.

Which framing does HTTP/1.1 use for its body, given Content-Length?

Length prefix.

Headers are delimiter-framed (blank line), but the body is length-prefixed by Content-Length — precisely so binary bodies can contain anything, including \r\n. Chunked mode turns into a stream of small length-prefixed pieces.

Prove it to yourself

Try it — catch a short read red-handed, 15 minutes 
# server: netcat just prints what arrives, in one process
nc -l 7002 > got.bin &
# client: one big write, split by the loopback? Force the issue:
python3 -c "
import socket
s = socket.create_connection(('localhost', 7002))
s.sendall(b'A' * 100000)     # one send, 100 KB
s.close()"
wc -c got.bin

All 100 KB arrives — the kernel reassembles for you. The split you must fear is on the read side: patch your Lesson-1 server to read(c, buf, 8) once per connection and send it a 20-byte message twice — watch the second half vanish into the void. Then fix it with recv_msg above and send framed messages with python3 or a small C client. Broken first, then correct: the lesson sticks.
