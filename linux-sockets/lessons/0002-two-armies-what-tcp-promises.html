What TCP Actually Promises

A byte stream, in order, not corrupted, eventually — and nothing else. No timing, no boundaries, no delivery deadline. Design your protocol around exactly these promises.

Lesson 1 gave you the mechanics. This lesson is the contract — because half of all socket bugs are code that assumes TCP promised something it didn't.

The promise list

  • Bytes, not messages. TCP is a bidirectional stream. It never records "this write ends here".
  • Order. Bytes arrive in the order written. Reordering happens constantly on the wire (IP routes each packet independently); TCP reassembles.
  • Integrity. A checksum covers every segment; corrupted segments are discarded (and retransmitted).
  • Eventual, best-effort reliability. Lost segments are retransmitted — if the connection survives. If the peer or the path dies for long enough, TCP gives up and errors out. "Reliable" does not mean "guaranteed", only "it will tell you when it failed".
Keystone TCP promises ordering and integrity of a byte stream — never timing, never boundaries, never a delivery deadline. Every protocol you build on top must add its own message framing (Lesson 4) and its own notion of "is the peer alive" (application-level timeouts / heartbeats).

Connection lifecycle: handshake → data → teardown

When you watch a connection in tcpdump, you see the state machine:

Three lifecycle facts that bite every beginner:

  • read() returning 0 is EOF. It means the peer called close() (or shutdown()). Zero is the signal, not an error, and not "nothing yet".
  • Closing has two directions. close() kills both. shutdown(fd, SHUT_WR) closes only your sending side — a "half-close": you've said your last word but can still listen. HTTP/1.0 and many request-response protocols end requests exactly this way.
  • TIME_WAIT belongs to whoever closes first. It exists so stray retransmits can't poison a future connection on the same ports. It's why a killed server sometimes can't rebind for a minute — the fix is SO_REUSEADDR (Lesson 9), not waiting.

The two-armies problem (why "guaranteed" is impossible)

Two armies on two hills must attack at the same time, but messengers can be captured; no amount of acknowledgment chaining creates certainty — the last ack might be lost, forever. TCP has the same shape: the final FIN-ACK can be lost, so clean disconnect is fundamentally unguaranteeable. Real systems accept this and add application-level confirmations when it matters. Wikipedia has the classic write-up.

Retrieve it

Your read() returned 0. What happened, and is it an error?

Peer closed. Not error.

Zero bytes at EOF is TCP's designed signal that the peer sent a FIN. Treat it as "no more input ever", close your side, free the connection. A real failure shows up as −1 with errno.

Client writes "A" then "B" in separate write() calls. What can the server read?

"AB", or split.

Nagle may coalesce the two writes into one segment (server reads "AB" at once); or network reordering/segmentation delivers them apart ("A", then "B"); or one read grabs "A" while "B" still sits in the kernel queue. All legal — the stream has no boundaries.

You unplug the peer's cable. When does your write() fail?

Not immediately.

write() only copies into the local kernel send buffer — it returns success long before delivery. Retransmissions grind on for minutes (tcp_retries2), then the connection resets. To detect dead peers fast you need application timeouts or keepalives, never "rely on write failing".

Why does TIME_WAIT exist, and who gets it?

Prevents port confusion.

The active closer lingers (2·MSL) so that delayed segments from the old connection can't be mistaken for data on a new connection using the same four-tuple. Servers that restart and can't rebind are usually hitting TIME_WAIT's remnant — hence SO_REUSEADDR.

Prove it to yourself

Try it — watch the state machine, 10 minutes 
# terminal 1: a server that reads forever, never writes
nc -l 7000
# terminal 2: client, then press Ctrl-D (EOF) or Ctrl-C
nc localhost 7000
# terminal 3: watch states appear and age out
watch -n1 'ss -tan | grep 7000'   # macOS: while true; do lsof -i :7000; sleep 1; done

Then in terminal 2, type hello + Enter, press Ctrl-D (sends EOF = half-close of your write side), and watch: the client socket shows the half-closed state while the server can still send back. Type text in terminal 1 and see it arrive at a client that already "ended". That is the half-close, visible.

On Linux (or a container), replace nc with your Lesson-1 server, kill it mid-connection, restart it, and meet EADDRINUSE personally — the TIME_WAIT lesson made flesh.
