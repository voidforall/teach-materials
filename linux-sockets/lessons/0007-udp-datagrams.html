UDP: Datagrams

TCP was a phone call; UDP is a postcard. You keep the message — you lose the delivery, the order, and the connection.

One flag changes the world: socket(AF_INET, SOCK_DGRAM, 0). No handshake, no listen/accept, no connection — you send self-contained datagrams to an address, and each carries its own return address. The API mirrors the model: sendto(fd, buf, len, 0, &dest, dstlen) and recvfrom(fd, buf, len, 0, &src, &srclen) — the sender's address arrives with every packet, because there is no "connection" to remember it.

What the postcard does and doesn't carry

  • Boundaries preserved. One sendto = one datagram = one recvfrom. No framing needed (Lesson 4 dissolves — mostly: a datagram larger than your read buffer is silently truncated).
  • No order. Datagram #2 can beat #1 across the network.
  • No delivery. Lost is lost; nobody retransmits, nobody is even told.
  • No congestion control. UDP never backs off — which is both its speed and its antisocial danger.
Keystone TCP exports complexity into the kernel; UDP exports it into your application. If you need ordering or reliability on UDP, you build retransmission, sequence numbers, and flow control — that's what QUIC, DNS-over-reliant-UDP designs, and game protocols are: bespoke reliability layers. Choose UDP when per-message value is low, latency beats completeness, or you multicast.

When UDP is the right answer

  • DNS — a query fits in one datagram; if it's lost, just ask again. Retrying a 60-byte question is cheaper than a handshake.
  • Games / live media** — a 200 ms-old position update is worthless; retransmitting it would poison the present. Lossy-realtime beats late-perfect.
  • Local discovery / logging — broadcast/multicast, fire-and-forget syslog, DHCP, mDNS. TCP literally cannot broadcast.
  • QUIC / HTTP/3 — the modern twist: user-space reliability on top of UDP, dodging middleboxes and TCP's ossified stacks.

Retrieve it

Two sendto() calls arrive. What does the second recvfrom() return?

Second whole datagram.

UDP preserves message boundaries: each recvfrom yields exactly one intact datagram, never a blend of two. But "second to be sent" may arrive first — order is the property you lost, not framing.

A datagram is bigger than your recvfrom buffer. What happens?

Truncated, silently.

The kernel copies what fits and discards the rest — no error, no retry flag (unless you set MSG_TRUNC, which Linux then reports). Buffers for UDP must be sized for the protocol's max datagram, or use recvmmsg-style big reads.

Why does UDP code often still call connect()?

Pins the peer.

UDP's connect sends nothing; it records the peer address so you can use plain send/recv, and the kernel then filters — datagrams from other sources are dropped instead of delivered. Also unlocks ICMP error delivery: an unreachable peer finally surfaces as ECONNREFUSED on the next send.

Your UDP flood saturates the link. What backs off?

Nothing at all.

TCP has congestion control (cwnd, backing off on loss); UDP has none and will happily crowd out everything including itself. That's why responsible UDP apps rate-limit themselves — and why ISPs throttle heavy UDP users.

Prove it to yourself

Try it — postcards in 10 minutes 
# terminal 1: a UDP sink that stamps each sender + payload
nc -ul 7003
# terminal 2: send two datagrams (each nc run = separate postcard)
printf 'first\n'  | nc -u -w1 localhost 7003
printf 'second\n' | nc -u -w1 localhost 7003

Now the loss experiment TCP made impossible: start a UDP listener in a container (docker run -it --rm -p 7004:7004/udp alpine sh, inside: nc -ul 7004), then from the host blast 10,000 tiny datagrams with a 3-line Python loop and count arrivals. Missing? Good — you just watched UDP drop traffic under load, the very property that makes it both fast and unreliable. Re-run the same count over TCP and compare.

Then write it in C — it's the Lesson-1 server, minus listen/accept, plus recvfrom/sendto with a sockaddr_storage out-param you echo back into.
