Non-blocking I/O

Blocking says "wake me when it's done." Non-blocking says "do what's possible now, tell me the rest later." EAGAIN is not an error — it's the whole vocabulary.

Flip a socket out of blocking mode and every syscall becomes a status probe: read returns data if any, -1/EAGAIN if none; write sends what fits, -1/EAGAIN if the send buffer is full. Nothing ever sleeps. Combine that with readiness notifications (Lesson 6) and you get an event loop where slow clients can't stall fast ones.

Setting it, and the two-sided discipline

// turn on O_NONBLOCK (both fcntl calls, not just the second — F_SETFL
// overwrites flags, so you must read-modify-write)
int fl = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, fl | O_NONBLOCK);

Then every read/write must be treated as partial:

  • Partial writes are normal. The kernel buffer fills when the peer reads slower than you write. Your write sends 300 of 1000 bytes; you keep the remaining 700 in the connection's output buffer, subscribe to EPOLLOUT, and flush when the kernel says there's room. That EPOLLOUT dance is the single most-skipped step in student event servers — without it you silently drop data.
  • EAGAIN means "later", not "never". Standard loop: try read → if EAGAIN, return to the event loop; the next EPOLLIN will call you again.
Keystone Non-blocking turns I/O from waiting into polling: syscalls answer "how much now", and readiness events answer "when to ask again". Each connection therefore owns two buffers — an input buffer (Lesson 4 framing) and an output buffer (pending bytes the kernel couldn't take yet). An event server is bookkeeping around those two buffers.

Level-triggered vs edge-triggered (epoll's sharp edge)

  • Level-triggered (default): "report ready while data remains." If you read once and leave bytes behind, next epoll_wait re-reports. Forgiving.
  • Edge-triggered (EPOLLET): "report only on each new arrival." You must drain in a loop until EAGAIN, or the un-drained remainder never triggers another event — and that connection hangs forever with data in queue. Faster (fewer wakeups), but demands the drain-until-EAGAIN discipline.

Rule of thumb: start level-triggered; adopt edge-triggering only when you've internalized "always read until EAGAIN, always keep an output buffer, always handle EPOLLOUT".

Retrieve it

write() returns 300 on a 1000-byte request. What do you do?

Queue 700, wait EPOLLOUT.

The send buffer filled — the peer isn't draining. Stash the rest in the connection's output buffer and subscribe for writability; on EPOLLOUT, flush more. Writing in a busy-loop wastes CPU; dropping bytes corrupts the protocol.

Why must the F_SETFL call read flags first?

F_SETFL overwrites.

F_SETFL replaces the flag word. Passing only O_NONBLOCK would silently clear anything else set on the fd. F_GETFL, OR it in, then set — a read-modify-write, like any shared register.

Edge-triggered epoll, you read once and leave bytes. Consequence?

Connection hangs forever.

ET only fires on transitions — no new arrival, no new event. Those stranded bytes sit in the kernel queue and never produce another EPOLLIN. Hence the law: with EPOLLET, read in a loop until read returns EAGAIN.

What does a blocking read() on a non-blocking fd never do?

Sleep waiting for data.

That's the entire definition: O_NONBLOCK converts "wait for readiness" into "return EAGAIN immediately". Waiting is delegated upward — to select/poll/epoll in your event loop.

Prove it to yourself

Try it — meet EAGAIN and EPOLLOUT, 20 minutes 
nc -l 7005 > /dev/null &          # a sink that never reads: the trap
python3 - <<'EOF'
import socket
s = socket.create_connection(('localhost', 7005))
s.setblocking(False)               # O_NONBLOCK
payload = b'X' * (50 * 1024 * 1024)   # 50 MB — far beyond any buffer
try:
    while payload:
        sent = s.send(payload)     # partial sends are now the norm
        payload = payload[sent:]
        print('sent', sent, 'left', len(payload))
except BlockingIOError:            # that's EAGAIN
    print('EAGAIN: kernel buffer full — peer must drain first')
EOF

You just watched the kernel say "I can't take more" — in a blocking socket this same loop would just sleep; here you get to decide policy. Now the kicker: kill the sink (kill %1) — the peer that never reads makes your output buffer the bottleneck. Patch your Lesson-6 epoll skeleton with an output buffer + EPOLLOUT flush and replay this scenario through it: slow-reader clients stop stalling the loop, and no bytes are lost. That patch is the graduation exercise of the whole course.
