select, poll, epoll

One thread, ten thousand clients, zero blocked syscalls. The trick isn't magic — it's asking the kernel one question: "which of these fds are ready right now?"

Lesson 5 bought concurrency with a process or thread per connection. At 10k mostly-idle connections (chat clients, proxies, IoT), that's 10k stacks and a scheduler thrash — the C10K problem. The alternative: demultiplex. Register interest in many fds; sleep until any of them is ready; handle just those.

The three APIs, one idea at increasing efficiency

APIYou pass itCost per callfd limit
selectthree fd_set bitmaps, rebuilt every callO(total fds) each way + full set copyFD_SETSIZE = 1024
pollarray of struct pollfdO(total fds) scan, no bitmap rebuildnone practical
epoll (Linux)a persistent kernel registration (epoll_ctl)O(ready fds) — kernel keeps the interest listnone practical

Read the trend: select/poll are stateless questions — you re-describe your whole fd set every call, and the kernel scans all of it. epoll is a standing subscription — the kernel remembers what you care about and wakes you with just the ready list. That one architectural difference is why nginx, Redis, and every modern high-concurrency server on Linux is built on epoll (macOS/BSD equivalents: kqueue; portable wrapper: libuv, libevent).

Keystone select/poll: you push the watch-list to the kernel every call. epoll: you set it up once, and the kernel pushes ready events to you. With 10k connections and 10 active, select scans 10k; epoll returns 10. Readiness-driven, never-blocking-per-fd, is the whole event-loop paradigm.

An epoll server's skeleton

int ep = epoll_create1(0);
struct epoll_event ev = { .events = EPOLLIN, .data.fd = s };
epoll_ctl(ep, EPOLL_CTL_ADD, s, &ev);          // subscribe: listener

struct epoll_event ready[64];
for (;;) {
    int n = epoll_wait(ep, ready, 64, -1);       // sleep until SOMETHING is ready
    for (int i = 0; i < n; i++) {
        if (ready[i].data.fd == s) {             // listener ready → new client
            int c = accept(s, NULL, NULL);
            set_nonblocking(c);                  // Lesson 8: essential here
            ev.events = EPOLLIN; ev.data.fd = c;
            epoll_ctl(ep, EPOLL_CTL_ADD, c, &ev);
        } else {                                 // client ready → read a chunk
            int c = ready[i].data.fd;
            ssize_t r = read(c, buf, sizeof buf);
            if (r <= 0) { epoll_ctl(ep, EPOLL_CTL_DEL, c, NULL); close(c); }
            else append_to_conn_buffer(c, buf, r);   // Lesson 4 framing applies
        }
    }
}

Notice what the loop never does: wait on one client. A slow client costs one iteration; ten thousand idle clients cost nothing until they speak. This loop is single-threaded — state lives in your connection structs, and Lesson 4's buffer-per-connection is now load-bearing, not optional.

Retrieve it

Why does select cap you at 1024 fds?

Fixed bitmap size.

fd_set is a fixed array of FD_SETSIZE bits, compiled into libc. Raising it is a recompile-and-pray hack; poll (dynamic arrays) and epoll (no per-call set at all) remove the ceiling entirely.

10k connections, 5 active. How many fds does each API examine per wakeup?

10k, 10k, 5.

select and poll must scan the full registered set on every call — active or not. epoll's ready list holds exactly the fds that became ready, so cost tracks activity, not population.

Where does the event loop's per-connection buffer live?

Userspace heap.

"Readable" only means "at least one byte arrived". One event may carry half a frame; a frame may span many events. You own reassembly in a per-connection heap buffer — the kernel queues bytes, never messages.

Why must client fds be non-blocking in an epoll server?

Readiness isn't permanence.

EPOLLIN promises data now; by the time you read, it may be gone (another thread drained it) — a blocking fd would then sleep the whole loop. Also writes: a full send buffer turns blocking write into an everyone-waits event. Details in Lesson 8.

Prove it to yourself

Try it — feel the O(n) vs O(active), 15 minutes (Linux/container) 
# a select-based server that prints how many fds it scans per loop
# (drop-in for your Lesson-1 server; strace shows the syscall churn)
cc -Wall srv_select.c -o srv_select && strace -e trace=select,accept4,read ./srv_select

Open 5 nc localhost 5000 sessions, send a byte in one, and watch the strace: every wakeup is preceded by a full select listing all fds. Now swap in the epoll skeleton and repeat — epoll_wait returns only the one active fd. Same behavior, wildly different work. If you're on macOS, run both under a Linux container: docker run -it --rm -v $PWD:/w -w /w alpine sh then apk add build-base strace.
