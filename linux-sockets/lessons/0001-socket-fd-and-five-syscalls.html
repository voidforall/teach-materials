A Socket Is a File Descriptor

Before the syscalls, the single idea that makes everything else click: a socket is just an open file the kernel owns — with a phone number attached.

Your mission is to write real network programs and understand the machine underneath. So we start with the theory in one sentence, then immediately write and run real code.

When you call socket(), the kernel allocates a communication endpoint and — like open() for files — hands you back a small integer: a file descriptor. You never touch the endpoint directly. Every later syscall (bind, listen, accept, connect, read, write, close) just names that integer. This is why sockets play with select/poll/epoll, why they're inheritable across fork(), and why "everything is a file" on Unix extends to the network.

Keystone A socket is a kernel object reached through an fd; the syscalls don't move data to the network — they ask the kernel to, and the kernel's queues do the rest. Client and server never share memory; the kernel holds one receive queue per socket. read() is just "drain my queue".

The five-syscall dance (TCP)

A TCP conversation takes two different fd's on the server side, and the sequence is where everyone gets lost. Watch the asymmetry:

Decode the asymmetry:

  • socket() creates the endpoint, but it has no address. bind() pins it to a local IP:port. The client usually skips bind — the kernel picks an ephemeral port at connect time.
  • listen() flips the socket from "active" to "listening": it will accept inbound connections. The kernel builds two queues: one for half-open handshakes (SYN received), one for finished handshakes waiting for your code.
  • accept() pops a completed connection off that queue and returns a brand-new fd for that one peer. The listening socket stays listening — it is a door, not a conversation.
  • connect() is the client's one move: it drives the TCP three-way handshake and returns when the connection is established.

One more theory bite, the one interviewers love: TCP gives you no message boundaries. It is a byte stream. One write() of 100 bytes can arrive as two read()s of 40 + 60 — or vice versa. This fact will dominate Lesson 4 (framing).

Retrieve it

Which call turns a fresh socket into one that can receive inbound TCP connections?

listen.

bind only assigns an address; the socket is still "active". listen marks it passive and allocates the accept queues. Both are needed before accept works.

A server handles one client at a time. How many fds are alive during the conversation?

Two.

The listening socket stays open (it keeps admitting new connections), plus the per-connection fd returned by accept. Confusing the two — closing the listener instead of the connection fd — is a classic first-server bug.

The client sends one 100-byte write. What does the server's single read return?

Not guaranteed 100.

TCP is a byte stream with no message boundaries. The kernel hands read whatever has arrived so far — could be 40 bytes now, 60 later. Only "at least 1, at most requested" is promised.

Why can the client skip bind() while the server cannot?

Nobody calls clients.

The peer needs a stable, known address to connect to — that's the server's job. The client's source port just needs to be unique, so the kernel auto-assigns an ephemeral one during connect.

Prove it to yourself

Try it — C, 15 minutes

Save as server.c — a complete TCP server in ~30 lines:

#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <arpa/inet.h>

int main(void) {
    int s = socket(AF_INET, SOCK_STREAM, 0);

    struct sockaddr_in addr = {0};
    addr.sin_family      = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);  // all interfaces
    addr.sin_port        = htons(5000);        // host → network byte order!
    bind(s, (struct sockaddr *)&addr, sizeof addr);
    listen(s, 8);

    puts("listening on :5000 ...");
    for (;;) {
        int c = accept(s, NULL, NULL);      // blocks until a client arrives
        char buf[256];
        ssize_t n = read(c, buf, sizeof buf - 1);
        buf[n > 0 ? n : 0] = 0;
        printf("got: %s", buf);
        write(c, buf, n);                   // echo it back
        close(c);                           // one conversation, then done
    }
}

Run it, then be the client with zero extra code:

cc -Wall server.c -o server && ./server
# in another terminal:
printf 'hello sockets\n' | nc localhost 5000

Then watch the theory become visible: run nc -l 9999 in one terminal and lsof -i :9999 (or ss -tlnp on Linux) in another — find the LISTEN entry. Connect a client, run it again, and find the ESTABLISHED pair. You are looking straight at the two-fd picture above.
