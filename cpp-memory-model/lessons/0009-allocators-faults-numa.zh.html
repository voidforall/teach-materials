分配器、缺页、THP 与 NUMA

new 预约的是地址空间而不是内存——内核只在首次写入时才交出物理页，而物理页放在哪、有多大才决定你真实的延迟。

内存不是分配时就有，而是触碰时才有

当你 new char[1<<30] 分配 1 GB 时，glibc 的 malloc 发现请求远超 M_MMAP_THRESHOLD（默认 128 KB），于是调用 mmap(NULL, 1<<30, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, ...)。内核的举动令人意外：它只是把一段虚拟地址映射到"保留且清零"的状态，微秒级返回。RSS 几乎不动。

物理内存是惰性出现的。对每个 4 KB 页的首次写入触发一次 minor page fault（次缺页）；缺页处理函数映射一个清零的物理页，即"按需清零分页"（demand-zero paging，见 man7 的 mmap(2) 以及 Ulrich Drepper《What Every Programmer Should Know About Memory》§4.1–4.3）。对未触碰的匿名页首次读取则映射共享零页（写时复制），纯读取几乎不占内存。

你早就感受过后果只是不知道原因：新分配的容器有"热身期"（第一遍被缺页卡住而非 CPU）、1 GB 缓冲的 memset 是 ~25 万次缺页加 DRAM 带宽、fork 出的服务进程写共享页会触发 COW 缺页。测量方式：

#include <sys/resource.h>
#include <cstdio>

long minflt() {
    struct rusage ru; getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;               // 次缺页 = 被按需清零的页数
}

int main() {
    constexpr size_t N = 1 << 30;      // 1 GiB
    char* p = new char[N];
    long before = minflt();
    for (size_t i = 0; i < N; i += 4096) p[i] = 1;   // 每页摸一个字节
    std::printf("faults=%ld (expect ~%zu)\n", minflt() - before, N / 4096);
}

或者从外部观测：perf stat -e page-faults,minor-faults ./a.out，用 pmap -x <pid> 或 top 看 RSS 一页一页地爬升。

NUMA：页住在首次写入它的地方

在双路机器上，每个 CPU 封装有各自的内存控制器和本地 DRAM。物理页归属哪个 NUMA 节点由首次触碰策略（默认策略，见 man7 的 numa(7)）决定：谁引发缺页，页就归谁的节点。如果 socket 0 上的线程 A 初始化一个大数组、socket 1 上的线程 B 来处理它，B 的每次访存都要跨互连（x86 的 UPI、ARM 服务器的一致性网格）——延迟约 1.5–2 倍，带宽只剩一部分。

这是多线程数值计算中最常被漏掉的性能 bug：代码是对的，布局是错的。用 numastat -p <pid> 诊断（看 numa_miss/numa_foreign 是否增长）或 perf c2c。修复方法：谁用谁初始化，或者显式绑核绑存：

numactl --cpunodebind=1 --membind=1 ./worker   # 全部放在节点 1
numactl --interleave=all ./worker              # 页轮询分布（带宽受限型）

macOS arm64 桌面是 UMA——单芯片统一内存——所以本节最好在 Linux 服务器或 CI 上做实验；但概念同样解释了 Apple Silicon 核心簇间的 L2 不对称。

透明大页：更少 TLB miss，偶发的尾延迟

TLB 表项有限；用 4 KB 页时 1 GB 工作集要 ~26 万个表项。一个 2 MB 大页用一个 TLB 项覆盖 512 个小页——对数组扫描类负载（哈希表、GC 堆、稠密矩阵）可把 TLB miss 减少一个数量级，遍历提速 10–30%（Drepper §6.2.2 有精确测量）。

THP 有 always、madvise、never 三档（/sys/kernel/mm/transparent_hugepage/enabled）。always 的问题：内核的 khugepaged 线程激进地合并、整理内存，一个每 2 MB 只写 4 KB 的程序会发现 RSS 被向上取整 ~512 倍，而内存整理会把线程卡住几毫秒——这就是经典的数据库运维事故（MongoDB、Redis、PostgreSQL 的官方文档都建议改成 madvise）。生产环境的调优答案是：

echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
// 再在程序里对真正需要的热点区域：
madvise(buf, len, MADV_HUGEPAGE);   // 该区间显式启用 THP

验证：查 /proc/<pid>/smaps，看每个区域是否出现 AnonHugePages: 2048 kB。macOS 没有用户可见的 THP 开关；改用 vmmap <pid> 观察 16 KB 基础页和各区域大小。

分配器版图

glibc malloc（ptmalloc2 血统）：小分配来自每线程arena（64 位下最多 8×核数），线程之间几乎不抢锁；每个线程还有 tcache——一个无锁的每线程空闲链表缓存，优先于一切被检查。尺寸分桶：≤~160 B 走 tcache/fastbin（单链表 push，无锁），到 1 KB 走 smallbin，更大走 unsorted/largebin。大请求（默认 ≥128 KB）直接 mmap，free() 即 munmap——内存立刻还给操作系统。而 arena 的堆块只有顶部连续空闲时才归还（M_TRIM_THRESHOLD），所以长期运行的服务的 RSS 通常是历史高水位而非当前用量。调优：mallopt()、环境变量 MALLOC_ARENA_MAX（JVM 侧运维常设 2–4，以争用换抗碎片）。

tcmalloc（Google）：每个线程有线程缓存，按 size class 组织空闲链表——快路径上的 malloc/free 只是几条指令、零原子操作；缓存空了/满了就批量向 central cache 补货/退货，后者通过 pagemap 元数据管理 page-heap 的 span。内存经 ReleaseFreeMemory() / 后台释放线程延迟归还。文档见 google/tcmalloc design.md。

jemalloc：按 size class 从 per-CPU/arena 的 extent 里分配，并有显式的衰减式清理——脏页按指数衰减计划归还操作系统（dirty_decay_ms / muzzy_decay_ms），三者中 RSS 曲线最温和，代价是更多 madvise 流量。

自定义 arena 与 slab在分配形态已知时获胜：游戏用帧 arena（bump 指针分配，帧末整体丢弃——零碎片、零单对象开销）；HFT 与嵌入式用定长对象 slab，把 malloc 彻底赶出热路径并让碎片不可能存在。第 8 课的 cache-line 思维同样适用：能从快路径上删掉分配器，就删。

负载选理由
通用服务、混合大小glibc 默认或 jemalloc若痛点是 RSS 膨胀/碎片则 jemalloc
海量短命小对象、线程多tcmalloc / mimalloc线程缓存消灭锁争用
长期稳定服务、RSS 涨jemalloc 或限制 arena 数衰减清理、arena 有界
帧式（游戏、仿真）arena / bump 分配器free 就是指针算术
定长对象（HFT、嵌入式）slab / 空闲链表池确定性、热身后无锁
大数组、顺序访问mmap + MADV_HUGEPAGETLB 覆盖、缺页节奏自己掌控
Keystone分配是承诺，首次触碰才是行动。new 只是预订虚拟地址空间；首次写入触发的缺页才真正决定物理内存、NUMA 归属与页大小——所以初始化循环就是放置策略，而分配器的选择是页何时归还的策略。
Anti-pattern一个线程初始化、另一个线程计算。所有页都落在初始化线程的 socket 上，计算循环的每次 cache miss 都要付跨节点延迟。同理：延迟敏感服务把 THP 设为 always——RSS 膨胀且 khugepaged 带来毫秒级停顿。

检索它

为什么 new char[1<<30] 之后 RSS 几乎为零？

匿名 mmap 只保留虚拟地址空间，物理页在首次触碰缺页时才挂上。

按需清零分页：写一页触发一次 minor fault，内核映射一个清零物理帧；只读触碰可能映射共享零页（COW）。

Linux 默认策略下，哪个 NUMA 节点拥有一页由什么决定？

首次写入该页的线程所在 CPU 的节点（first-touch）。

本地分配策略让缺页节点出内存，所以初始化即放置——用 numactl --cpunodebind --membind，或者在哪算就在哪初始化。

说出透明大页的一个收益和一个代价。

收益：每表项 512 倍 TLB 覆盖；代价：RSS 向上取整膨胀与 khugepaged 整理停顿。

所以生产上的调优是 madvise 档 + 对热点区域显式 madvise(MADV_HUGEPAGE)，而非全局 always。

亲手验证

试一试 — 20 分钟

在 Linux（或 VM/容器）上：

// faultdemo.cpp — clang++ -std=c++20 -O2 faultdemo.cpp
#include <sys/mman.h>
#include <sys/resource.h>
#include <chrono>
#include <cstdio>
#include <vector>

long minflts() { struct rusage ru; getrusage(RUSAGE_SELF, &ru); return ru.ru_minflt; }

int main(int argc, char**) {
    constexpr size_t GB = 1 << 30;
    bool huge = argc > 1;                       // argv[1] => MADV_HUGEPAGE
    std::vector<char*> bufs;
    char* p = (char*)mmap(nullptr, GB, PROT_READ|PROT_WRITE,
                          MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    if (huge) madvise(p, GB, MADV_HUGEPAGE);
    auto t0 = std::chrono::steady_clock::now();
    long f0 = minflts();
    for (size_t i = 0; i < GB; i += 4096) p[i] = 1;   // "触碰每一页"
    auto t1 = std::chrono::steady_clock::now();
    std::printf("faults=%ld  time=%.1f ms (huge=%d)\n",
        minflts() - f0,
        std::chrono::duration<double, std::milli>(t1 - t0).count(), huge);
}

先 ./a.out 再 ./a.out huge：预期 ~26.2 万次缺页、每页 10–25 ns；THP 以 2 MB 页 backing 后预期 ~512 次缺页（循环仍触碰 26 万个地址，但只有 512 个页成真）且耗时明显下降。用 perf stat -e page-faults,minor-faults,dTLB-load-misses ./a.out 交叉验证，并 cat /proc/$(pgrep a.out)/smaps | grep AnonHuge。macOS arm64：THP 部分不适用，但缺页计数有效——用 vmmap <pid> 观察匿名 MALLOC_LARGE 区域的增长。
