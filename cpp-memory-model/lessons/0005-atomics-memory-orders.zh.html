std::atomic 与内存序

std::atomic 给你不可分割性（不撕裂）并参与 happens-before；六种内存序（memory order）是调节"每次操作买多少排序"的旋钮。

两个保证，一个模板

std::atomic<T> 承诺普通 T 给不了的两件事：不可分割性（indivisibility，不撕裂）——读到的必然是某次真实写入的值，绝不是写了一半的混合体——以及参与跨线程机制：每次访问携带一个内存序，可能创建 synchronizes-with 边。六种内存序（memory_order）：

  • memory_order_seq_cst——默认；所有线程的全部 seq_cst 操作对同一个全序 S 达成一致。
  • memory_order_acquire——用于 load：后面的不能重排到它前面。
  • memory_order_release——用于 store：前面的不能重排到它后面。
  • memory_order_acq_rel——用于读-改-写：acquire + release 二合一。
  • memory_order_relaxed——只保证原子性，不排序周边内存。
  • memory_order_consume——数据依赖排序；所有实现都把它当 acquire，标准也不鼓励。跳过它。

RMW：fetch_add 与 compare_exchange

读-改-写（read-modify-write）操作是唯一"读+写作为一步原子完成"的操作——这正是 ++counter 丢一百万次更新与一次不丢的区别。

std::atomic<int> c{0};
c.fetch_add(1, std::memory_order_relaxed);   // 原子自增

// CAS 循环惯用法：weak 可能伪失败（spurious failure），所以要循环
int expected = head.load(std::memory_order_relaxed);
while (!head.compare_exchange_weak(expected, node->next,
                                    std::memory_order_acq_rel)) {}

compare_exchange_weak 允许在值并未不同时失败（伪失败——想想 ARM 上的 LL/SC）；strong 不允许。循环里 weak 可能更便宜，所以口诀是循环用 weak，单发用 strong。

哪些序用在哪里是合法的？

  • load()：seq_cst、acquire、relaxed（consume）。绝不能 release——load 无所 release。
  • store()：seq_cst、release、relaxed。绝不能 acquire。
  • RMW（fetch_add、exchange、CAS）：seq_cst、acq_rel、acquire、release、relaxed。

atomic<T> 什么时候偷偷变成锁

is_lock_free() 在运行时告诉你；is_always_lock_free 是编译期常量。在主流 ABI 上不超过 8 字节都免锁；32 位平台上的 atomic<double>、或拷贝非平凡的 16 字节结构体，可能退化为每个对象一把隐藏 mutex——伴随信号处理器里死锁与 false sharing 的一切麻烦。先检查再假设；对批量数据，C++20 的 atomic_ref 往往是更好的形态。

即使免锁也有一个躲不开的坑：ABA 问题——即使指针 P 在你 load 与 store 之间被释放又重新分配回同一地址，CAS 也会成功。原子性看不见历史；第 10 课处理它。

各编译成什么指令

来自 Compiler Explorer（clang，-O2），同一份源码在两种 ISA 上：

// x86-64                                    // ARM64
x.store(1, seq_cst);   mov 1, eax            stlr wzr, [x0]
                       xchg [x], eax         //（stlr = store-release，
                       //（xchg 隐含 lock 前缀）    与 ldar 配对即 seq_cst）
x.store(1, release);   mov [x], eax          stlr w1, [x0]
r = x.load(acquire);   mov eax, [x]          ldar w0, [x0]
r = x.load(relaxed);   mov eax, [x]          ldr  w0, [x0]

x86-64 是全存储排序（TSO）：每条 store 天然带 release、每条 load 天然带 acquire，所以 acquire/release 免费；只有 seq_cst store 要付钱（xchg 或 mov+mfence，约 20-40 周期）。ARM64 是弱排序：ldar/stlr 携带排序，relaxed 操作就是普通 ldr/str。这正是 Herb Sutter 的 atomic<> Weapons 演讲花一个小时讲"你要的与你付的之间的差别"的原因：一次 seq_cst 原子自增在 x86-64 上是 lock xadd，在 ARM64 上是 ldaxr/stlxr 循环——比非原子 ++ 编译出的普通 add 贵一个数量级。在目标 ISA 上测量，别信传说。

Keystone原子性与排序是分开购买的两样东西。每种序都给你不撕裂；只有 acquire/release/acq_rel/seq_cst 给你 happens-before 边。relaxed 只是"仅仅不可分割"。
Anti-pattern以为 atomic<MyStruct> 能编译就一定免锁。超过平台免锁宽度你会得到一把隐藏 mutex：操作会阻塞、不能进信号处理器、可能死锁。查 is_always_lock_free。

回忆检索

compare_exchange_weak 会伪失败，为什么还要有它？

因为在 LL/SC 架构上 strong CAS 本身就是 weak CAS 套循环，所以你反正要写的循环直接用 weak，还省了代码。

必须一次成功、不能伪失败的 CAS 用 strong；循环惯用法顺带免费吸收了伪失败。

为什么 load() 不允许 release 序？

release 是把更早的访问与一次将被发布的写排序；load 不发布任何东西，语义为空。

类型系统编码了这一点：load() 只接受对读有意义的序（seq_cst、acquire、relaxed）。

在 x86-64 上，relaxed load 与 seq_cst store 哪个贵得多？

seq_cst store——必须排空 store buffer（xchg 或 mfence）；relaxed load 就是普通 mov。

x86-64 的 TSO 已让 acquire load 与 release store 免费；只有跨线程全序才要付钱。

亲手验证

Try it — 10 分钟

粘贴到 godbolt.org（clang，-O2）：

#include <atomic>
std::atomic<int> x;
void sc_store()  { x.store(1, std::memory_order_seq_cst); }
void rel_store() { x.store(1, std::memory_order_release); }
int  acq_load()  { return x.load(std::memory_order_acquire); }
int  rx_load()   { return x.load(std::memory_order_relaxed); }

在 x86_64 与 aarch64 之间切换目标并对比：数一数 x86-64 上 sc_store 的 xchg/mfence，以及 aarch64 上 ldar/stlr 与 ldr 的区别。然后把 x 改成普通 int，看一切塌缩成单条 mov/add。
