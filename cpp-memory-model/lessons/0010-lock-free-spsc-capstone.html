Capstone: A Lock-Free SPSC Ring Buffer

Everything in the course — ordering, ownership of atomics, false sharing — compresses into forty correct lines: a single-producer/single-consumer ring buffer where relaxed, acquire, and release each do exactly one job.

Why SPSC is the perfect capstone

One producer thread, one consumer thread, one bounded buffer. That constraint lets each index have exactly one writer, and single-writer atomics are where the memory model becomes elegant: the owner of an index can use relaxed stores for its own updates (nobody needs to be ordered against them yet), while the reader of the other side's index needs acquire/release so the slot contents become visible before/after the index moves. No CAS, no retry loops — every operation completes in a bounded number of steps, which makes this structure wait-free, not merely lock-free.

The implementation, annotated

#include <atomic>
#include <cstddef>
#include <array>
#include <optional>

// Cache-line padding (Lesson 8): head and tail must not share a line,
// or producer and consumer ping-pong that line between caches.
struct alignas(64) PaddedAtomic {                 // 64 on x86; use 128 on
    std::atomic<size_t> v{0};                     // Apple arm64 (fetchadd
    PaddedAtomic() = default;                     // collision domain)
    PaddedAtomic(const PaddedAtomic& o) : v(o.v.load()) {}
};

template <typename T, size_t Cap>                 // Cap MUST be a power of two
class SpscRing {
    static_assert((Cap & (Cap - 1)) == 0);
    std::array<T, Cap> buf_{};
    PaddedAtomic head_{};   // consumer-side position (next to read)
    PaddedAtomic tail_{};   // producer-side position (next to write)
    char pad_[64 - sizeof(PaddedAtomic) % 64];     // keep data off the lines too

    static size_t idx(size_t v) { return v & (Cap - 1); }   // cheap modulo

public:
    bool push(const T& t) {
        size_t tail = tail_.v.load(std::memory_order_relaxed); // I own tail
        size_t head = head_.v.load(std::memory_order_acquire); // see consumer's frees
        if (tail - head == Cap) return false;      // full
        buf_[idx(tail)] = t;                       // write the slot...
        tail_.v.store(tail + 1, std::memory_order_release);   // ...then publish
        return true;                               // release pairs with the
    }                                              // consumer's acquire load
    std::optional<T> pop() {
        size_t head = head_.v.load(std::memory_order_relaxed); // I own head
        size_t tail = tail_.v.load(std::memory_order_acquire); // see producer's data
        if (head == tail) return std::nullopt;     // empty
        T t = buf_[idx(head)];                     // read the slot...
        head_.v.store(head + 1, std::memory_order_release);   // ...then free it
        return t;                                  // release pairs with the
    }                                              // producer's acquire load
};

Read the annotations as three rules from earlier lessons: (1) your own index is relaxed — only you write it, and your own reads of it are ordered by sequenced-before; (2) the other side's index is acquire — the load must synchronize with the release store so the slot payload written before the store is visible after the load (Lesson 3's publish pattern); (3) your index update is release — so the other side, acquire-loading it, also sees what you did to the slot. Indices grow monotonically and are masked into the array, so the capacity check tail - head == Cap works across wraparound in unsigned arithmetic.

Why alignas(64)? Without it, head and tail typically land on one cache line; the producer stores to tail and the consumer stores to head, and that line ping-pongs between their private caches on every operation (Lesson 8's false sharing) — measured cost is typically 2–5× on contended pipelines. Portable spelling: alignas(std::hardware_destructive_interference_size), with the literal 64/128 as the fallback because GCC's libstdc++ historically gated the constant behind <new> availability flags.

Why this doesn't generalize naively

MPMC breaks wait-freedom. With multiple producers, "read tail, check, write slot, bump tail" is no longer single-writer: two producers can read the same tail, and the only general fix is a CAS loop (compare_exchange_weak until you win), which retries under contention — lock-free but not wait-free, and each failed CAS is wasted cross-core traffic. Real MPMC queues (Vyukov, Fol ly) shard into per-producer cells to claw back the single-writer property.

ABA, and why we dodged it. A CAS algorithm that reads value A, does work, and CASes "only if still A" is fooled if the value went A→B→A in between — a classic pop-two-nodes-off-a-freelist hazard. Our ring never compares indices at all: each side owns its index outright and the other side only ever reads it. Monotonic counters that wrap only through the full unsigned range (264 operations) make "same number, different epoch" impossible in practice. The lesson: CAS-with-equality-check invites ABA; ownership transfer with counters sidesteps it.

Modern touches. C++20 std::atomic_ref<T> lets you apply this discipline to non-atomic storage (e.g., the slot array views) — same ordering rules, lifetime rules apply (the referred object must outlive all atomic_refs). C++20 std::atomic::wait()/notify_one()/notify_all() (futex-backed on Linux, os_sync_wait_on_address-class primitives on Darwin) gives you the blocking variant of this queue without condition variables: a producer that finds the queue full can wait() on tail instead of spinning or returning false.

Verify and benchmark

Correctness first: a harness that pushes/pops millions of items across two threads, summing checksums, must run clean under -fsanitize=thread (TSAN understands acquire/release — it models the happens-before edges we built). Then throughput. Typical numbers on a modern x86-64 laptop, ping-pong two threads over shared L3, single slot at a time:

QueueRound-tripNotes
std::mutex + deque~90–150 ns/opcontended lock/unlock, allocator noise
SPSC ring, padded~20–40 ns/optwo atomics + one acquire-load pair
SPSC ring, unpadded~60–150 ns/opfalse sharing dominates
SPSC ring, batched by 64~5–10 ns/itemamortizes the cross-core signal

The right comparison is your own machine's; the ratio (mutex ≈ 3–5× the padded ring) is the portable result. Reproduce on godbolt if you lack a Linux box.

KeystoneSingle writer ⇒ relaxed for self, release to publish, acquire to observe. The whole six-order table collapses to three verbs once each piece of state has one owner — that ownership, not cleverness, is what makes the ring wait-free.
Anti-patternGoing lock-free because it sounds faster. A mutex queue is correct, debuggable, and within 3–5× of optimal; a botched lock-free queue is a heisenbug factory. Use mutexes until a profiler shows lock contention is your bottleneck and you can afford the verification cost (TSAN, litmus tests, review by someone who can explain every memory order in the diff).

Retrieve it

Why can the producer's load of its own tail_ be relaxed?

Only the producer writes tail_, and its own reads are ordered by sequenced-before.

Relaxed still guarantees atomicity and single total modification order; ordering with other threads is only needed at the acquire/release boundaries, which is where the payload visibility is decided.

Why is the SPSC ring wait-free while a CAS-loop MPMC queue is not?

Each SPSC operation is a fixed sequence of loads/stores; CAS loops can retry unboundedly under contention.

Wait-free means every thread finishes in bounded steps regardless of others. Single ownership of each index removes the need to compare-and-retry at all.

How do monotonic indices sidestep ABA here?

Nothing ever compares indices for equality; ownership transfer means "same value" cannot mean "different epoch".

ABA needs a compare that can succeed on a recycled old value. The ring's indices only increase (wrapping once per 2⁶⁴ ops), and each side exclusively writes its own.

Prove it to yourself

Try it — 40 minutes

Type the ring in verbatim (typing, not pasting, is the point). Then:

// bench.cpp — pair of threads, ping-pong N items
// clang++ -std=c++20 -O2 -pthread bench.cpp && ./a.out
// clang++ -std=c++20 -O2 -g -fsanitize=thread bench.cpp && ./a.out   # TSAN must be clean

SpscRing<uint64_t, 1024> q;
constexpr uint64_t N = 1'000'000;

void producer() {
    for (uint64_t i = 0; i < N; ) {
        uint64_t h = 0, t = q.tail_debug();
        if (q.push(i)) ++i;                    // spin-retry on full is fine
        else std::this_thread::yield();
    }
}
void consumer() {
    uint64_t expect = 0, sum = 0;
    while (expect < N) {
        if (auto v = q.pop()) { sum += *v; ++expect; }
    }
    assert(sum == N*(N-1)/2);                  // the correctness oracle
}

Expected: clean TSAN run; time the producer-consumer pair and print ns/op — expect tens of ns on the padded ring vs. ~100+ ns for a std::mutex+std::deque version you write in ten lines. Then the sabotage: change the producer's tail store from memory_order_release to memory_order_relaxed. On x86-64 stores are release anyway, so it may keep passing — that's your machine being forgiving, not the code being right. Run the TSAN build (TSAN models the abstract machine and will flag the missing release), or compile the same code as ARM64 via godbolt/qemu, or add a payload that's wider than one store so store tearing/reordering becomes observable with enough iterations. Observe, revert, re-run clean.
