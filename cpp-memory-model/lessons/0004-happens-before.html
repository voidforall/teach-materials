The Abstract Machine: Happens-Before

C++11 didn't add "some atomics" — it defined a formal abstract machine, and every legal program is the set of executions the machine permits; everything else, including races, is undefined behavior.

One machine, three relations

The standard (see eel.is [intro.races] and the cppreference memory model page) defines concurrency in terms of relations between evaluations:

  • sequenced-before — the ordering you already know within one thread: a; is sequenced before b; that follows it. Single-threaded, unchanged since C.
  • synchronizes-with — the inter-thread edge: when thread A releases a mutex and thread B acquires it, everything A did before unlocking synchronizes-with everything B does after locking. Release/acquire atomics create the same edge (Lesson 6).
  • happens-before — the transitive closure of both: if A is sequenced before B, and B synchronizes with C, and C is sequenced before D, then A happens-before D, even across three threads that never touch each other directly.

Crucially, these are semantic relations, not hardware ones. The compiler and CPU may reorder anything as long as the single total order of each thread's sequenced-before edges is preserved (the as-if rule) — for a single-threaded program that's the whole story, which is why single-threaded reasoning you already trust is just the degenerate case of this model.

Annotated: mutex unlock → lock

std::mutex m;
int payload = 0;                       // plain, non-atomic

// Thread A
payload = 42;                          // (1) sequenced-before (2)
{ std::lock_guard<std::mutex> g(m); }   // (2) unlock(m): release
                                      //      (2) synchronizes-with (3)

// Thread B
{ std::lock_guard<std::mutex> g(m); }   // (3) lock(m): acquire
assert(payload == 42);                 // (4) sequenced-after (3)
                                       // (1) happens-before (4) → defined

The assert can never fire. Not because the mutex "flushes cache" (it doesn't need to), but because the abstract machine forbids any execution where (4) sees the old value. That's the entire game: you reason on the abstract machine; the implementation makes it true on silicon.

The data race rule — UB, not "reads garbage"

Two conflicting accesses (same object, at least one write, not both atomic) not ordered by happens-before constitute a data race, and a program with a data race has undefined behavior. This is not "you might read a stale value" — the standard places no limit on the consequences, because the optimizer assumes no races exist. The classic manifestation is register caching: the compiler is allowed to hoist a non-atomic load out of a loop, so the loop reads the variable once and never again:

bool stop = false;               // non-atomic — WRONG

// Thread A
while (!stop) { work(); }        // compiler: while(true) { work(); }
                                 // load hoisted out; A never sees stop=true

// Thread B
stop = true;                     // legal under as-if: no thread may
                                 // observe the loop NOT ignoring it

At -O2 this compiles to an infinite loop on every compiler and every ISA. Not a hardware visibility bug — a compiler transformation that is provably invisible in every defined execution. There are none here.

You are not alone

Every serious ecosystem converged on the same shape of model: Java's happens-before (JMM, JSR-133), LLVM's atomics (the IR-level ordering the compilers actually implement), and the Linux Kernel Memory Model (LKMM) for kernel code. Learn the C++ one and the vocabulary transfers.

Keystonehappens-before = sequenced-before ∪ synchronizes-with, closed under transitivity. It is the only legal way to order a read against a write in another thread; without it you don't have a stale value, you have UB.
Anti-patternThinking of a race as "reads garbage data". UB licenses the compiler to hoist loads, sink stores, and assume single-threaded invariants — the failure is usually an infinite loop or a deleted branch, not a torn value.

Retrieve it

Why is single-threaded reasoning a subset of the memory model?

Because happens-before restricted to one thread is exactly sequenced-before, and the as-if rule permits reordering only within that constraint.

The model was designed so that all pre-C++11 single-threaded semantics survive unchanged; concurrency adds new relations on top.

A thread loops on a non-atomic bool while another sets it. What went wrong at the compiler level?

The load of the bool was hoisted out of the loop — cached in a register — so the loop condition never re-reads memory.

With no synchronizes-with edge, no defined execution can distinguish the hoisted version, so as-if permits it. The result is an infinite loop.

Does a mutex unlock "flush" the writes before it?

No — it creates a synchronizes-with edge with the next lock, giving happens-before, which guarantees visibility.

The mechanism is abstract: the implementation achieves it with whatever barriers the ISA needs, often none on x86-64.

Prove it to yourself

Try it — 15 minutes

Race, observe, fix. Save:

// race.cpp
#include <thread>
#include <cstdio>
int counter = 0;                      // non-atomic
int main() {
  std::thread t1([]{ for (int i=0;i<1'000'000;++i) ++counter; });
  std::thread t2([]{ for (int i=0;i<1'000'000;++i) ++counter; });
  t1.join(); t2.join();
  std::printf("%d\n", counter);       // expect 2000000; usually less
}

1. Build and run 5 times: clang++ -std=c++20 -O2 race.cpp && for i in 1 2 3 4 5; do ./a.out; done — note the lost updates.
2. Rebuild with -fsanitize=thread -g -O1 and run once. Read the report: it names both access stacks and shows the missing happens-before edge between them.
3. Wrap the increments in a std::mutex, re-run under TSAN (clean) and plain (always 2000000). You created the synchronizes-with edge.
