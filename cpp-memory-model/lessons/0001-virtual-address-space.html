Virtual Memory: The Process Address Space

Every address your C++ program manipulates is a fiction maintained jointly by the MMU and the OS, at page granularity.

When you write &x, the value is a virtual address (VA). It names a byte in your process's private address space, not a byte in DRAM. The hardware's MMU translates VA→PA (physical address) on every memory access, using page tables walked by the CPU (4 levels on x86-64: PML4 → PDPT → PD → PT, covering 48-bit canonical addresses; more levels or bigger radix nodes on ARM64), and caches translations in the TLB. A TLB hit costs ~nothing; a miss costs a multi-level walk. This is the substrate everything else in the course sits on.

Pages, faults, demand paging

Translation happens in units of pages — typically 4 KiB. The OS maps in pages, and it does so lazily: mmap and exec only update page tables; memory is attached on first touch, when the access raises a page fault. A minor fault is satisfied from memory (e.g. map a zero page, or steal a recycled frame); a major fault requires disk I/O (reading in a text page of the binary, or a swap-backed page). "Your allocator touched memory and it was slow" is usually "you faulted in N pages", a story we quantify in Lesson 9 and in Drepper's classic "What Every Programmer Should Know About Memory".

Layout of a Linux process

Reading /proc/pid/maps bottom-up: text (code, r-x), rodata (r--), data (rw-, initialized globals), bss (rw-, zero-initialized, demand-zero), the heap grown via brk, the mmap region (shared libraries, large allocations, file mappings), the stack, and the vsyscall/vdso pages. proc(5) documents the file; see also pmap(1). ASLR (Address Space Layout Randomization) randomizes the base of stack, heap, mmap, and PIE binaries each run — print an address twice and it will differ.

// addrs.cpp — g++ -O0 addrs.cpp; run twice, addresses shift (ASLR)
#include <cstdio>
#include <cstdlib>
int g_init = 42;            // .data
int g_zero;                 // .bss
int main() {
  int local = 1;                    // stack
  static int s_local = 2;           // .data
  int* heap = new int[3];           // heap (mmap'd)
  auto lam = []{ return 1; };       // code-ish: usually .text
  std::printf("stack   %p\n", (void*)&local);
  std::printf("static  %p\n", (void*)&s_local);
  std::printf("global  %p\n", (void*)&g_init);
  std::printf("bss     %p\n", (void*)&g_zero);
  std::printf("heap    %p\n", (void*)heap);
  std::printf("lambda  %p\n", (void*)&lam);
  delete[] heap;
}

mmap with MAP_ANONYMOUS|MAP_PRIVATE is the universal primitive: the kernel creates a mapping with no backing file, filled with zero pages on demand. malloc's big allocations, thread stacks, std::vector growth — all end here. Huge pages (2 MiB/1 GiB) reduce TLB pressure; we defer them to Lesson 9.

KeystoneYour pointers never address RAM; they address a per-process mapping the OS can rewrite, on demand, at page granularity. Unmapped? SIGSEGV. Swapped or not-yet-faulted? The same pointer value stalls until the page arrives. The mapping, not the number, is the real object.
Anti-patternTreating an address as stable identity or as evidence of physical layout. "It worked because the pointer was small" is nonsense under ASLR and mmap; "allocation == memory used" is wrong under demand paging. Cost models built on addresses instead of page-fault counts mispredict every time.

Retrieve it

What does an MMU TLB cache?

Virtual-to-physical page translations

The TLB caches page-table entries so repeated accesses to a page skip the multi-level walk — hence "TLB pressure" from scattered access.

What triggers a major fault?

Disk I/O for backing storage

Minor faults are resolved from memory (zero page, recycled frame); major faults must read from disk (binary text, swap) — orders of magnitude slower.

What does brk extend?

The program break (heap)

brk moves the end of the data segment to grow/shrink the classic heap; large allocations go to the mmap region instead.

Prove it to yourself

Try it — 10 minutes Compile the program above, run ./a.out &, then inspect it: cat /proc/$(pgrep a.out)/maps (Linux) or vmmap $(pgrep a.out) (macOS). Match each printed pointer to a mapped region — note the heap pointer's region differs between runs (ASLR), while the offset between globals stays constant. On Linux, also run pmap -x $(pgrep a.out) and compare the "RSS" column (faulted-in pages) to mapping sizes: most mapped pages are not resident.

Primary source

Drepper, "What Every Programmer Should Know About Memory", §1–2 — the canonical hardware/OS view of memory from the metal up; pair with proc(5) for the maps file you just used.

Why this matters for the mission

The memory model's guarantees are about visibility and ordering of writes; but every write first has to land in a page someone else can eventually see. Cache coherence (Lesson 8) operates on physical memory; atomics (Lesson 5) only work on memory the MMU actually maps. When a lock-free demo mysteriously corrupts, page granularity, aliasing mappings, and demand paging are among the first physical suspects.
