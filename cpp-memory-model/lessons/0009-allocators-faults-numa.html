Allocators, Page Faults, THP, NUMA

new reserves address space, not memory — the kernel hands you physical pages only on first touch, and where and how big those pages are decides your real latency.

Memory is not allocated until you touch it

When you allocate 1 GB with new char[1<<30], glibc's malloc sees a request far above the M_MMAP_THRESHOLD (default 128 KB) and calls mmap(NULL, 1<<30, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, ...). The kernel does something surprising: it maps a range of virtual addresses to a single reserved-and-zeroed state and returns in microseconds. RSS barely moves.

Physical memory appears lazily. The first write to each 4 KB page raises a minor page fault; the fault handler maps a fresh zeroed physical page ("demand-zero paging" — see mmap(2) on man7 and Ulrich Drepper's What Every Programmer Should Know About Memory, §4.1–4.3). The first read of an untouched anonymous page maps the shared zero page copy-on-write — reads alone cost almost no memory.

Consequences you have felt without knowing why: freshly allocated containers "warm up" (first pass is fault-bound, not CPU-bound), memset of a 1 GB buffer is ~250k faults plus DRAM bandwidth, and forked servers that write shared pages trigger copy-on-write faults. Measure it:

#include <sys/resource.h>
#include <cstdio>

long minflt() {
    struct rusage ru; getrusage(RUSAGE_SELF, &ru);
    return ru.ru_minflt;               // minor faults = pages demand-zeroed
}

int main() {
    constexpr size_t N = 1 << 30;      // 1 GiB
    char* p = new char[N];
    long before = minflt();
    for (size_t i = 0; i < N; i += 4096) p[i] = 1;   // touch one byte per page
    std::printf("faults=%ld (expect ~%zu)\n", minflt() - before, N / 4096);
}

Or from outside: perf stat -e page-faults,minor-faults ./a.out, and watch RSS climb page by page in pmap -x <pid> or top.

NUMA: the page lives where it was first written

On a dual-socket machine, each CPU package has its own memory controllers and its own local DRAM. A physical page is assigned to a NUMA node by first-touch policy (the default, Mpolicy_default with local allocation — see numa(7) on man7): the node that faults it in owns it. If thread A on socket 0 initializes a huge array and thread B on socket 1 processes it, every load B makes crosses the interconnect (UPI on x86, AMBA coherency mesh on ARM servers) — roughly 1.5–2× the latency and a fraction of the bandwidth.

This is the most commonly missed performance bug in multithreaded number crunching: the code is correct, the layout is wrong. Diagnose with numastat -p <pid> (watch numa_miss/numa_foreign grow) or perf c2c. Fix by initializing data on the node that will use it, or pin explicitly:

numactl --cpunodebind=1 --membind=1 ./worker   # everything on node 1
numactl --interleave=all ./worker              # round-robin pages (bandwidth-bound)

macOS arm64 desktops are UMA — single-chip unified memory — so this lesson is best run on a Linux server or in CI; the concepts still explain Apple Silicon's core-cluster L2 asymmetry.

Transparent Huge Pages: fewer TLB misses, occasional tail latency

The TLB has limited entries; with 4 KB pages, a 1 GB working set needs ~262k of them. A 2 MB huge page covers 512 small pages with one TLB entry — for array-striding workloads (hash tables, GC heaps, dense matrices) this can cut TLB misses by an order of magnitude and speed up walks 10–30% (Drepper §6.2.2 measures exactly this).

THP can be always, madvise, or never (/sys/kernel/mm/transparent_hugepage/enabled). The problem with always: the kernel's khugepaged thread aggressively collapses and compacts memory, so an application that touched 4 KB out of every 2 MB region finds RSS rounded up ~512×, and compaction stalls threads for milliseconds — the classic database-ops incident (MongoDB, Redis, PostgreSQL all ship guidance telling you to switch to madvise). The tuned setting in production is:

echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
// and in the program, on the regions that deserve it:
madvise(buf, len, MADV_HUGEPAGE);   // opt this range into THP

Verify with /proc/<pid>/smaps — look for AnonHugePages: 2048 kB per backed region. On macOS there is no user-facing THP switch; observe 16 KB base page size and region sizes in vmmap <pid> instead.

The allocator landscape

glibc malloc (ptmalloc2 lineage): small allocations come from per-thread arenas (up to 8×cores on 64-bit) so threads rarely contend a lock; each thread additionally has a tcache — a lock-free per-thread cache of free lists checked before anything else. Size buckets: tcache/fastbins for ≤~160 B (single-linked freelist pushes, no locks), smallbins up to 1 KB, unsorted/largebins above. Big requests (≥128 KB by default) go straight to mmap and free() munmaps them — memory returns to the OS immediately. Arena chunks are trimmed only if the top of the heap is free and contiguous (M_TRIM_THRESHOLD), so a long-lived server's RSS is usually a high-water mark, not current usage. Tuning knobs: mallopt(), the MALLOC_ARENA_MAX env var (JVM-adjacent ops folk set it to 2–4 to fight fragmentation at the cost of contention).

tcmalloc (Google): every thread gets a thread cache of size-class free lists — malloc/free on the fast path are a few instructions with zero atomics; when a cache empties or fills it refills/drains in batches from the central cache, which manages page-heap spans via pagemap metadata. Memory returns to the OS via ReleaseFreeMemory() / the background MemoryDecoder, on a delay. See the docs at google/tcmalloc design.md.

jemalloc (FreeJS/Facebook lineage): size-class allocations out of per-CPU/arena extents, plus explicit decay-based purging — dirty pages are returned to the OS on an exponential decay schedule (dirty_decay_ms / muzzy_decay_ms), giving it the best-behaved RSS curve of the three, at the cost of more madvise traffic.

Custom arenas and slabs win when allocation shape is known: games use frame arena allocators (bump-pointer, wholesale free at frame end — zero fragmentation, zero per-object cost); HFT and embedded use slabs of fixed-size objects to get malloc off the hot path entirely and to make fragmentation impossible. The rule from Lesson 8's cache-line thinking applies: if you can delete the allocator from the fast path, do it.

KeystoneAllocation is a promise, first touch is the act. new books virtual address space; the page fault on first write is when physical memory, NUMA placement, and page size are actually decided — so initialization loops are a placement policy, and your choice of allocator is a policy about when pages go back.
Anti-patternOne thread initializes, another thread computes. The pages all land on the initializer's socket; the compute loop then pays cross-node latency on every cache miss. Similarly: THP set to always on a latency-sensitive service — RSS balloons and khugepaged introduces multi-ms stalls.

Retrieve it

Why does RSS stay near zero right after allocating 1 GB with new char[1<<30]?

Anonymous mmap reserves virtual address space only; physical pages attach on demand at first-touch faults.

Demand-zero paging: writing a page raises a minor fault, and the kernel maps a zeroed physical frame then. Read-only touches may map the shared zero page copy-on-write.

What decides which NUMA node owns a page under Linux's default policy?

The node of the CPU whose thread first writes the page (first-touch).

Local-allocation policy assigns the faulting node's memory, so initialization placement is placement policy — use numactl --cpunodebind --membind or initialize where you compute.

Give one benefit and one cost of transparent huge pages.

Benefit: 512× TLB coverage per entry; cost: RSS rounding-up and khugepaged compaction stalls.

That's why the tuned production setting is madvise mode with explicit madvise(MADV_HUGEPAGE) on hot regions, not global always.

Prove it to yourself

Try it — 20 minutes

On Linux (or a VM/container):

// faultdemo.cpp — clang++ -std=c++20 -O2 faultdemo.cpp
#include <sys/mman.h>
#include <sys/resource.h>
#include <chrono>
#include <cstdio>
#include <vector>

long minflts() { struct rusage ru; getrusage(RUSAGE_SELF, &ru); return ru.ru_minflt; }

int main(int argc, char**) {
    constexpr size_t GB = 1 << 30;
    bool huge = argc > 1;                       // argv[1] => MADV_HUGEPAGE
    std::vector<char*> bufs;
    char* p = (char*)mmap(nullptr, GB, PROT_READ|PROT_WRITE,
                          MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    if (huge) madvise(p, GB, MADV_HUGEPAGE);
    auto t0 = std::chrono::steady_clock::now();
    long f0 = minflts();
    for (size_t i = 0; i < GB; i += 4096) p[i] = 1;   // "touch every page"
    auto t1 = std::chrono::steady_clock::now();
    std::printf("faults=%ld  time=%.1f ms (huge=%d)\n",
        minflts() - f0,
        std::chrono::duration<double, std::milli>(t1 - t0).count(), huge);
}

Run ./a.out then ./a.out huge: expect ~262k faults and ~10–25 ns/page; with THP backed by 2 MB pages expect ~512 faults (the loop still touches 262k addresses but only 512 pages materialize) and visibly lower time. Cross-check with perf stat -e page-faults,minor-faults,dTLB-load-misses ./a.out, and inspect grep -A1 AnonHugePages /proc/self/smaps style output via cat /proc/$(pgrep a.out)/smaps | grep AnonHuge. On macOS arm64: the THP half of the demo won't apply, but the fault counts will — and run vmmap <pid> to see the anonymous MALLOC_LARGE region grow.

Primary source

mmap(2) on man7 plus Drepper's “What Every Programmer Should Know About Memory”: the man page defines the demand-paging contract your measurements rest on, and Drepper §6 gives the canonical NUMA and huge-page benchmarks you just reproduced.
