Stack vs Heap: Allocation Mechanics

Stack allocation is one register move; heap allocation is a data-structure algorithm plus, sooner or later, page faults.

The stack: allocation = moving a register

Each call pushes a stack frame. The x86-64 SysV prologue is typically push rbp; mov rbp,rsp; sub rsp,N — "allocating" N bytes is the sub. Epilogue: add rsp,N; pop rbp; ret (or leave; ret). Deallocation is equally free. The red zone (128 bytes below RSP that leaf functions may use without moving SP) is why even the sub can vanish. In Compiler Explorer, compile this and watch:

int sum(int a, int b) {      // x86-64 SysV: esi, edx
  int t = a + b;             // eax, esi, edx... no frame needed
  return t;                  // red zone: nothing pushed at all
}
int frame(int n) {
  int buf[64];               // sub rsp, 272-ish
  buf[0] = n;
  return buf[0];
}

Because allocation is just pointer arithmetic, nothing stops you from falling off the end. The kernel places a guard page below the stack and enforces a size cap — ulimit -s, typically 8 MiB on Linux. Blow through it (deep recursion, big int buf[1<<20] in a frame) and you get SIGSEGV; per-thread stacks are usually far smaller (pthread default ~8 MiB virtual, but see pthread_create(3)).

The heap: from brk to bins

The classic heap is the brk area: bump and shrink the program break. Modern glibc malloc layers real machinery on top (see the glibc malloc internals wiki): a per-thread tcache of recently freed small chunks (no lock in the common case), then fastbins / smallbins / largebins, and per-thread arenas so threads don't serialize on one lock. Allocations larger than the dynamic mmap threshold (starting at 128 KiB, M_MMAP_THRESHOLD) bypass the bins and go straight to mmap(2) — freed immediately on free, which is why big new/delete cycles show up as RSS churn and page faults on every reuse.

So the true cost of new T(args): (1) allocator bookkeeping (fast: tcache pop), (2) the constructor, (3) possibly faulting in pages the allocator never touched before — and Lesson 1's rule: the mapping is free, the fault is not.

// grow.cpp — g++ -O2 grow.cpp && ./a.out
#include <vector>
#include <chrono>
#include <cstdio>
int main() {
  using clk = std::chrono::steady_clock;
  auto t0 = clk::now();
  std::vector<int> v;
  for (int i = 0; i < 10'000'000; ++i) v.push_back(i);   // ~2x memcpy churn
  auto t1 = clk::now();
  std::vector<int> w;
  w.reserve(10'000'000);                                  // one mmap, one fault sweep
  for (int i = 0; i < 10'000'000; ++i) w.push_back(i);
  auto t2 = clk::now();
  std::printf("push_back only : %lld ms\n",
    (long long)std::chrono::duration_cast<std::chrono::milliseconds>(t1-t0).count());
  std::printf("reserve first  : %lld ms\n",
    (long long)std::chrono::duration_cast<std::chrono::milliseconds>(t2-t1).count());
}

Second experiment: loop new char[1<<20] / delete[] and watch ps -o rss (or grep VmRSS /proc/self/status) — above the mmap threshold each cycle tears down and re-faults pages, so RSS oscillates and faults accumulate; below it, the tcache/bins reuse warm memory and RSS stays flat.

KeystoneStack allocation is pointer arithmetic; heap allocation is a library data structure whose worst cost is a page fault. Everything you pay for at runtime — locks, bin walks, zeroing, faults — lives on the heap side of that line.
Anti-pattern"new is like a stack variable that lives longer." No: the stack cost is one sub and is reclaimed wholesale at return; heap cost is allocator state, constructor, and faulting, and is reclaimed one chunk at a time. Budgeting them identically produces programs that "randomly" jitter on allocation.

Retrieve it

What does a frame prologue do?

Saves RBP, subtracts RSP

push rbp; mov rbp,rsp; sub rsp,N — the sub is the entire allocation for N bytes of locals.

What is malloc's tcache?

Per-thread free-chunk cache

A lock-free-in-practice cache of recently freed small chunks, so the common free-then-same-size-alloc pattern skips arena locking entirely.

When does malloc use mmap?

Above ~128KB threshold

Requests larger than the dynamic mmap threshold (M_MMAP_THRESHOLD, starting at 128 KiB) are mapped directly and returned to the OS on free.

Prove it to yourself

Try it — 15 minutes Run grow.cpp above — reserve-first is typically 2–5x faster; confirm in a profiler that the difference is memcpy of geometric growth, not push_back itself. Then run the churn loop for(;;){ char* p = new char[1<<20]; p[0]=1; delete[] p; } in one terminal while ps -o rss= -p <pid> loops in another: watch faults via grep majflt /proc/<pid>/status (Linux) or Instruments' Allocations (macOS arm64). Repeat with new char[4096] — RSS and faults go flat because the bins recycle warm pages.

Why this matters for the mission

Lock-free code is usually motivated by allocation on the hot path: shared state must live somewhere stable. Knowing exactly when new turns into mmap+faults tells you why a "lock-free" queue that allocates per item can lose to a blocking one that doesn't — and Lesson 3 formalizes what "the object" you allocated actually is.
