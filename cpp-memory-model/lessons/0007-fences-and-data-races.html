Fences, Data Races, and UB

A fence orders nothing by itself — it only works in partnership with atomic operations, and everything else about "racy but works on my machine" is undefined behavior.

The fence sandwich problem

std::atomic_thread_fence(memory_order_release) looks like it should mean "flush everything before this point". It does not. A fence with no atomic operation nearby is a no-op in practice: fences don't order memory, they order atomic operations. Jeff Preshing's formulation (Acquire and Release Fences) gives the exact rule:

  • A release fence F synchronizes-with an acquire operation B on atomic object M if there exists some atomic store A to M (any ordering — even memory_order_relaxed) that is sequenced before F, and B reads the value written by A (or a later value in M's modification order).
  • Mirror rule for acquire fences: an acquire fence F synchronizes-with a release operation A on M if some atomic load B from M is sequenced after F and B reads the value A wrote.

So the pattern is a sandwich: relaxed store → release fence on the producer side, and acquire fence → relaxed load on the consumer side. Miss any ingredient — no fence-ordered relaxed load, no store sequenced before the release fence — and there is no synchronizes-with edge, no happens-before, and a data race.

Why fences exist at all

If acquire/release atomics already synchronize, why fences? Because one fence can order many cheap relaxed atomics. The classic pattern is "data dependency without atomic payload": publish a group of relaxed counters or flags, then one release fence before publishing a single sentinel; the reader takes one acquire fence after seeing the sentinel, and every relaxed value written before the fence is now guaranteed visible. You pay one expensive barrier instead of N release stores. This is how lock-free libraries (Dmitry Vyukov's mpmc queue, RCU-style publication) are built.

volatile is NOT atomic

volatile has exactly two legitimate jobs: memory-mapped I/O registers and sig_atomic_t-style communication with signal handlers. It guarantees the compiler will not elide or merge accesses — nothing more:

  • No tearing protection: a volatile int64_t store on 32-bit hardware can be observed half-written.
  • No happens-before: volatile accesses participate in neither synchronizes-with nor the modification order that makes races defined.
  • No hardware barrier: on weakly-ordered ARM, volatile loads/stores compile to plain ldr/str with no dmb.

In signal handlers, the standard only blesses lock-free atomics (std::atomic_signal_fence for ordering) and volatile std::sig_atomic_t. A non-lock-free atomic that touches a heap lock inside a handler that interrupted the lock's owner is deadlock.

KeystoneFences order atomics, not variables. A release fence is only half of a synchronizes-with edge; the other half is an atomic store sequenced before it paired with an atomic load that reads that value. No atomics, no ordering.
Anti-patternReplacing a mutex with volatile "because it's faster". The data race is still there — the whole program's behavior is undefined, and it will fail precisely during the demo. volatile is for MMIO and signal handlers; nothing else.

TSAN is ground truth

Data races are UB, so you cannot test for them by observing output. ThreadSanitizer (-fsanitize=thread) instruments the actual happens-before graph at runtime and reports races even when the interleaving happened to be benign. Learn to read the report: it names the two conflicting accesses, the memory location, and — most valuably — the creation stacks of both threads, so you can see which synchronization edge you forgot to create. Keep TSAN runs separate from ASAN runs (they're incompatible); CI one configuration with TSAN always on.

$ clang++ -std=c++20 -O1 -g -fsanitize=thread race.cpp && ./a.out
WARNING: ThreadSanitizer: data race (pid=12345)

Mutex vs atomic vs fence — the decision rule

  • Mutex: default choice. Any state bigger than a word, any critical section with more than one operation, any blocking wait.
  • Atomic: single-word flags, counters, sequence numbers — when the operation is genuinely one word and you can name its ordering.
  • Fence: library builders only. If you're writing application code and reach for atomic_thread_fence, you are almost certainly re-inventing something <atomic> already expresses more safely.

Retrieve it

State Preshing's rule for when a release fence synchronizes-with an acquire load.

When some atomic store to the same object is sequenced before the fence, and the load reads that stored value.

The store–fence pair on one side plus a reading load on the other forms the edge; either half alone orders nothing.

Why can one release fence publish many relaxed atomics?

The fence's ordering applies to every atomic store sequenced before it, not just one.

Happens-before is transitive: all relaxed writes before the fence become visible after the paired acquire read — one barrier, N publications.

What may a C++ signal handler safely touch?

Lock-free atomics, sig_atomic_t, and atomic_signal_fence for ordering.

A handler can interrupt arbitrary code, so anything that might take a lock with the lock-holder suspended can never return.

Prove it to yourself

Try it — 20 minutes

Classic racy flag+payload:

// race.cpp
#include <atomic>
#include <thread>
#include <cstdio>
int payload = 0;
bool flag = false;                       // racy plain types
int main() {
    std::thread t([]{ payload = 42; flag = true; });
    while (!flag) {}
    std::printf("%d\n", payload);        // may print 0 under TSAN = UB
    t.join();
}

1) Compile with clang++ -std=c++20 -O1 -g -fsanitize=thread race.cpp; read the report — note it flags the race even if the output is "correct". 2) Fix #1: make flag an atomic<bool>, store with release, load with acquire. Verify TSAN clean. 3) Fix #2: keep all atomic ops relaxed and insert atomic_thread_fence(memory_order_release) after the payload store / acquire fence after the observing load — Preshing's sandwich. Verify TSAN clean again. Both fixes are correct; the second is what libraries do to batch many relaxed ops under one barrier.

Primary source

Preshing — Acquire and Release Fences — the clearest statement anywhere of the exact synchronizes-with rule for standalone fences, with the sandwich worked example.

Why this matters for the mission

Undefined behavior from data races is the single most common way "works on x86, corrupts on ARM" ships. Once you can read a TSAN report and know the fence rule, you can both diagnose races and understand what lock-free library code is doing beneath its API.
