实战中的 Acquire/Release、seq_cst 与 Relaxed

Acquire/release 用来发布数据，relaxed 用在没人借它排序的数据上，seq_cst 用在多个原子操作必须被所有人以同一顺序观察时。

经典的发布（publish）模式

一次 release store 与一次 acquire load 配对；synchronizes-with 边让生产者写入的一切对消费者在 load 之后的操作可见（见 Preshing《Acquire and Release Semantics》）：

struct Widget { int a, b; std::string name; };
Widget payload;                       // 普通数据
std::atomic<bool> ready{false};

// 生产者线程
payload.a = 1; payload.b = 2; payload.name = "hi";   // (1)
ready.store(true, std::memory_order_release);        // (2) 发布 (1)

// 消费者线程
while (!ready.load(std::memory_order_acquire)) {}    // (3) 看到 (2)
// (2) synchronizes-with (3)：(1) happens-before 下面的一切
assert(payload.a == 1 && payload.name == "hi");      // 不可能触发

把任一侧换成 relaxed，assert 就变成掷硬币：标志位依然原子地翻转，但边不存在，payload 的写可能不可见。

Relaxed：计数器正确，生命周期错误

当没有其他内存借助该原子排序时，relaxed 正确且高效：统计、进度计数、序列号生成。但引用计数递减绝不能 relaxed。对象的最后一次释放必须 happens-after 其他所有持有引用的线程的全部访问——这就是"last-release"模式，要求递减用 acq_rel（或 seq_cst）：acquire 让析构函数看到其他线程对对象的所有访问，release 让你自己的访问排在析构之前。relaxed 递减可能让析构与另一个线程仍在执行的方法并发。

seq_cst：需要一个人人认同的全序时

Acquire/release 给的是成对的边。有时你需要多个原子操作在多个线程眼中构成全序（total order）。两个典型案例：

IRIW（Independent Reads of Independent Writes，独立写各自的独立读）——四个线程：

// T1: x.store(1, release);        // T2: y.store(1, release);
// T3: r1 = x.load(acquire);  r2 = y.load(acquire);
// T4: r3 = y.load(acquire);  r4 = x.load(acquire);
// 可能观察到 r1==1, r2==0, r3==1, r4==0 吗？acquire/release：可以。
// seq_cst：不可能——所有线程都认同 x 的写先于 y 的写。

Dekker 式先存后读——两个线程各写自己的标志再查对方的：

// T1: a.store(1, release);  if (b.load(acquire) == 0) enter();
// T2: b.store(1, release);  if (a.load(acquire) == 0) enter();
// 用 release+acquire，两个线程都可能看到对方标志 == 0 而同时进入。
// 每个 load 确实 acquire 到了对方的 store……但顺序各不相同，
// 因为不存在共享的全序。
// 用 seq_cst，至少一方会看到 1——两次 store 被全序化了。

决策表

  • 默认：seq_cst。在上述所有模式中都正确；只在 TSO ISA 上、只对 store 付一条 fence 的代价。
  • 放宽为 release（store）/ acquire（load）：当你通过单个标志发布或消费数据——成对的边正是你需要的。
  • 放宽为 relaxed：只用于没人借其值排序其他内存的独立计数器/统计量。
  • acq_rel：既发布又消费的 RMW——引用计数上的 fetch_sub 是教科书案例。

同一原子上混用不同序是一种坏味道——说明有人只优化了一处访问而没有证明边依然成形。但混用有时是对的：同一引用计数上 relaxed 递增配 acq_rel 递减正是正确的非对称（递增不发布任何东西；最后一次递减终结一个生命周期）。

Keystone问自己"谁在观察什么、方向是哪边？"发布：release store + acquire load。终结生命周期：acq_rel RMW。多个原子、多个观察者、一个故事：seq_cst。没人借它观察：relaxed。
Anti-pattern对引用计数使用 fetch_sub(1, std::memory_order_relaxed)。减到零的那次递减不与其他线程对对象的读排序，析构函数可能与仍在运行的方法竞争——披着优化外衣的 UB。

回忆检索

发布模式为什么必须在 store 上用 release，而只在 load 上用 seq_cst 不行？

因为 synchronizes-with 需要一次 release 写与读到该值的 acquire 读配对；边需要两个端点。

单独一个 seq_cst load 无法对 relaxed 或普通 store 排序任何东西；排序是这一对的属性，不是单侧的。

在 Dekker 模式中，acquire/release 会让两个线程观察到什么 seq_cst 禁止的现象？

双方都可能把对方的标志读为 0，从而同时进入临界区。

两组 store→load 顺序互相冲突，而 acquire/release 允许各自独立成立；只有全部 seq_cst 操作的单一全序才能排除该结果。

为什么引用计数递增用 relaxed 正确、递减却不行？

递增不发布数据、不守护生命周期；减到零的递减必须 happens-after 其他所有线程的访问。

递减上的 acq_rel 创建这些边；relaxed 递减会在仍有读者在对象内部时析构它。

亲手验证

Try it — 25 分钟 
// refcount.cpp — 编译：clang++ -std=c++20 -O2 -pthread refcount.cpp
#include <atomic>
#include <thread>
#include <cstdio>

struct Handle {
  std::atomic<int> refs{1};
  int value = 42;
  void add_ref()   { refs.fetch_add(1, std::memory_order_relaxed); }
  void release_ref() {
    if (refs.fetch_sub(1, std::memory_order_acq_rel) == 1) delete this;
  }
};

int main() {
  auto* h = new Handle;
  h->add_ref();
  std::thread t([h]{ h->add_ref(); h->release_ref(); });  // 使用 value
  std::thread u([h]{ std::printf("%d\n", h->value); });    // 普通读
  t.join(); u.join();
  h->release_ref();   // 只有在所有读者结束后才析构
}

1. 编译运行——输出 42，正常退出。再在 -fsanitize=thread 下运行：无报告（acq_rel 边为最终 delete 排序）。
2. 把递减改为 memory_order_relaxed，在纸上推理：现在哪一对访问无序？解释为什么 TSAN 可能仍抓不到它（delete 之后对 this 的竞争）。
3. 恢复 acq_rel；把递增改为 seq_cst 并测一个紧凑的 add/release 循环——吞吐下降就是你拒绝支付的那笔钱。
