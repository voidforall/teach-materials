Acquire/Release vs seq_cst vs Relaxed in Practice

Acquire/release is for publishing data, relaxed is for data nobody orders through, and seq_cst is for when multiple atomics must be seen in one order by everyone.

The canonical publish pattern

One release store pairs with one acquire load; the synchronizes-with edge makes everything the producer wrote visible to everything the consumer does after the load (per Preshing, Acquire and Release Semantics):

struct Widget { int a, b; std::string name; };
Widget payload;                       // plain data
std::atomic<bool> ready{false};

// Producer thread
payload.a = 1; payload.b = 2; payload.name = "hi";   // (1)
ready.store(true, std::memory_order_release);        // (2) publishes (1)

// Consumer thread
while (!ready.load(std::memory_order_acquire)) {}    // (3) sees (2)
// (2) synchronizes-with (3): (1) happens-before everything below
assert(payload.a == 1 && payload.name == "hi");      // cannot fire

Swap either order for relaxed and the assert becomes a coin-flip: the flag still flips atomically, but no edge exists, so the payload writes may not be visible.

Relaxed: right for counters, wrong for lifetimes

When no other memory is ordered through the atomic, relaxed is correct and fast: statistics, progress counters, sequence-number generation. But a refcount decrement must never be relaxed. The last release of a shared object must happen-after every access by every other thread that held a reference — that's the "last-release" pattern, and it requires the decrement to be acq_rel (or seq_cst): acquire so the destructor sees all other threads' accesses to the object, release so your own accesses are ordered before destruction. A relaxed decrement can let the destructor run while another thread is still inside a method.

seq_cst: when you need one order everyone agrees on

Acquire/release gives pairwise edges. Sometimes you need a total order over several atomics observed from several threads. Two canonical cases:

IRIW (Independent Reads of Independent Writes) — four threads:

// T1: x.store(1, release);        // T2: y.store(1, release);
// T3: r1 = x.load(acquire);  r2 = y.load(acquire);
// T4: r3 = y.load(acquire);  r4 = x.load(acquire);
// Can observe r1==1, r2==0, r3==1, r4==0? With acquire/release: YES.
// With seq_cst: NO — all threads agree x's store preceded y's.

Dekker-style store-then-load — two threads each store their flag then check the other's:

// T1: a.store(1, release);  if (b.load(acquire) == 0) enter();
// T2: b.store(1, release);  if (a.load(acquire) == 0) enter();
// With release+acquire, BOTH threads can see the other's flag == 0
// and both enter. Each load acquired the other's store... in
// different orders, because there is no shared total order.
// With seq_cst, at least one sees 1 — the stores are totally ordered.

The decision table

  • Default: seq_cst. Correct in every pattern above; costs a fence only on stores, and only on TSO ISAs.
  • Relax to release (store) / acquire (load) when you're publishing or consuming data through a single flag — the pairwise edge is exactly what you need.
  • Relax to relaxed only for standalone counters/statistics whose value nobody uses to order other memory.
  • acq_rel for RMWs that both publish and consume — fetch_sub on a refcount is the textbook case.

Mixed orders on the same atomic are a smell — they signal someone optimized one access without proving the edges still form. But mixed is sometimes right: relaxed increments with an acq_rel decrement on the same refcount is precisely the correct asymmetry (increments publish nothing; the final decrement terminates a lifetime).

KeystoneAsk "who observes what, in which direction?" Publishing: release store + acquire load. Lifetime termination: acq_rel RMW. Multiple atomics, multiple observers, one story: seq_cst. Nobody observes through it: relaxed.
Anti-patternfetch_sub(1, std::memory_order_relaxed) on a refcount. The last decrement doesn't order against other threads' reads of the object, so the destructor can race with a still-running method — UB dressed up as an optimization.

Retrieve it

Why does the publish pattern need release on the store and not just seq_cst on the load?

Because synchronizes-with requires a releasing write paired with an acquiring read of that same value; the edge needs both endpoints.

A seq_cst load alone orders nothing against a relaxed or plain store; ordering is a property of the pair, not one side.

In the Dekker pattern, what do both threads observe with release/acquire that seq_cst forbids?

Both can load the other's flag as 0 and enter the critical section simultaneously.

The two store→load orders conflict but acquire/release permits each pair independently; only a single total order over all seq_cst ops rules the outcome out.

Why is relaxed correct for refcount increments but not the decrement?

An increment publishes no data and guards no lifetime; the decrement that reaches zero must happen-after all other threads' accesses.

acq_rel on the decrement creates the edges; a relaxed decrement destroys objects with readers still inside.

Prove it to yourself

Try it — 25 minutes 
// refcount.cpp — build: clang++ -std=c++20 -O2 -pthread refcount.cpp
#include <atomic>
#include <thread>
#include <cstdio>

struct Handle {
  std::atomic<int> refs{1};
  int value = 42;
  void add_ref()   { refs.fetch_add(1, std::memory_order_relaxed); }
  void release_ref() {
    if (refs.fetch_sub(1, std::memory_order_acq_rel) == 1) delete this;
  }
};

int main() {
  auto* h = new Handle;
  h->add_ref();
  std::thread t([h]{ h->add_ref(); h->release_ref(); });  // exercises value
  std::thread u([h]{ std::printf("%d\n", h->value); });    // plain read
  t.join(); u.join();
  h->release_ref();   // destructor runs only after every reader finished
}

1. Compile and run — output 42, clean exit. Then run under -fsanitize=thread: no report (the acq_rel edge orders the final delete).
2. Change the decrement to memory_order_relaxed and reason on paper: which pair of accesses is now unordered? Explain why TSAN may still not catch it (races on this after deletion).
3. Restore acq_rel; switch increment to seq_cst and measure a tight add/release loop — the drop in throughput is the price you refused to pay.
