Caches, MESI, and False Sharing

Hardware keeps every core's cache coherent — but a 64-byte line can only be owned by one writer at a time, and that fact costs you 5–10x on code that looks perfectly parallel.

The latency ladder

Everything in this lesson follows from one table of approximate costs on a modern x86/Apple-Silicon-class core:

  • L1 hit: ~4 cycles. L2: ~12 cycles. L3: ~40 cycles.
  • DRAM: ~200+ cycles — and each NUMA hop to another socket's memory makes it worse.
  • coherence traffic between private caches: a cross-core line transfer is a round trip in the same tens-to-hundreds-of-cycles regime as L3/DRAM.

The cache line — 64 bytes on essentially all current CPUs — is the actual unit of allocation and the unit of coherency. Two variables in the same line are, as far as the coherency protocol is concerned, one variable.

MESI in one minute

Every line in every cache is in one of four states (see Wikipedia's MESI article for the state diagram):

  • Modified — this cache has the only valid copy, and it's dirty (memory is stale).
  • Exclusive — only valid copy, clean. You may write it silently: E→M costs nothing.
  • Shared — possibly valid in other caches, read-only.
  • Invalid — no usable copy.

Writing to a line in State forces an RFO — Read For Ownership: the core must invalidate every other cache's copy and wait for the line to arrive before its store retires. That's a cross-core round trip on the critical path of your loop, repeated on every conflicting write. (Intel later added F; AMD uses MOESI — both optimizations let sharers keep reading a dirty line, but the invalidation-before-write cost you feel is the same.)

Coherent ≠ consistent

Here's the subtlety that makes this course necessary at all: hardware is cache-coherent — two cores will never long-term disagree about the contents of a line. So why do we need std::atomic and memory orders? Because of store buffers (writes sit in a per-core buffer before they reach L1, so a core observes its own writes early and others' late) and instruction reordering. Coherency says each location eventually agrees; it says nothing about the order in which different locations' writes become visible. As Sorin, Hill & Wood's A Primer on Memory Consistency and Cache Coherence hammers home: coherency is about single locations; consistency (the memory model) is about the order of all operations. C++'s memory model exists to let you constrain that order portably.

False sharing

Two threads writing different fields that happen to share one 64-byte line: no data race (different objects), fully correct C++ — and the line ping-pongs M↔I between the cores on every increment. You pay an RFO per iteration instead of ~1 cycle per increment.

// bench.cpp
#include <thread>
#include <chrono>
#include <cstdio>

struct Counters { long a; long b; };                      // same line
struct Padded   { alignas(64) long a; alignas(64) long b; };

template<class C>
long run() {
    C c{0,0};
    auto t0 = std::chrono::steady_clock::now();
    std::thread t1([&]{ for (long i = 0; i < 100'000'000; ++i) ++c.a; });
    std::thread t2([&]{ for (long i = 0; i < 100'000'000; ++i) ++c.b; });
    t1.join(); t2.join();
    auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
        std::chrono::steady_clock::now() - t0).count();
    return ms;
}

int main() {
    std::printf("shared:  %ld ms\n", run<Counters>());
    std::printf("padded:  %ld ms\n", run<Padded>());
}

Typical result on multicore x86 or Apple Silicon: the shared version takes ~5–10x longer than the padded one, with identical assembly for the loop bodies. Nothing in the C++ abstract machine explains the gap — only the 64-byte line does.

Detection and tools

  • Hardware counters: Linux perf c2c is purpose-built for false sharing; plain perf stat -e cache-memories,l2-deallocation-from-x-core ... style HITM events point at contended lines. macOS exposes Instruments' Cache/TLB templates instead.
  • Source suspicion: any frequently-written member adjacent to another frequently-written member in a hot struct.
  • Fix: alignas(64), or better, alignas(std::hardware_destructive_interference_size) (defined only where the platform provides it — GCC/libstdc++ guards it behind __cpp_lib_hardware_interference_size).
  • Caution: [[no_unique_address]] can make empty members share an address — fine for tags, but it also lets the compiler pack things you assumed were padded; don't rely on it for interference avoidance. And don't pad everything: padding wastes cache capacity and can hurt single-threaded locality.
  • Same family of thinking: AoS vs SoA — if you loop over one field, store that field contiguously. And prefetchers reward sequential access patterns; strided pointer-chasing defeats them. (NUMA is Lesson 9's problem.)
KeystoneThe unit of coherency is the 64-byte line, not the variable. Logical independence of two objects doesn't buy performance independence — if they share a line and both are written, you pay RFO round trips for code that has no race at all.
Anti-patternPer-thread counters packed in an array of std::atomic<long>. Eight counters, one line, eight threads: every increment invalidates the line for all others. Pad each element to a line (or to hardware_destructive_interference_size) and the contention vanishes.

Retrieve it

What does writing a line in Shared state cost, and why?

An RFO: a cross-core round trip to invalidate all other copies first.

MESI requires single-writer ownership; you can only write from E or M, so a Shared line must be invalidated elsewhere before your store can retire.

Caches are coherent — so why does C++ need a memory model?

Store buffers and reordering reorder visibility across different locations.

Coherency governs each single location; consistency — which locations' writes appear in what order — is what the memory model constrains. Different questions, per Sorin/Hill/Wood.

Two threads increment adjacent longs in one struct. Is it a data race? Why is it slow?

No race — different objects. Slow because both writes hit one 64-byte line.

The line ping-pongs M↔I between private caches, one RFO per write; pad with alignas(64) to separate the lines.

Prove it to yourself

Try it — 15 minutes

Compile and run the benchmark above: clang++ -std=c++20 -O2 bench.cpp && ./a.out on your machine (macOS arm64 or Linux). Record your two numbers and compute the speedup — expect ~5–10x. Then change Padded to use alignas(128). On Apple Silicon (and some Intel with adjacent-line prefetchers) 128-byte spacing can improve further or change nothing — observe, and explain with the prefetcher's two-line window. Optional on Linux: run under perf c2c record / perf c2c report and find your contended cache line in the output.
