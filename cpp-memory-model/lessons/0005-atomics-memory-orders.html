std::atomic and the Memory Orders

std::atomic gives you indivisibility (no tearing) plus a role in happens-before; the six memory orders are the dial for how much ordering you're buying with each operation.

Two guarantees, one template

std::atomic<T> promises two things a plain T cannot: indivisibility — reads see some value that was actually written, never a half-written mix ("no tearing") — and participation in the inter-thread machinery: each access carries a memory order that may create synchronizes-with edges. The six orders (memory_order):

  • memory_order_seq_cst — default; all seq_cst ops on all threads agree on one total order S.
  • memory_order_acquire — loads: nothing after you moves before you.
  • memory_order_release — stores: nothing before you moves after you.
  • memory_order_acq_rel — read-modify-write ops: acquire + release in one.
  • memory_order_relaxed — atomicity only, no ordering of surrounding memory.
  • memory_order_consume — data-dependency ordering; all implementations map it to acquire, and the standard discourages it. Skip it.

RMW: fetch_add and compare_exchange

Read-modify-write operations are the only ones that read and write atomically as one step — the difference between ++counter losing a million updates and losing none.

std::atomic<int> c{0};
c.fetch_add(1, std::memory_order_relaxed);   // atomic increment

// CAS loop idiom: weak may fail spuriously, so loop
int expected = head.load(std::memory_order_relaxed);
while (!head.compare_exchange_weak(expected, node->next,
                                    std::memory_order_acq_rel)) {}

compare_exchange_weak is allowed to fail without the value differing (spurious failure — think LL/SC on ARM); strong is not. In a loop, weak can be cheaper, so weak-in-loop, strong-once is the rule.

Which orders are legal where?

  • load(): seq_cst, acquire, relaxed (consume). Never release — a load releases nothing.
  • store(): seq_cst, release, relaxed. Never acquire.
  • RMW (fetch_add, exchange, CAS): seq_cst, acq_rel, acquire, release, relaxed.

When atomic<T> is secretly a lock

is_lock_free() tells you at runtime; is_always_lock_free is a compile-time constant. On mainstream ABIs anything up to 8 bytes is lock-free; atomic<double> on 32-bit, or a 16-byte struct with a non-trivial copy, may fall back to a hidden mutex per object — with all the deadlock-in-signal-handler and false-sharing pain that implies. Check before you assume; atomic_ref (C++20) is often a better shape for bulk data.

One trap even lock-free doesn't dodge: the ABA problem — a CAS on pointer P succeeds even though P was freed and reallocated back to the same address between your load and your store. Atomicity can't see history; we deal with it in Lesson 10.

What compiles to what

From Compiler Explorer (clang, -O2), same source on two ISAs:

// x86-64                                    // ARM64
x.store(1, seq_cst);   mov 1, eax            stlr wzr, [x0]
                       xchg [x], eax         // (stlr = store-release,
                       // (xchg is implicitly locked)  seq_cst when paired)
x.store(1, release);   mov [x], eax          stlr w1, [x0]
r = x.load(acquire);   mov eax, [x]          ldar w0, [x0]
r = x.load(relaxed);   mov eax, [x]          ldr  w0, [x0]

x86-64 is total-store-ordered: every store already has release semantics and every load acquire, so acquire/release are free; only seq_cst stores must pay (xchg or mov+mfence, ~20-40 cycles). ARM64 is weakly ordered: ldar/stlr carry the ordering, relaxed ops are plain ldr/str. This is why Herb Sutter's atomic<> Weapons talk spends an hour on "distinction between what you asked for and what you paid for": a seq_cst atomic increment is a lock xadd on x86-64 and a loop of ldaxr/stlxr on ARM64 — an order of magnitude more expensive than the plain add a non-atomic ++ becomes. Measure on your target ISA, not on folklore.

Keystoneatomicity and ordering are separate purchases. Every order gives you no-tearing; only acquire/release/acq_rel/seq_cst give you happens-before edges. relaxed is "just indivisible".
Anti-patternAssuming atomic<MyStruct> is lock-free because it compiles. Past the platform's lock-free width you get a hidden mutex: blocking ops, no signal safety, possible deadlock. Check is_always_lock_free.

Retrieve it

Why does compare_exchange_weak exist if it can fail spuriously?

Because on LL/SC architectures a strong CAS is just a weak CAS in a loop, so the loop you'd write anyway can use weak and save code size.

A one-shot CAS that must not fail spuriously needs strong; the loop idiom absorbs spurious failures for free.

Why is a release order illegal on load()?

Release orders earlier accesses against a write being published; a load publishes nothing, so the semantic is empty.

The type system encodes it: load() only accepts orders meaningful for reads (seq_cst, acquire, relaxed).

On x86-64, which operation is dramatically more expensive: relaxed load or seq_cst store?

The seq_cst store — it must drain the store buffer (xchg or mfence); the relaxed load is a plain mov.

x86-64's TSO already gives acquire loads and release stores for free; only total order across threads costs.

Prove it to yourself

Try it — 10 minutes

Paste into godbolt.org (clang, -O2):

#include <atomic>
std::atomic<int> x;
void sc_store()  { x.store(1, std::memory_order_seq_cst); }
void rel_store() { x.store(1, std::memory_order_release); }
int  acq_load()  { return x.load(std::memory_order_acquire); }
int  rx_load()   { return x.load(std::memory_order_relaxed); }

Switch the target between x86_64 and aarch64 and diff: count the xchg/mfence on x86-64 for sc_store, and the ldar/stlr vs ldr distinction on aarch64. Then change x to plain int and watch everything collapse to single mov/add instructions.

Why this matters for the mission

Every memory order is a price/performance contract with the compiler. Knowing which instructions each order buys on your ISA is what lets you read generated code — and generated code, unlike prose, never lies.
