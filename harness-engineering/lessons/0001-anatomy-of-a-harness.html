Anatomy of a Harness

An agent product is not "a model". It is a program you own — assembled context, a tool surface, a loop, and guardrails — wrapped around a fixed model. Learn the five parts and you can engineer any of them.

You use harnesses every day: Claude Code, ZCode, Cursor, a support bot. When one behaves badly — loops forever, ignores your instructions, calls the wrong tool — the fix is almost never "get a better model". The fix is in the scaffolding. Anthropic's Building effective agents makes the point bluntly: agents are simply models using tools in a loop, and most use cases call for simpler, composable patterns — not more magic.

Decompose any harness and you find the same five parts:

  • Model — the fixed LLM at the center. You don't engineer this.
  • Assembled context — system prompt, tool definitions, files, history: everything in the context window at call time.
  • Tool surface — the functions the model may call, their schemas, descriptions, and permissions.
  • Loop — the code that runs turns: model call → tool call → observation → repeat, until a stop condition.
  • Guardrails — permissions, hooks, sandboxes, output checks: deterministic code that constrains what the model's decisions can actually do.

One request, traced through the loop

Take "fix the failing test in parser_test.py" in a Claude Code-style harness:

  1. User message arrives. The harness starts assembling context: system prompt, CLAUDE.md/AGENTS.md instructions, tool definitions.
  2. Context assembly — the harness decides what else goes in: file listings, earlier conversation, relevant file contents.
  3. Model call — the assembled messages go to the model. It responds with text and/or a tool call, e.g. Read("parser_test.py").
  4. Tool execution — the harness, not the model, runs the tool (a guardrail may veto it first). The result becomes an observation.
  5. Repeat — observation is appended; the model is called again. Read → edit → run tests → read output…
  6. Stop — the model produces a final answer with no tool call, or the harness hits a limit (turn cap, budget, interrupt).
while True:
    context = assemble(system_prompt, instructions, tools, history)
    msg = model(context)                 # the only "intelligent" step
    if not msg.tool_calls:
        return msg.text                  # stop condition
    for call in msg.tool_calls:
        if not permitted(call):          # guardrail
            observation = deny(call)
        else:
            observation = run(call)      # harness executes, not model
        history.append(call, observation)

Everything except the model() line is ordinary code — versionable, testable, debuggable code that you own.

Keystone The model is fixed; everything you engineer is around it. Context, tools, loop, and guardrails are your levers. When behavior disappoints, diagnose which of the five parts is failing before blaming the model.
Anti-pattern Treating the harness as "the model's magic". If you can't say where your instructions enter the context, which tools exist, or what stops the loop, you can't fix anything — you can only retry and hope. Vague harnesses also breed over-building: adding agency where a single prompt or a fixed workflow would do.

Retrieve it

In the core loop, who actually executes a tool call — and why does it matter?

The harness, never the model.

The model only emits a structured request. Execution happens in harness code, which is why guardrails (permissions, hooks) can intercept every call deterministically — the model cannot bypass a veto it never sees past.

What are the two main ways the agent loop terminates?

Model stops, or harness stops it.

Either the model returns a message with no tool call (a natural final answer), or the harness enforces a limit — turn cap, token budget, timeout, or user interrupt. Both are stop conditions you design.

A user says "the agent keeps ignoring my project rules." Which of the five parts do you inspect first?

Assembled context.

Project rules travel via context — a CLAUDE.md/AGENTS.md file, a system prompt section. If the rules are missing, truncated, or buried under competing instructions, the model never reliably "saw" them; no loop or tool change will help.

Prove it to yourself

Try it — 10 minutes, no code Take a harness you use daily (ZCode, Claude Code, Cursor). On paper, enumerate its five parts: 1) which model(s); 2) what gets assembled into context — find the instruction files and system prompt if you can; 3) list its tools; 4) describe its loop and stop conditions; 5) name at least one guardrail. The parts you can't fill in are exactly where your knowledge gaps — and the syllabus — are.
