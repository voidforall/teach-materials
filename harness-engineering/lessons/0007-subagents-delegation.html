Subagents & Delegation

A subagent burns its own context window and hands back only the conclusion. Delegation is a trade: latency and tokens for a clean main thread.

By now your main thread accumulates everything: the system prompt, every tool result, every file read. Somewhere around the tenth tool call, the harness starts to sag — the model re-reads stale output, misses earlier decisions, drifts. The fix is not a bigger window. It's isolation.

A subagent is a fresh agent loop with its own context window, its own tool permissions, and often its own system prompt. The main thread launches it with a prompt; the subagent grinds through whatever reading, searching, or verifying it needs; the main thread receives one thing: the answer.

Context isolation — read wide, return narrow

The core mechanism is asymmetric context flow. The subagent may read 200KB of logs, twenty files, a dozen search results — none of that touches the main thread. What crosses the boundary is only the final message: "the bug is in parser.ts:88, the guard skips empty payloads." A hundred thousand tokens of exploration collapse into thirty tokens of conclusion.

This is why subagents shine for high-volume-read, low-volume-write work: research, codebase exploration, log triage, document review. The read side is where context goes to die; the write side is all the main thread actually needs.

Keystone Delegation trades latency and tokens for a clean context — worth it exactly when the work is high-volume-read, low-volume-write. If the subagent must consume a lot of context to produce a little conclusion, the trade pays. If not, you're paying the overhead for nothing.

Parallel fan-out

The second win is concurrency. Independent searches don't need to run sequentially in one window — launch them as parallel subagents. "Find every call site of processRefund", "summarize the current refund policy doc", "list open bugs mentioning refunds" — three isolated windows, three conclusions, one merged answer. In Claude Code, the Task tool fans out; you get the latency of the slowest branch, not the sum of all three, and the main thread pays only for the three summaries.

The handoff contract

Delegation lives or dies on the boundary. Two rules:

  • Prompt in must be self-contained. The subagent cannot see your conversation. "Check the auth code" fails; "In src/auth/, find where expired tokens are handled and quote the relevant function" works. Include the goal, the scope, and what to return.
  • Summary out, not transcript. Specify the return shape: findings, file paths, a verdict, next steps. An unbounded return dumps the subagent's mess right back into your window.

When NOT to delegate

Delegation is not free: each launch costs tokens, latency, and a full context rebuild. Don't delegate when:

  • The task needs the main thread's accumulated state — the requirements doc, the user's earlier corrections. You'd have to serialize all of it into the prompt, at which point you've rebuilt the main context in a worse place.
  • The task is a cheap lookup — one file read, one grep. Spawning an agent loop for that is like hiring a consultant to pass you a sticky note.
  • The task is stateful back-and-forth — a design discussion with the user, an interactive debug session. Every round-trip re-crosses the boundary and re-pays the overhead.
Anti-pattern Delegating a task that needs the main thread's accumulated state. The subagent returns an answer that ignores the constraint the user stated forty messages ago — or you bloat the handoff prompt trying to replay the whole conversation, and lose the isolation you delegated for in the first place.

One more mechanism worth knowing: resume/continuation. Some harnesses let a finished subagent conversation be continued — fed a follow-up without rebuilding from scratch. That turns a subagent into a durable scratch context you can revisit ("re-check with the new schema"), keeping the main thread clean across multiple consultations.

Retrieve it

Why does log triage make better subagent work than answering a clarifying question from the user?

Read/write volume, and state.

Triage reads a huge volume and returns a small conclusion — the isolation pays for itself. A clarifying question is stateful back-and-forth anchored in the main thread's conversation; every round-trip across the boundary re-pays the launch overhead and risks dropping context.

A subagent prompt says "look into the flaky test." What's wrong with it?

It isn't self-contained.

The subagent can't see your conversation, so it doesn't know which test, what "flaky" means here, or what to return. The handoff contract needs goal, scope, and the expected return shape — file paths, verdict, or next steps.

Three independent research questions, run in one main thread versus three parallel subagents. What exactly do you gain and lose?

Cleaner context and lower latency, for more tokens.

Fan-out means each question burns its own window — the main thread sees only three conclusions. Latency becomes the slowest branch instead of the sum. The cost is total tokens: three fresh loops each re-pay the system prompt and launch overhead.

Prove it to yourself

Try it — split a research task, 15 minutes

Take a multi-part research task you actually have (e.g. "compare how three frameworks handle retries"). Split it into parallel subagent prompts. For each, write:

  1. A self-contained prompt: goal, scope, constraints, and the exact return format ("a table of framework × retry feature, with doc URLs").
  2. The return shape the main thread will merge.

Then run them (Task tool, or your harness's equivalent), and check: did any subagent ask a question it could have answered from a better prompt? That question is a bug in your handoff contract.
