Evals & Iteration — Capstone

Every harness change is a code change. Without an eval suite, you're refactoring in the dark — and "it feels better" is not a measurement.

You've now built every layer: prompts, context, tools, loops, skills, hooks, subagents. Here's the uncomfortable truth about all of it: harness changes are code changes. Tightening a tool description can break a case that used to pass. A new hook can reject an edit that used to succeed. If you wouldn't refactor an API without regression tests, you can't rework a harness without evals.

Keystone You cannot steer what you cannot measure — the eval suite is the harness's harness. Prompts steer the model; evals steer your editing of the prompts. Without them, every "improvement" is an untested hypothesis.

Anatomy of an eval

Every eval has three parts:

  • Input — the scenario: user message, fake file tree, seeded error, a realistic task from your actual usage.
  • Task — what the harness should do: call the right tool, refuse, produce output matching a contract.
  • Grader — the check. Two families:
    • Code-graded: deterministic assertions. "Did it call read_file exactly once?" "Is the output valid JSON?" "Did the hook block git push?" Cheap, fast, unambiguous — prefer it whenever the property is mechanical.
    • Model-graded: a grader model judges a fuzzy property against a rubric. "Does the reply actually address the user's constraint?" Necessary for quality, but noisy — write the rubric like a tool description, with concrete pass examples.

Small scenario suites over one big benchmark

A public benchmark score won't tell you whether your harness regressed. What will: ten to thirty small scenarios lifted from your real failures — the exact prompt that made the loop spin, the tool call your hook should have blocked, the task where the skill failed to trigger. Each one is a regression test pinned to a real incident. When a suite of 15 catches a break that "it feels better" missed, you'll never go back.

A/B the change and measure

The iteration loop is boring on purpose:

  1. Change one variable — one prompt edit, one tool, one hook. Never a batch; batches make attribution impossible.
  2. Run the suite on old and new (an A/B across the change).
  3. Keep or revert — strictly by the numbers. If pass rate holds and a specific case degrades, that case joins the suite permanently.

This is just red-green-refactor, relocated from code to harness. The suite grows one scenario per real failure; each scenario is a fossil of something that once went wrong and can now never silently return.

Retrieve it

"The tool descriptions are clearer now, so the agent should pick tools more accurately." Why is this not a shippable claim?

It's an unmeasured feeling.

"Clearer" is your impression of the input, not a measurement of behavior. Run the scenario suite on old and new: if tool-selection accuracy on your cases didn't move, the change didn't help — regardless of how the prompt reads.

Choosing between a code-graded and a model-graded check — what's the decision rule?

Code-grade whenever the property is mechanical.

If a program can check it — tool called or not, output parses, hook fired — code-grade it: cheap, fast, unambiguous. Reserve model-graders for genuinely fuzzy properties like "does the answer respect the constraint", and pin them with a concrete rubric.

You ship a prompt tweak plus a new hook at once; three suite cases break. Why can't you act on this result?

Two variables, no attribution.

Either change could own each failure — the tweak may have shifted behavior, or the hook may be over-blocking. Re-run each change alone against the suite; keep the ones that pass independently, then combine.

Capstone — engineer one real harness

Capstone — one harness you actually use, ~1 hour

Pick a real harness you live in — Claude Code, ZCode, a custom agent, even this course's agent. Improve it end to end:

  1. One tool or skill improvement. Find the tool that misbehaves or the skill that triggers badly. Fix it with this course's doctrine: tighter schema, better description, progressive disclosure.
  2. One hook. Add a deterministic guardrail on a tool event — block a destructive command, enforce a format on save, log every shell call.
  3. A 5-case eval that would catch a regression in your change. Five scenarios from real usage; grade mechanically where possible; include at least one case that failed before your fix.

Then run the loop once more: change one thing, eval, keep or revert. You're not doing course exercises anymore — you're doing harness engineering.
