Permissions & Hooks

The model proposes; the harness disposes. Anything that must happen — or must never happen — belongs in deterministic code, not in polite requests.

An agent with tool access can read, write, and run anything you can. The model is brilliant but probabilistic; your repo's safety cannot be. The harness answers with two mechanisms: permissions, which decide whether an action runs, and hooks, deterministic code that runs around tool events no matter what the model intended.

The trust boundary

Every tool call crosses a line: on one side the model's intention, on the other the harness's execution. The model proposes — "run git push --force" — and the harness disposes, applying rules the model never sees and cannot negotiate with. This separation is the whole game: policy lives outside the context window, so it can't be forgotten, diluted, or talked around.

Permission modes and matchers

Permissions are matchers plus modes. A matcher pattern selects a set of tool calls (by tool name, by command prefix, by file path); a mode says what happens to a match:

  • ask — pause and surface the call to a human. The default for anything with side effects.
  • allow — run without asking. Reserve for calls you've judged safe, like reading within the workspace.
  • deny — refuse outright, before execution. For calls that are simply never right in this project.

One rule spans it all: approval in one context doesn't extend to the next. "Yes, you may push this branch" does not mean yes to force-push, to other branches, or to tomorrow's session. Grant the narrowest matcher that covers the actual work.

Hooks: deterministic code on tool events

Where permissions answer yes/no, hooks run your code at fixed points — before a tool runs, after it, on session start. A pre-tool hook can block a command, and crucially it can also feed information back. Here's a hook that stops git push and tells the model why:

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command",
        "command": "jq -r '.tool_input.command' | grep -q 'git push' && \
          echo '{\"decision\":\"block\",\"reason\":\"No direct pushes. Open a PR instead.' \
          'Run: gh pr create --draft\"}' || true" }]
    }]
  }
}

Blocking alone just stops the world; blocking with a reason is a steering signal. The model reads the reason and reroutes — this is the feedback loop from the tool-design lesson, applied to guardrails. Good hooks act like good error messages: they point at the right next action.

Beyond hooks, sandboxing removes the choice entirely: run the agent's shell with no network and a filesystem jail, and "dangerous" commands fail because the environment can't satisfy them, not because anyone remembered to block them. Belt, suspenders, and a locked room.

Keystone Guardrails belong in the harness, not in the prompt — prompts advise, hooks enforce. A prompt instruction is a suggestion with a failure rate; a hook is code with none. Everything safety-critical goes where the model can't talk its way past it.
Anti-pattern Trying to prompt the model into never running a dangerous command. "Never run git push --force" works right up until context grows long, attention drifts, or a plausible-sounding task makes an exception seem reasonable. The prompt is the wrong layer: instructions degrade; matchers and hooks don't.

Retrieve it

Why put policy in the harness rather than the system prompt?

The harness can't be talked around.

A rule in the prompt is context — it can be forgotten, diluted by long sessions, or outweighed by other instructions. A rule in the harness executes identically every time, outside the model's reach, so it holds exactly when the prompt would fail.

You approved one git push an hour ago. The model pushes again. What's the correct design?

It should ask again.

Approval in one context doesn't extend to the next: a yes to one push is not a yes to pushes in general. If you want standing consent, grant it explicitly as a narrow allow rule — never by letting one approval leak forward.

What can a blocking hook do that a plain denial cannot?

Explain and redirect.

A denial ends the action; a hook's reason field becomes context the model reads. "Blocked — use gh pr create instead" turns a dead end into a correct next step, closing the loop between guardrail and behavior.

Prove it to yourself

Try it — sketch one hook, 10 minutes

Name the one command you'd genuinely fear an agent running on your machine — rm -rf in the wrong place, drop database, a force-push, an npm publish. Sketch the config for it: which event (PreToolUse), which matcher, and — the part everyone skips — the reason string that tells the model what to do instead. Then check: does your reason name a concrete alternative command?
