Skills & Progressive Disclosure

Context is a budget. A skill is a folder of instructions that costs almost nothing — until the moment it's needed, when it costs exactly as much as the task requires.

Your system prompt is a fixed cost: every token in it is paid on every turn, whether or not it's relevant. A skill inverts that economics. It is a folder with a SKILL.md — YAML frontmatter plus a Markdown body, optionally with bundled reference files and scripts — that the harness loads in three stages.

The three load levels

  • Level 1 — always: the skill's name and description ride in context permanently. A few dozen tokens each. This is the index the model decides with.
  • Level 2 — on invoke: when the model judges the skill relevant, it reads the full SKILL.md body into context. Now the instructions exist — only for this conversation.
  • Level 3 — on demand: bulky assets bundled with the skill — a spec PDF, a cheatsheet, a Python script — are read or executed only when the body tells the model to. They may never load at all.

Compare with the naive alternative: paste the whole procedure into the system prompt and pay for it always, in every session, on every task. Progressive disclosure means the harness pays for knowledge lazily, at the moment of use.

Keystone A skill is a context valve — closed by default, opened by need. The description is the valve handle: it must let the model recognize "now" precisely, both when to open the skill and when to leave it shut.

What becomes a skill?

The unit-of-work decision. Heuristics that hold up well:

  • Skill: a repeatable workflow with steps the model can't guess — release checklists, migration procedures, house style for this repo. Enough recurring shape to justify an index entry.
  • Doc (referenced, not always loaded): reference material the model should fetch when asked — an API reference, a glossary. It needs no trigger logic, only a pointer.
  • Tool: anything with a crisp input/output contract the model shouldn't improvise. If it's an action, not knowledge, it wants a schema, not prose.

Writing descriptions that trigger reliably

The description is doing retrieval over your whole workflow, with a model as the matcher. Make its job easy:

  • State the trigger phrases. "Use when the user says X, Y, or asks for Z" beats any abstract summary. A real example, from a skill on this very machine: "Teach the user a new skill or concept, within this workspace." — one line, and the model can match "teach me…", "explain…", "walk me through…".
  • Say when NOT to use it. Negative space prevents false triggers: "Do not use for one-off questions; only for multi-session learning."
  • Keep it specific enough to be wrong. A description that could match anything matches nothing reliably. Vagueness is the enemy of Level 1.
Anti-pattern Stuffing everything into the system prompt. A prompt carrying ten procedures pays for all ten on every turn, dilutes attention on the one that matters, and still can't hold the bulky references. If a procedure has a trigger condition, it is a skill — gated behind its description, not taxed on every conversation.

Retrieve it

What lives in context at Level 1, and what does it cost?

Name and description only.

The index entry — a few dozen tokens per skill, permanently resident. The body and every bundled asset stay on disk until invoked or demanded, so a skill you never use costs its description and nothing more.

You have a 40-page API reference the model needs occasionally. Skill, doc, or tool?

A referenced doc.

It's knowledge, not action, and it has no multi-step procedure — so not a tool and not a skill body. Put it somewhere findable, keep a pointer to it in context, and let the model read it only when a task touches that API.

A skill triggers constantly, including on tasks it shouldn't. What do you fix first?

The description's boundaries.

Level 1 matching is entirely driven by the description. Add explicit "when NOT to use" clauses and name the specific trigger phrases — false positives mean the valve handle is too vague, not that the body is wrong.

Prove it to yourself

Try it — draft a SKILL.md, 10 minutes

Pick a workflow you repeat weekly (a release checklist, a weekly report, a code-review ritual). Draft its frontmatter — nothing else:

---
name: release-checklist
description: Run the release process for this repo. Use when the user
  says "cut a release", "ship v...", or asks to publish. Do not use for
  feature work or dependency bumps.
---

Test the description like a retrieval query: read it aloud against three real requests, one that should trigger and two that shouldn't. If you can't tell which is which, neither can the model.
