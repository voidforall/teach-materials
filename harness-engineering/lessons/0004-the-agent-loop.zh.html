智能体循环

每个智能体（agent）底下都是一个 while 循环：行动、观察、反思，如此往复。工程要点不在于循环本身 —— 而在于决定它何时停止、运行时说什么。

剥掉聊天界面和工具协议，一个智能体小得令人尴尬：一个循环，把模型自己的近期工具结果喂回去，问它"下一步？"，直到某个东西喊停。你体验到的所有"智能体替你干活"都是这个循环加上设计良好的工具。而你体验到的所有"失控的智能体"，都是这个循环减去设计好的停止条件。

诚实地画出这个循环

while true:
    response = model(system_prompt, messages, tools)

    if response.has_tool_calls:          # 行动 ACT
        for call in response.tool_calls:
            messages.append(run(call))   # 观察 OBSERVE
        if not within_budget(): stop("budget exhausted")
        if error_rate > threshold: stop("too many failures")
        continue                          # 反思 REFLECT 在下一轮发生

    if response.done: stop("task complete")
    if response.asks_user: stop("input needed")
    stop("no tool calls and not done — end turn")

每轮迭代三个动作。行动：模型发出工具调用。观察：harness 执行调用，把真实结果追加进消息列表 —— 这是模型了解世界的唯一途径。反思：在下一轮，模型读到这些结果并决定：再来一次工具调用、向用户提问，还是给出最终答案。

关键点 没有设计好停止条件的智能体，就是一个绑了信用卡的 while(true)。循环会停，是因为你逐一枚举了它允许停下的方式：任务完成、预算耗尽、需要用户输入、错误阈值触发。要么有意地设计它们，要么模型会意外地即兴发挥。

停止条件才是产品

"任务完成"是人人都记得的条件；另外几个才是救你命的条件。预算：对迭代数、token 数或运行时长设上限，让困惑的模型停下来，而不是磨穿你的额度。错误：如果最近 N 次工具调用全部失败，就停下并暴露失败 —— 永远重试一个坏掉的调用不叫坚持，叫循环 bug。歧义：关键信息缺失时，结束本轮去问用户是一个停止条件，不是失败。

规划模式 vs 行动模式

同一个循环可以被系统提示词拨到不同的挡位。规划模式（plan mode）要求模型先提出计划、等批准后才能运行任何改变状态的工具。待办机制（如 Claude Code 里的 TodoWrite）把计划外化到上下文中，让每一轮迭代都能对照清单检查进度，而不是从越来越长的对话记录里重新推导意图。规划不是另一套架构 —— 它就是加了一句"第一次行动之前先想清楚"的指令、外加一块供反思的草稿纸的循环。

叙述的详略也是转向

循环的"自述"是一个系统提示词面。"每次工具调用前给一行进展说明，任务完成或受阻时给一段简短总结"能造出一个人类可以监督 —— 并且能尽早打断 —— 的智能体。一个到第 40 轮才开口的智能体是个黑箱，它发现自身错误时已经太晚。

工作流 vs 智能体

按 Anthropic 的表述：工作流（workflow）是一张固定的图 —— 代码沿着预定义的步骤编排模型，控制流住在你的代码里。智能体（agent）是模型驱动的 —— 由循环中的模型自己决定下一步，控制流住在上下文里。工作流可预测、易调试，应当是你的默认选择；智能体为开放式任务买到灵活性，代价是不可预测。对每个用例问一句：需要模型来选步骤吗，还是步骤我本来就清楚？

反面模式 工作流就够，却硬上智能体。如果步骤事先已知 —— 先摘要、再分类、再格式化 —— 就直接写死。在确定性流水线上套智能体，等于凭空增加一个每步都要评估、调试、限额的决策点，却什么都没换回来。

检索一下

说出每个智能体循环都应该设计好的四个停止条件。

完成、预算、输入、错误。

任务完成（模型自己的终局答案）、预算耗尽（迭代数/token/时间）、需要用户输入（歧义时结束本轮）、错误阈值（连续失败的调用让循环停止）。每一个都对应一种具体的失败模式，让它在你的规则下停下。

循环里某个工具连续六轮报同一个错。什么坏了？harness 该做什么？

错误停止条件坏了。

格式良好的错误信息应该在一两轮内把重试引向修正后的调用（第 3 课）。连续六次同样的失败说明转向失效、错误阈值缺失 —— harness 应当停下并暴露失败，而不是放任循环烧预算。

用一个测试问题区分工作流和智能体。

谁来选步骤。

如果你的代码事先知道步骤顺序，那就是工作流 —— 控制流在你写的图里。如果模型必须根据观察决定下一步，那就是智能体 —— 控制流在上下文里。步骤已知：工作流。开放式：智能体。

亲手验证

任务 — 审计一个你在用的循环

挑一个你每天都在跑的 harness（ZCode、Claude Code 或自研智能体）。找出它的停止条件：迭代数或 token 上限在哪里？连续第五次工具错误会发生什么 —— 重试、停止，还是提问？有没有"先规划再行动"的模式，有没有供反思的草稿纸？把找到的每个停止条件和缺失的每个都写下来。缺失的那些，就是你还没踩到的失败模式。
