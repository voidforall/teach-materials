The Agent Loop

Under every agent is a while-loop: act, observe, reflect, repeat. The engineering is not the loop — it's deciding when it stops, and what it says while it runs.

Strip away the chat UI and the tool protocol, and an agent is embarrassingly small: a loop that feeds the model its own recent tool results and asks "next step?" until something says stop. Everything you experience as intelligence-on-your-behalf is this loop plus well-designed tools. And everything you experience as a runaway agent is this loop minus designed stop conditions.

The loop, honestly rendered

while true:
    response = model(system_prompt, messages, tools)

    if response.has_tool_calls:          # ACT
        for call in response.tool_calls:
            messages.append(run(call))   # OBSERVE
        if not within_budget(): stop("budget exhausted")
        if error_rate > threshold: stop("too many failures")
        continue                          # REFLECT happens next turn

    if response.done: stop("task complete")
    if response.asks_user: stop("input needed")
    stop("no tool calls and not done — end turn")

Three moves per iteration. Act: the model emits tool calls. Observe: the harness executes them and appends real results to the message list — this is the only way the model learns anything about the world. Reflect: on the next turn, the model reads those results and decides: another tool call, a question for the user, or a final answer.

Keystone An agent without designed stop conditions is a while(true) with a credit card. The loop stops because you enumerated the ways it may stop: task done, budget exhausted, user input needed, error threshold hit. Design them on purpose, or the model will improvise them by accident.

Stop conditions are the product

"Task complete" is the condition everyone remembers; the others are the ones that save you. Budget: a cap on iterations, tokens, or wall-clock time, so a confused model grinds to a halt instead of grinding through your quota. Errors: if the last N tool calls all failed, stop and surface the failure — retrying a broken call forever is not persistence, it's a loop bug. Ambiguity: when critical information is missing, ending the turn to ask the user is a stop condition, not a failure.

Planning modes vs acting modes

The same loop can be steered into different gears by the system prompt. A plan mode tells the model to propose a plan and wait for approval before any state-changing tool runs. A todo mechanism (like TodoWrite in Claude Code) externalizes the plan into the context, so each loop iteration can check progress against a list instead of re-deriving intent from a growing transcript. Planning isn't a different architecture — it's the loop with a "think before the first act" instruction and a scratchpad to reflect against.

Verbosity is steering

The loop's narration is a system-prompt surface. "Give a one-line update before each tool call, and a short summary when the task is done or blocked" produces an agent a human can supervise — and interrupts early. An agent that says nothing until turn 40 is a black box that discovers its own mistakes too late.

Workflows vs agents

Anthropic's framing: a workflow is a fixed graph — code orchestrates the model through predefined steps, and control flow lives in your code. An agent is model-driven — the loop's own model decides the next step, and control flow lives in the context. Workflows are predictable, cheap to debug, and should be your default; agents buy flexibility for open-ended tasks and pay for it with unpredictability. Ask for each use case: do I need the model to choose the steps, or do I already know the steps?

Anti-pattern Reaching for an agent when a workflow would do. If the steps are known in advance — summarize, then classify, then format — hard-code them. An agent over a deterministic pipeline adds a per-step decision you must now evaluate, debug, and budget-cap, in exchange for nothing.

Retrieve it

Name the four stop conditions every agent loop should have designed in.

Done, budget, input, errors.

Task complete (the model's own terminal answer), budget exhausted (iterations/tokens/time), user input needed (ambiguity ends the turn), and error threshold (consecutive failed calls halt the loop). Each one exists so a specific failure mode stops on your terms.

A tool in the loop has failed with the same error six turns in a row. What has broken, and what should the harness do?

The error stop condition.

A well-formed error message should steer a retry into a corrected call within a turn or two (Lesson 3). Six identical failures means the steering failed and the error threshold is missing — the harness should halt and surface the failure instead of letting the loop burn budget.

What distinguishes a workflow from an agent, in one test question?

Who chooses the steps.

If your code knows the step sequence in advance, it's a workflow — control flow lives in the graph you wrote. If the model must decide the next step from observations, it's an agent — control flow lives in the context. Known steps: workflow. Open-ended: agent.

Prove it to yourself

Task — audit a loop you use

Take a harness you run daily (ZCode, Claude Code, or an in-house agent). Find its stop conditions: where is the iteration or token cap? What happens on the fifth consecutive tool error — retry, halt, or ask? Is there a mode where it plans before acting, and a scratchpad it reflects against? Write down each stop condition you find and each one that's missing. The missing ones are the failure modes you haven't hit yet.
