Tool Design

A tool is four things: a name, a description, a JSON schema, and a behavior. Three of the four are prompts — and you already know how to write prompts.

To the model, your tool surface is not an API. It is a block of text in the context window that it reads before every single call. A tool definition is a prompt that happens to be shaped like a function signature. Design it like one.

Anatomy of a tool

Every tool — whether it's an MCP tool, a Claude Code tool, or an OpenAI function — carries the same four parts: name (when to reach for it), description (what it does, when not to use it, what the args mean), JSON schema (the shape of valid input), and behavior (what actually runs and comes back). The model only ever sees text: name + description + schema go into the prompt on every turn. The behavior speaks only through its return value.

Keystone Every tool description is a prompt; every error message is a course correction. The description steers when and how the model calls; the error steers how it recovers when the call fails. Both are steering surfaces — write them like prompts, not like documentation.

Descriptions are prompts, not docs

A docstring written for humans ("Retrieves records from the records service") tells the model almost nothing. A description written for a model says what it returns, what the args mean in practice, and shows a concrete example. Compare:

// Bad: docs for humans
name: get_records
description: Retrieves records from the records service.
input: { type: object, properties: { q: { type: "string" } } }

// Fixed: a prompt for a model
name: get_records
description: Searches support tickets. Returns up to 50 matches,
  newest first. Use quotes for exact phrases (q: "\"refund\" delayed").
  Prefer this over list_all_records; it's faster and cheaper.
  Example: q="plan:pro status:open" returns open tickets on the Pro plan.
input: { type: object, properties: {
  q: { type: "string",
       description: "Query string. Supports field:value filters
                     (plan:, status:, org:) and quoted phrases." } },
  required: ["q"] }

The fixed version answers the model's real questions: what comes back, in what order, how do I compose a query, and when should I pick a different tool? Concrete input/output examples in the description are the single highest-leverage edit you can make.

Errors are steering

When a call fails, you get one free turn of the model's attention. Spend it well: say what's wrong and how to fix it. "Date must be YYYY-MM-DD, e.g. 2026-08-23; you sent 'Aug 23'" lets the loop self-correct on the next step. A stack trace does not.

Anti-pattern Returning a stack trace instead of actionable guidance. Error: ValueError at utils/dates.py:88 is a dead end — the model guesses, retries, and burns budget. Error: invalid date 'Aug 23'. Use ISO format YYYY-MM-DD, e.g. 2026-08-23." is a course correction. Every error string is a mini-prompt for the recovery step.

Few tools, sharp edges

Tool definitions ride along in the context on every turn, so the surface itself has a token cost — and a confusion cost: overlapping tools force the model into a fuzzy choice on every step. Ten high-impact tools with crisp boundaries outperform forty overlapping ones. Before adding a tool, ask: can an existing tool plus a better description cover it? If two tools overlap, merge them or sharpen the descriptions until only one can ever be the right answer.

Retrieve it

Why put a concrete example query inside a tool description?

The model imitates examples.

Descriptions are prompts. A worked example (q="plan:pro status:open" → open tickets on the Pro plan) pins down format and filters far better than prose rules — the model pattern-matches the example on its next call.

A tool call fails with a malformed date. What should the error string contain?

What's wrong and the fix.

Name the bad input, state the expected format, and give an example: "invalid date 'Aug 23'; use YYYY-MM-DD, e.g. 2026-08-23." That turns the failure into a one-step self-correction instead of a blind retry.

Your harness has 40 tools and the model keeps picking the wrong one. First move?

Cut and sharpen, don't add.

Overlapping tools force a fuzzy choice every step, and 40 definitions tax the context on every turn. Merge overlapping tools, then rewrite descriptions so each one states when to use it — and when to prefer another tool instead.

Prove it to yourself

Try it — 10 minutes

Find the worst tool description in a harness you use (any MCP server or plugin config will do). Rewrite it: one sentence on what it returns, one on when not to call it, one concrete input example, and a schema field description for the trickiest argument. Then run a task that needs the tool and watch whether the first call is correct — before and after.
