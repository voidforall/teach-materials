权限（Permissions）与钩子（Hooks）

模型提议，harness 裁决。凡是必须发生 —— 或绝不能发生 —— 的事，都该放进确定性的代码里，而不是礼貌的请求里。

一个能调用工具的 agent，可以读、写、运行你能读、写、运行的一切。模型很强，但它是概率性的；而你仓库的安全不能是。harness 用两套机制来应对：权限（permissions）决定一个动作是否执行，钩子（hooks）是在工具事件周围运行的确定性代码 —— 无论模型本意如何，它们都会跑。

信任边界

每次工具调用都跨过一条线：一侧是模型的意图，另一侧是 harness 的执行。模型提议 —— "运行 git push --force" —— harness 裁决，依据的是模型看不见、也无法与之讨价还价的规则。这个分离就是全部要义：策略活在上下文窗口之外，所以不会被遗忘、稀释，也无法被绕开。

权限模式与匹配器

权限 = 匹配器（matcher）+ 模式（mode）。匹配器按工具名、命令前缀或文件路径圈定一组调用；模式决定命中之后发生什么：

  • ask（询问）—— 暂停，把调用交给人类裁决。任何有副作用的操作的默认档。
  • allow（允许）—— 不问直接执行。只留给你已判定安全的调用，比如在工作区内读文件。
  • deny（拒绝）—— 执行之前直接拒绝。用于在这个项目里根本不该出现的调用。

还有一条统领一切的原则：在一个上下文里的批准，不会延续到下一个。"可以，你可以 push 这个分支"不代表可以 force-push、可以 push 其他分支、或者明天那个会话也可以。授权时，匹配器收得越窄越好，刚好罩住眼前的活儿。

钩子：工具事件上的确定性代码

权限回答是与否，而 hooks 运行的是你的代码 —— 在固定的时机：工具执行前、执行后、会话启动时。一个 pre-tool 钩子可以拦下一条命令，而更关键的是它还能回灌信息。下面这个钩子拦下 git push 并告诉模型原因：

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command",
        "command": "jq -r '.tool_input.command' | grep -q 'git push' && \
          echo '{\"decision\":\"block\",\"reason\":\"No direct pushes. Open a PR instead.' \
          'Run: gh pr create --draft\"}' || true" }]
    }]
  }
}

只拦截只是让世界停下；带着原因拦截则是一个转向信号。模型读到 reason 就会改道 —— 这是工具设计那一课的反馈回路，用在了护栏上。好的 hook 像好的报错信息：指向正确的下一步。

在 hooks 之外，沙箱（sandboxing）干脆取消选择：让 agent 的 shell 无网络、锁在文件系统监狱里，"危险"命令失败的原因是环境满足不了它，而不是因为有人记得去拦。腰带、背带，再加一间上锁的房间。

关键点 护栏属于 harness，不属于提示词 —— 提示词是建议，hooks 是执行。写进 prompt 的指令是一条有失败率的建议；一个 hook 是没有失败率的代码。一切安全攸关的东西，都放在模型无法用语言绕过去的地方。
反模式 试图用提示词让模型永远不运行某条危险命令。"绝不要运行 git push --force" 一直有效 —— 直到上下文变长、注意力漂移，或者某个听起来合理的任务让"破例"显得情有可原。prompt 是错误的层级：指令会退化，匹配器和 hooks 不会。

检索一下

为什么把策略放进 harness 而不是系统提示词？

harness 无法被绕过。

写在 prompt 里的规则只是上下文 —— 会被遗忘、被长会话稀释、或被其他指令压过。写在 harness 里的规则每次都原样执行，在模型够不到的地方，于是在 prompt 会失灵的恰好在那一刻，它依然成立。

一小时前你批准过一次 git push。模型又 push 了。正确的设计是什么？

应该再次询问。

在一个上下文里的批准不会延续到下一个：对某一次 push 的"是"，不等于对 push 这件事的"是"。如果你想要长期许可，就明确地立一条窄的 allow 规则 —— 绝不要靠让一次批准向前泄漏。

能拦截的 hook 比单纯的拒绝强在哪？

能解释、能改道。

拒绝只终结这个动作；而 hook 的 reason 字段会变成模型读到的上下文。"已拦截 —— 请改用 gh pr create"把死路变成了正确的下一步，闭合了护栏与行为之间的回路。

亲手验证

试一试 —— 画一个钩子，10 分钟

说出那条你真心害怕 agent 在你机器上运行的命令 —— 在错误位置的 rm -rf、drop database、一次 force-push、一次 npm publish。为它画出配置：哪个事件（PreToolUse）、哪个匹配器，以及人人都跳过的那一步 —— 告诉模型改做什么的 reason 字符串。然后自查：你的 reason 有没有给出一个具体的替代命令？
