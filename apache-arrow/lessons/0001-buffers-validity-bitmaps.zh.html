Buffer 与 validity bitmap（位图）

Arrow 数组不是一张对象图。它是两块字节板 —— 一旦你能直接读懂它们，所有 Arrow API 就都成了视图。

你的任务是在 libarrow 和 pyarrow 之上做开发，同时理解底层机器。所以我们不从某个 API 开始，而是从字节开始。取这个你敲过一千遍的列：

[10, 20, null, 40] (int64)

问一句：它在内存里长什么样？Arrow 的答案是这个课程里其余一切内容的根基 —— SIMD 扫描、zero-copy 切片、IPC，全都在其上。

两块字板的布局

整个数组就这些。在 buffer 之外，Array 对象只携带三个整数：length = 4、null_count = 1、offset = 0。在 C++ 里这就是字面意义上的 arrow::ArrayData 结构体；pyarrow 包装的是同一个东西。

关键点 值住在一块连续的 buffer 里，而"是否为 null"住在一块单独压缩的位图（validity bitmap）里 —— 每个值一个 bit。一个 null 的代价是 1 个 bit 的开销，而不是一个带标签的指针或哨兵值。把"是不是 null"与"值是什么"分开，正是 values buffer 能保持稠密、规整、可 SIMD 扫描的原因。

逐 bit 读位图

位图在每个字节内是 LSB 优先的：槽位 i 的 bit 位于字节 i ÷ 8 的第 i mod 8 位 —— 所以第一个槽位是最低有效位。bit 为 1 = 值存在；bit 为 0 = null。我们的 0b00001101 从右往左读：槽 0 ✓、槽 1 ✓、槽 2 null、槽 3 ✓。与那个列正好对应。

两个值得刻进脑子里的规范细节：

  • 如果 null_count = 0，validity buffer 可以整个省略 —— 隐含一张全 1 位图。
  • values buffer 中 null 槽位上的字节是未指定的垃圾值。永远不要读它们；先查位图。

练一练

解码字节，点出 null 槽位。连对 5 题 —— LSB 优先的方向正是人人都搞反的那一处。

检索一下

一个 100 行、37 个 null 的 int32 数组，它的 validity bitmap 有多少字节？

13 字节。

ceil(100 / 8) = 13。位图的大小取决于长度，从不取决于 null_count —— 37 个 null 和 1 个 null，同样是 13 字节。

位图字节为 0b01000000。哪个槽位是 null —— 它的下标是多少？

槽 1。

只有 bit 1 是 0。bit 按 LSB 优先编号，所以 0b01000000 → 槽 1 为 null，槽 0 和 2–7 都有值。

为什么 Arrow 用位图，而不是在 values buffer 里保留一个 null 哨兵值？

稠密的 buffer 扫得快。

压缩位图的开销约每行 1 bit，并让 values buffer 保持均匀：每个值步长相同、每个类型都完整可表示，向量化 kernel 直接在裸内存上循环，数据通路里不必穿插逐值的 null 检查。

亲手验证

试一试 — pyarrow，5 分钟 
import pyarrow as pa
a = pa.array([10, 20, None, 40], type=pa.int64())
buf = a.buffers()          # [validity, values]
print(buf[0])              # size 是多少？它到底存不存在？
print(a.null_count, a.offset)

b = pa.array([1, 2, 3], type=pa.int64())   # 没有 null...
print(b.buffers()[0])      # ...那 validity buffer 怎么了？
运行之前先预测两个输出。如果第二个 validity buffer 让你意外，回去重读上面的"两个规范细节"。
