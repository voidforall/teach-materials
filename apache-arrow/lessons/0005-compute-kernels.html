The Compute Layer

A kernel is just a pure function from buffers to buffers. Once you see that, "compute" stops being magic and becomes layout arithmetic.

You have the whole memory story. Now: pa.compute.add(a, b) — what actually runs? No rows, no objects, no interpreter. The compute layer is a registry of kernels: compiled, vectorized functions with a uniform shape.

The kernel contract

Three things to extract from that picture:

  • Elementwise kernels are buffer-in, buffer-out. The hot loop is a strided scan of the two value buffers writing a third — three contiguous regions, which is exactly the shape auto-vectorizers and SIMD love. The bitmap layout from Lesson 1 wasn't aesthetics; it created this loop shape.
  • Validity is computed, not stored as an afterthought. Output null = AND of input validities. The kernel writes a fresh output bitmap; a null input slot's garbage value bytes are never read (so they can't leak).
  • Outputs are new buffers. Buffers are immutable (Lesson 3) — every kernel result is a new allocation. Chained expressions allocate per step, which is why Arrow has expression fusion on some paths and why kernels like replace_with_mask exist instead of in-place update.
Keystone Null semantics live in the kernel's type signature, not in your data. add(a, b) propagates null (either null → null); coalesce(a, b) absorbs them (both null → null); min_max skips them by option. Same bitmaps in, different bitmap logic out — the propagation rule is part of the kernel, listed in the function docs.

How one kernel serves every type

Under pa.compute.add sit dozens of registered kernel implementations — one per type combination: int8+int8, int64+int64, timestamp+duration, …. Dispatch happens in two steps. Name lookup finds the ScalarFunction in the registry; then its kernel signatures are matched against your argument types (with implicit promotion — e.g. int32 + int64 → int64). The matched kernel's loop runs over your buffers. This is plain function-table dispatch, per call — no JIT, no specialization on your data. (Contrast: DataFusion/DuckDB build on top and add their own planning; Arrow compute itself stays a vector library.)

The function registry sorts into four families, worth knowing by name:

  • Scalar functions — elementwise, output length = input length (add, equal, utf8_upper).
  • Vector functions — shape-changing (filter, take: the copy-makers from Lesson 3).
  • Scalar aggregates — many rows → one value (sum, min_max).
  • Hash aggregates — group → aggregate (hash_sum), the engine building-block.

And one plumbing rule that surprises people: kernels take arrays, so a ChunkedArray input gets its kernels run per chunk and re-assembled (or combine_chunks'd first — Lesson 3's copy). Everything you learned about chunking is compute-layer relevant.

Drill it

Validity propagation until it's reflex: given the input bitmaps and the kernel's null rule, mark the output nulls. Streak of 6.

Retrieve it

Why does the output of add(a, b) have nulls exactly where a or b does?

Bitmap AND rule.

The kernel's signature defines elementwise null propagation: output valid = a-valid AND b-valid. That's literally a bitwise AND of the two validity bitmaps — 64 rows per instruction.

Input a lacks a validity buffer (no nulls). What must the elementwise kernel do?

Treat as all-ones.

Lesson 1's omittable-buffer rule surfaces in every kernel: an absent bitmap is implied all-valid. Kernels branch on buffer presence — that's why the layout allows omission: it's a real fast path, not just space savings.

Why can't Arrow compute update a column in place?

Buffers stay immutable.

Sharing (Lesson 3) is only safe because buffers never mutate — a slice or mmap view could be watching. So kernels allocate fresh outputs; "in-place" APIs like replace_with_mask still produce new buffers under the hood.

filter and add are both kernels. What's the structural difference?

Output length differs.

add is a scalar (elementwise) function — output slot i from input slot i, length preserved. filter is a vector function — a variable number of rows survive, so the result can't be a window over the input (hence Lesson 3: it copies).

Prove it to yourself

Try it — pyarrow, 10 minutes 
import pyarrow as pa, pyarrow.compute as pc

a = pa.array([10, 20, None, 40])
b = pa.array([2, 5, 99, 4])

out = pc.add(a, b)
print(out)                                   # where are the nulls?
print(out.buffers()[0])                      # ...and is the bitmap what AND predicts?

# null semantics are per-kernel:
print(pc.coalesce(a, b))                     # absorbs the null
print(pc.min_max(a))                         # skips it
print(pc.sum(a))                             # and the scalar aggregate?

# dispatch: peek at what one name holds
f = pc.get_function("add")
print(len(f.kernels), "kernel variants")     # int8+int8 ... timestamp+duration ...

# and the chunk plumbing:
chunked = pa.chunked_array([[1, 2], [3, None]])
print(pc.add(chunked, chunked))              # per-chunk? null preserved?
Cross-check the add output bitmap against your own a_valid & b_valid by hand — you now know enough to audit a compute kernel's validity handling.
