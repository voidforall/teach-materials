Arrow Flight

Lesson 4's stream format, wrapped in a gRPC envelope, with seven verbs for finding and moving data.

Everything so far has been in-process or on-disk. Arrow Flight is the network chapter: a standard RPC protocol for serving Arrow data. The point isn't novelty — it's that the wire format is already the memory format, so the traditional serialize/parse tax of data-over-network just… doesn't apply.

The envelope

■ metadata  ■ body  ■ transport

Honest caveat, because you care about mechanisms: gRPC is a protobuf-based protocol, and protobuf message assembly copies into its send buffers. Flight is "zero-copy" in the sense that no conversion of the data's representation ever happens — the body bytes go on the wire as-is and are wrapped as Buffers on receipt — but the gRPC layer does memcpy on both ends. Compare: any JSON/Avro path pays representation conversion on every row; Flight pays a bulk memcpy per message. Also inherited from gRPC: the default ~4 MB message limit — servers must chunk into multiple FlightData messages, which is why writers expose a max_chunksize.

Keystone Flight's model is: advertise data by descriptor, fetch it by ticket, stream it as IPC. GetFlightInfo(descriptor) returns schema + endpoints; each endpoint carries an opaque ticket; DoGet(ticket) streams the Arrow record batches. The ticket is deliberately opaque bytes — your query plan, partition ID, page token — so Flight the protocol never parses your intent.

The seven verbs

  • Handshake — optional auth preamble (token exchange).
  • ListFlights — catalog: what descriptors exist.
  • GetFlightInfo — plan a read: schema, endpoints+tickets, total rows/bytes. GetSchema — the cheap schema-only variant.
  • DoGet — server→client data stream (the common read).
  • DoPut — client→server upload; server acks per stream.
  • DoExchange — bidirectional; the substrate Flight SQL runs on.

And the Lesson 6 connection: dictionaries ride the stream as dictionary messages before the batches — a Flight reader must track replace/delta dictionaries per stream, or batches arrive with indices pointing at nothing. The layout subtlety became a protocol state machine.

Retrieve it

Why does Flight avoid the per-row serialization tax of JSON/Avro services?

Body bytes pass through.

The data_body field carries the Arrow buffers verbatim — the same representation on wire, on disk, and in RAM. No row-level conversion; the only cost is gRPC's bulk memcpy into/out of the HTTP/2 stream.

What's in a ticket, and who decides?

Opaque server bytes.

The ticket is whatever the issuing server wants — query handle, partition number, continuation token. Flight never parses it; it's the correlation between GetFlightInfo's advertisement and DoGet's stream.

Your Flight upload fails with "received message larger than max". Why?

gRPC's 4 MB default.

FlightData rides in gRPC messages, which cap at ~4 MB by default. Fix on the write side: smaller max_chunksize so each batch is its own message (streaming sidesteps the limit), or raise the gRPC cap on both ends.

Why must a Flight reader track dictionary state across a stream?

Indices need payloads.

Dictionary messages precede batches (Lesson 6). A replace message invalidates prior indices; a delta appends. A reader that ignores them will decode batches with indices into a stale or missing payload.

Prove it to yourself

Try it — pyarrow, 15 minutes 
import pyarrow as pa
import pyarrow.flight as fl

class Demo(fl.FlightServerBase):
    def list_flights(self, ctx, crit):
        info = fl.FlightInfo(
            pa.schema([("n", pa.int64())]),
            fl.Descriptor.for_path("demo"),
            [fl.Ticket(b"page-1")], total_records=3, total_bytes=24)
        yield info
    def do_get(self, ctx, ticket):
        table = pa.table({"n": [1, 2, 3]})
        return fl.RecordBatchStream(table)

with Demo("grpc://localhost:8815"):
    client = fl.connect("grpc://localhost:8815")
    for f in client.list_flights(): print(f.schema, f.endpoints[0].ticket)
    reader = client.do_get(fl.Ticket(b"page-1"))
    print(reader.read_all())
A complete advertise→fetch loop in ~20 lines. Then break it on purpose: try reader.read_chunk() and inspect the message types — you'll see Schema, then RecordBatch messages, the Lesson 4 stream arriving over gRPC.
