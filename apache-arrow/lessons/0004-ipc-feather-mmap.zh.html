IPC、Feather 与 mmap

Arrow 的序列化不转换数据 —— 只是在数据前面加上说明书。全部奥妙就在这里。

第 3 课结尾留了个悬念：buffer 不过是一堆字节，那要是根本不用重写它们呢？本课就把这个想法落到物理层面 —— IPC 协议和 Arrow 文件格式（Feather V2）。学完你就明白为什么一个 40 GB 的文件可以"瞬间加载"。

封装：metadata + body

一条 IPC 消息分两部分。先是 metadata 块 —— 一段序列化的 Flatbuffer，说的是"这是一条 schema 为 S 的 RecordBatch，含 N 个 buffer，位于这些（offset, length）对上，共这么多行"。然后是 body：buffer 本身，按它们在内存中的原样排布（第 1–2 课的布局），8 字节对齐。metadata 里不含数据 —— 它是一份 buffer 清单（manifest）：标记每个 buffer 在 body 块内的起点。

关键点 body 是对活跃 buffer 的一次 memcpy；metadata 是指向它的一份 manifest。没有逐行序列化，也不需要把值解析回对象。反序列化 = 读 manifest，把 body 区域包装成 Buffer 视图。如果 body 来自 mmap，这些视图直接指向 page cache —— 文件就是内存。这就是 Arrow IPC 能跑 GB/s、而 JSON/protobuf 这类行式格式只能爬行的原因。

两种容器

■ metadata（Flatbuffer）  ■ body（原始 buffer）  ■ footer  ■ magic bytes

同样的消息，两种塑形。stream 是只追加的：帧到达就读，无需寻址 —— 正适合 socket（也适合 Arrow Flight，第 7 课的地盘）。file 则加了一个 footer：一个 Flatbuffer，按 offset 索引每个 schema/dictionary/batch 块，并且在头尾各放 ARROW1 magic bytes（两端都检查，以便发现被截断的文件）。有 footer ⇒ 随机访问：open_file(...).read_batch(417) 直接定位到第 417 个 batch，完全不碰其余 5000 个。

几个要紧的规范细节：每个块都带长度前缀且 8 字节对齐（推荐 64，让 buffer 正好落在缓存行上）；一条 RecordBatch 的 buffer 按 manifest 顺序出现 —— 对第 2 课的字符串数组就是：validity、offsets、data —— 但是被省略的 buffer（全默认的 validity，还记得吗？）会编码成长度为零的条目，所以即便 buffer 缺席，manifest 里也永远为每个 buffer 留了位置。

mmap：回报时刻

用内存映射源打开文件（pa.memory_map → pa.ipc.open_file）："读取"返回的数组，其 buffer 就是指向映射的视图。不拷贝、不解析 —— kernel 碰到哪些页，OS 才懒加载哪些页。由此可以推导（而不是死记）以下结论：

  • "打开"一个 40 GB 的文件是瞬间的；实际付出的 I/O 只按真正触碰的页计算 —— 一个只读十列中一列的过滤器只碰大约 1/10。
  • 数组会钉住映射，正如第 3 课的 slice 钉住父数组：同一套所有权模型，往上一层。
  • 写操作需要拷贝 —— 被映射的 buffer 是只读的。zero-copy 是读路径上的超能力。

回忆检索

IPC 的 "metadata" 块里装的是什么 —— 数据、schema、还是别的？

一份 buffer manifest。

一个 Flatbuffer，包含 schema 引用、行数，以及每个 buffer 指向后续 body 的 (offset, length)。值从不出现在 metadata 里 —— 它们已经是 body 中的字节。

为什么文件格式支持 read_batch(417)，而 stream 格式不行？

footer 提供索引。

文件的 footer 记录了每个块的 offset，读方因此可以寻址。stream 是管道上只追加的帧 —— 随机访问不可能，只能按顺序读 batch。

Arrow 的哪个机制让巨型文件的 mmap "加载"是瞬间的？

buffer 变成视图。

反序列化只是读 manifest、把 body 区域包装成 Buffer 视图 —— 用 mmap 时这些区域就是 page cache。懒分页意味着你只为真正触碰的页付费。

schema 里可空的列在第 3 个 batch 中没有 null。它的 IPC body 里 validity 是什么样？

一个长度为零的 buffer。

第 1 课讲过：null_count = 0 允许省略 validity buffer。IPC 把它编码成零长度的 manifest 条目 —— 槽位存在，字节不存在。

亲手验证

试一试 — pyarrow，10 分钟 
import pyarrow as pa, pyarrow.ipc as ipc

table = pa.table({"name": ["al", "paris", None, "hi"], "n": [10, 20, None, 40]})
with ipc.new_file("batch.arrow", table.schema) as w:
    w.write_table(table)

blob = open("batch.arrow", "rb").read()
print(blob[:6], blob[-6:])                     # 两端都是 ARROW1？

# 然后是回报 —— 从磁盘 zero-copy：
with pa.memory_map("batch.arrow") as src:
    m = ipc.open_file(src)
    t2 = m.read_all()
    print(t2.combine_chunks().column("n").buffers()[1])  # 只读且来自 mmap？

# 再验证"两种容器"的说法：
with ipc.new_stream(open("batch.arrows", "wb"), table.schema) as w:
    w.write_table(table)
print(len(open("batch.arrows","rb").read()) - len(blob),  # footer+magic 的差值 ≈ 很小
      "extra bytes for the footer")
加餐：hexdump 这个文件（xxd batch.arrow | head -20），找出 Flatbuffer manifest —— 那些可读的片段 —— 与原始 body 块的分界。你看到的正是第 1 课的 buffer 被原样序列化。
