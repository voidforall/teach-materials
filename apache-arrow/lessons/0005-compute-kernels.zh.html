计算层

kernel 不过是一个从 buffer 到 buffer 的纯函数。看清这一点，"compute" 就不再是魔法，而是布局算术。

内存的故事你已经全部掌握。现在的问题是：pa.compute.add(a, b) —— 实际运行的是什么？没有行，没有对象，没有解释器。计算层是一个 kernel 注册表：一批形态统一、经编译和向量化的函数。

kernel 的契约

从这张图里提炼三点：

  • 逐元素 kernel 是 buffer 进、buffer 出。热循环就是对两个值 buffer 做跨步扫描、写入第三个 —— 三块连续区域，正是自动向量化器和 SIMD 最喜欢的形状。第 1 课的 bitmap 布局不是为了好看；它造就了这个循环形状。
  • validity 是算出来的，不是事后补存的。输出为 null = 两个输入 validity 的 AND。kernel 写一个新的输出 bitmap；null 输入槽位的垃圾值字节永远不会被读（所以不会泄漏）。
  • 输出是全新的 buffer。buffer 不可变（第 3 课）—— 每个 kernel 结果都是一次新分配。链式表达式逐步分配，这也是 Arrow 在某些路径上做表达式融合、以及存在 replace_with_mask 这类 kernel 而非原地更新的原因。
关键点 null 语义写在 kernel 的类型签名里，不在你的数据里。add(a, b) 传播 null（任一为 null → null）；coalesce(a, b) 吸收 null（两个都 null 才 null）；min_max 按选项跳过 null。同样的 bitmap 进，不同的 bitmap 逻辑出 —— 传播规则是 kernel 的一部分，列在函数文档里。

一个 kernel 如何服务所有类型

pa.compute.add 底下注册着几十个 kernel 实现 —— 每种类型组合一个：int8+int8、int64+int64、timestamp+duration……分派分两步。名字查找在注册表里找到 ScalarFunction；然后拿你的参数类型去匹配它的 kernel 签名（含隐式提升 —— 如 int32 + int64 → int64）。匹配到的 kernel 的循环跑在你的 buffer 上。这就是普通函数表分派，逐次调用 —— 没有 JIT，也不会针对你的数据做特化。（对比：DataFusion/DuckDB 在其上加了自己的规划层；Arrow compute 本身始终保持一个向量库。)

函数注册表分四族，值得记住名字：

  • Scalar functions —— 逐元素，输出长度 = 输入长度（add、equal、utf8_upper）。
  • Vector functions —— 改变形状（filter、take：第 3 课的拷贝制造者）。
  • Scalar aggregates —— 多行 → 一个值（sum、min_max）。
  • Hash aggregates —— 分组 → 聚合（hash_sum），引擎的积木。

还有一条常让人意外的管道规则：kernel 接收的是数组，所以 ChunkedArray 输入会按 chunk 逐个跑 kernel 再拼回（或者先 combine_chunks —— 第 3 课的那次拷贝）。你学过的一切关于分块的知识在计算层都用得上。

练一练

把 validity 传播练成条件反射：给定输入 bitmap 和 kernel 的 null 规则，标出输出的 null。连胜 6 题。

回忆检索

为什么 add(a, b) 的输出恰好在 a 或 b 为 null 的位置上是 null？

bitmap AND 规则。

kernel 的签名定义了逐元素的 null 传播：输出有效 = a 有效 AND b 有效。这字面上就是两个 validity bitmap 的按位与 —— 每条指令处理 64 行。

输入 a 没有 validity buffer（无 null）。逐元素 kernel 必须怎么做？

视作全 1。

第 1 课"buffer 可省略"规则在每个 kernel 里都会冒头：缺席的 bitmap 隐含全有效。kernel 会按 buffer 是否存在走分支 —— 这正是布局允许省略的原因：它是真实的快路径，不只是省空间。

为什么 Arrow compute 不能原地更新一列？

buffer 保持不可变。

共享（第 3 课）之所以安全，是因为 buffer 从不改变 —— 可能有 slice 或 mmap 视图正看着它。所以 kernel 分配全新输出；replace_with_mask 这类"原地"API 底层仍然产出新 buffer。

filter 和 add 都是 kernel。结构性差别在哪？

输出长度不同。

add 是 scalar（逐元素）函数 —— 输出槽 i 来自输入槽 i，长度不变。filter 是 vector 函数 —— 存活的行数不定，结果无法是输入上的窗口（于是第 3 课：它要拷贝）。

亲手验证

试一试 — pyarrow，10 分钟 
import pyarrow as pa, pyarrow.compute as pc

a = pa.array([10, 20, None, 40])
b = pa.array([2, 5, 99, 4])

out = pc.add(a, b)
print(out)                                   # null 在哪里？
print(out.buffers()[0])                      # ……bitmap 是否如 AND 所预测？

# null 语义是逐 kernel 的：
print(pc.coalesce(a, b))                     # 吸收 null
print(pc.min_max(a))                         # 跳过 null
print(pc.sum(a))                             # 那标量聚合呢？

# 分派：看一个名字底下装了多少
f = pc.get_function("add")
print(len(f.kernels), "kernel variants")     # int8+int8 ... timestamp+duration ...

# 再看分块管道：
chunked = pa.chunked_array([[1, 2], [3, None]])
print(pc.add(chunked, chunked))              # 逐 chunk？null 保留？
亲手用 a_valid & b_valid 核对 add 的输出 bitmap —— 你现在已有能力审计一个计算 kernel 的 validity 处理。
