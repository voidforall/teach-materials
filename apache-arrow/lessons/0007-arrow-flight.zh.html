Arrow Flight

把第 4 课的流格式装进 gRPC 信封，再配上七个用于发现与搬运数据的动词。

到目前为止，一切都是进程内或磁盘上的事。Arrow Flight 是网络这一章：一个用于对外提供 Arrow 数据的标准 RPC 协议。它的重点不在于新颍，而在于线上格式（wire format）本来就是内存格式，所以「数据上网络就得付序列化/解析税」这条传统规律在这里根本不成立。

信封

■ 元数据  ■ 数据体  ■ 传输层

一个诚实的提醒，因为你在意的是机制：gRPC 是基于 protobuf 的协议，而 protobuf 组装消息时会拷贝到发送缓冲区。说 Flight 是 zero-copy（零拷贝），是指数据表示从不转换——数据体字节原样上线、到达后被包装成 Buffer——但 gRPC 层在两端都各做一次 memcpy。对比一下：任何 JSON/Avro 路径都要每一行都付表示转换的税；Flight 每条消息只付一次批量 memcpy。同样继承自 gRPC 的还有默认约 4 MB 的消息上限——服务器必须把数据切成多条 FlightData 消息，这也正是写入器会暴露 max_chunksize 的原因。

关键点 Flight 的模型是：用 descriptor 广告数据，用 ticket 取回数据，以 IPC 流的形式传输。 GetFlightInfo(descriptor) 返回 schema + 端点；每个端点携带一个不透明的 ticket；DoGet(ticket) 以流的形式返回 Arrow 的 record batch。ticket 刻意设计成不透明字节——它可以是你的查询计划、分区 ID、分页 token——这样 Flight 协议本身永远不会去解析你的意图。

七个动词

  • Handshake — 可选的认证前奏（token 交换）。
  • ListFlights — 目录：有哪些 descriptor。
  • GetFlightInfo — 规划一次读取：schema、端点 + ticket、总行数/字节数。GetSchema — 只取 schema 的廉价变体。
  • DoGet — 服务器→客户端的数据流（最常见的读取方式）。
  • DoPut — 客户端→服务器上传；服务器按流确认。
  • DoExchange — 双向流；Flight SQL 就跑在它上面。

再连回第 6 课：dictionary 会以 dictionary 消息的形式在批次之前随流传输——Flight 读取器必须按流跟踪 replace/delta dictionary，否则批次到达时索引会指向空无一物的地方。布局上的细节在这里升级成了一个协议状态机。

检索

为什么 Flight 能躲开 JSON/Avro 服务那种按行计费的序列化税？

数据体字节直接透传。

data_body 字段原封不动地携带 Arrow buffer——线上、磁盘、内存里是同一种表示。没有行级转换；唯一的代价是 gRPC 把整块数据批量 memcpy 进/出 HTTP/2 流。

ticket 里装的是什么？由谁决定？

服务器自定义的不透明字节。

ticket 的内容完全由签发它的服务器决定——查询句柄、分区号、续传 token 都行。Flight 从不解析它；它只是 GetFlightInfo 的广告与 DoGet 的流之间的关联凭证。

你的 Flight 上传报错 "received message larger than max"。为什么？

gRPC 默认的 4 MB 上限。

FlightData 装在 gRPC 消息里，默认上限约 4 MB。在写入侧修复：调小 max_chunksize，让每个批次各自成一条消息（流式传输可以绕开上限），或者在两端调高 gRPC 上限。

为什么 Flight 读取器必须跨流跟踪 dictionary 状态？

索引需要对应的载荷。

dictionary 消息先于批次到达（第 6 课）。replace 消息会使之前的索引失效；delta 消息做追加。忽略它们的读取器会解出这样的批次：索引指向过期或不存在的载荷。

亲手验证

试一试 — pyarrow，15 分钟 
import pyarrow as pa
import pyarrow.flight as fl

class Demo(fl.FlightServerBase):
    def list_flights(self, ctx, crit):
        info = fl.FlightInfo(
            pa.schema([("n", pa.int64())]),
            fl.Descriptor.for_path("demo"),
            [fl.Ticket(b"page-1")], total_records=3, total_bytes=24)
        yield info
    def do_get(self, ctx, ticket):
        table = pa.table({"n": [1, 2, 3]})
        return fl.RecordBatchStream(table)

with Demo("grpc://localhost:8815"):
    client = fl.connect("grpc://localhost:8815")
    for f in client.list_flights(): print(f.schema, f.endpoints[0].ticket)
    reader = client.do_get(fl.Ticket(b"page-1"))
    print(reader.read_all())
约 20 行就完成了一个完整的「广告→取回」回路。然后故意弄坏它：试试 reader.read_chunk() 并查看消息类型——你会先看到 Schema 消息，再看到 RecordBatch 消息：第 4 课的流正经由 gRPC 到达。
