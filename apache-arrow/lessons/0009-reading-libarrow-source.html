Reading libarrow Source

Eight lessons of theory, one repository. Everything below should read like a letter from an old friend.

This is the graduation exercise: a guided tour through four files in the real Arrow C++ tree, each one hiding in plain sight the machinery you already know. Read on GitHub or clone locally — git clone --depth 1 https://github.com/apache/arrow and live in cpp/src/arrow/.

Stop 1 — the struct you've been using all along

array/data.h → class ArrayData

Find the member list. You will see, nearly verbatim, Lesson 1's sidecar: length, null_count (note: it's kUnknown-able — lazy computation), offset, buffers (a vector of shared_ptr<Buffer> — Lesson 3's refcounting, in the type). Then two members that were foreshadowed but unnamed: child_data (Lesson 2's recursion — a list's child lives here) and dictionary (Lesson 6's out-of-band payload). Six fields; the entire course so far.

Stop 2 — the byte-owners

buffer.h and memory_pool.cc

In Buffer: it's just {data, size, capacity, parent, ...} — a view, not an owner (why slices can be O(1)). Look for the constructor taking a parent buffer: that's Lesson 3's pinning, explicit in the field. In memory_pool.cc: find the 64-byte alignment constant and the bytes_allocated() accounting from Lesson 8, and where jemalloc/mimalloc/system-malloc backends switch.

Stop 3 — a builder, in the flesh

array/builder_base.h and the primitive builder in array/ (builder_primitive.h / type builders); bitmap machinery in util/bit_util.h

Three things to find: the capacity-doubling in Reserve/UnsafeAppendToBitmap paths (Lesson 8's simulator, as code); the BitmapWriter/FirstTimeBitmapWriter in bit_util — the LSB-first writer from Lesson 1; and Finish() calling FinishInternal → ArrayData construction, where scratch is trimmed and transferred. If you read only one function: AppendNull — watch it clear one bit and skip the value slot.

Stop 4 — one kernel, end to end

compute/function.cc (dispatch), compute/exec.h (KernelContext, exec loop), compute/kernels/scalar_arithmetic.cc (the kernel you've called as pc.add)

In function.cc: the Execute path that matches kernel signatures against argument types (Lesson 5's dispatch). In scalar_arithmetic.cc: an ARROW_SCALAR…-style macro table generating one loop per type pair — the "dozens of kernel variants behind one name," generated. In the elementwise exec path: the argument null-check — output validity = AND of inputs, possibly as an actual bitwise AND (bit_util::and_bitmaps) when the compiler can prove all-nulls handling isn't needed per-element. This is Lesson 5's diagram with line numbers.

Keystone libarrow is ~600k lines, but the load-bearing core you just read is six struct fields, one view type, one pool, and one generated loop. The rest is breadth (types, kernels, formats, bindings) composed from those primitives. That's the test of a good architecture — and now the test of your understanding: you navigated it without a guidebook.

Retrieve it

In ArrayData, why can null_count be "unknown"?

Counting is deferred.

Scanning a bitmap to count nulls costs O(n/64); Arrow defers it until someone asks (kUnknown sentinel) — construction and slicing stay O(1). Lazy metadata, same spirit as omitted buffers.

What does a Buffer's parent field exist for?

Slices pin parents.

A slice Buffer holds a shared_ptr to the allocation it views — Lesson 3's "a slice keeps its parent alive," implemented as one field rather than an ownership convention.

Where do the "dozens of kernels behind one name" come from, mechanically?

Macro-generated tables.

scalar_arithmetic.cc uses codegen-style macro expansion to emit one typed loop per type pair and registers each with its signature. Dispatch then just matches signatures — no runtime code generation.
