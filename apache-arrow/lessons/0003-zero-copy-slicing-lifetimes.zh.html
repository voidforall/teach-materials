Zero-copy 切片与 buffer 生命周期

第 1 课里你见过的那个 offset = 0 整数？它是 Arrow 整个所有权模型的冰山一角。

你已经知道布局配方了。本课讲的是数据在视图之间移动时会发生什么 —— 切片、分块、跨语言 —— 以及那个发现：在 Arrow 里数据通常根本不动。

切片什么都不搬

取 a = pa.array([10, 20, 30, 40]) 并切片：b = a[1:3]（值 [20, 30]）。b 拥有什么？什么都没有。还是那两个 buffer，只是数组级的元数据重新指了向：

这就是为什么 Slice()（C++）和 Python 切片在时间和内存上都是 O(1) —— 一张 10 GB 的表切成一千个窗口，一个字节都不分配。这个机制可以组合：a[1:3][1:] 只是叠加 offset；ChunkedArray.slice() 收窄一组 zero-copy 视图；Table.select(['b','a']) 只重排元数据。

一个要从第 1 课带过来的细节：数组级的 offset 会平移一切 —— values 的窗口以及 validity bitmap 的起始 bit。切片的位图并不从 buffer 的 bit 0 开始；bit 运算永远相对 offset 进行。这就是库代码从不裸读 buffer 的原因 —— 它走 accessor。

关键点 Arrow 的共享模型：一次不可变的分配，许多轻量视图。buffer 从不被原地修改 —— 每个"派生"数组都是同一批字节之上的新元数据（offset、length、buffers 列表）。只有当结果不可能是窗口时才会发生拷贝：拼接、gather/take、filter、cast、分块合并。

谁来释放这些字节？

buffer 是引用计数且不可变的 —— 在 C++ 里是由 arrow::MemoryPool 发出的 std::shared_ptr<Buffer>；在 pyarrow 里，Python 的 GC 在 Arrow 的引用之上再持有一份。切片会保住父对象的 buffer；你无法造出一个悬空的 Arrow 视图。值得背下来的生命周期规则：

  • Buffer 比视图活得久：一个 3 元素的切片会钉住整个 10 GB 的分配。释放大块内存有时需要显式丢弃父对象 —— 或者把窗口拷贝出来（combine_chunks()、pa.concat_arrays）以甩掉悬出部分。没错 —— 有时你是故意拷贝来缩身的。
  • Zero-copy 桥梁：当数组是原始类型时，np.asarray(int64_arr) 包装同一个 buffer —— numpy 没有 validity bitmap，所以可空数组或字符串数组必然触发拷贝。C++ 包装外部内存（Buffer::FromWrap 一族，或 mmap）同理：Arrow 引用它没有分配过的字节，通过回调来释放。
  • 分块不是窗口：ChunkedArray只是一个独立数组组成的 Python/C++ 列表。combine_chunks()必须拷贝 —— N 个 buffer 变不成一个。

分个类

对每个操作判断：它是搬字节，还是共享 buffer？刻意混入了第 1–2 课的检索题 —— 交错练习正是意义所在。连对 8 题。

检索一下

你从一张 10 GB 的表里切出 100 行，然后删掉了指向表的变量。内存里还留着什么？

整整十个 GB。

切片持有父对象 buffer 的引用 —— 悬出部分仍然处于已分配状态。只想留住窗口的话，就物化一份拷贝并丢弃父对象。

为什么 pa.concat_arrays 永远不可能是 zero-copy？

两个 buffer，一个结果。

结果必须是单个连续 buffer；两次独立的分配无法靠任何元数据伎俩融合。每个元素都被拷贝。

np.asarray(arrow_arr) 什么时候会拷贝？

可空或嵌套时。

numpy 没有 validity bitmap，也没有变长布局。原始类型、无 null 的数组共享 buffer；其余的都必须转换成 numpy 的表示。

一个字符串数组切成 [:3] —— 那锅数据汤怎么样了？

原封不动，悬在外面。

切片只重指 offsets/元数据；后面那些字符串的字节仍留在 buffer 里、越过窗口末尾，被切片钉着不放。

亲手验证

试一试 — pyarrow，5 分钟 
import pyarrow as pa

a = pa.array([10, 20, 30, 40])
b = a[1:3]
print(a.buffers()[1] is b.buffers()[1])   # 同一个 Buffer 对象吗？

big = pa.array(range(10_000_000))
window = big[9_000_000:]
import sys; print("window len:", len(window))
del big                                    # 猜猜：内存被释放了吗？
# （可以用这个检查：import resource; resource.getrusage(...).ru_maxrss）

c = pa.chunked_array([[1, 2], [3, 4]])
print(c.combine_chunks().buffers())        # 现在只剩一个 values buffer 了 —— 代价是什么？
第 4 行那个恒等判断，就是一个 True 装下的整堂课。

接下来去哪

不可变 buffer 模型还有一个更壮观的推论，也是 Arrow 作为一个项目而不只是一个 C++ 库存在的理由：如果 buffer 只是一堆字节，你就可以不经重写地序列化它们 —— 把 buffer 写进磁盘、mmap 回来，而 mmap 到的字节就是数组。那就是 IPC / Feather 文件格式，第 4 课，zero-copy 从进程内的小知识升级为跨进程的架构。
