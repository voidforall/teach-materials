Builder 与内存池

buffer 是不可变的——那数据究竟是怎么被创建出来的？草稿区、几何增长，以及一次交出所有权的 Finish。

构建篇从第 3 课那条规则最疼的地方开始：任何 buffer 都不会被修改，可数据却是一行一行到达的。ArrayBuilder 家族就是 Arrow 的答案——也是你接下来真正要构建于其上的 C++ 机制。

builder 就是草稿区 + 一次交接

Int64Builder 持有你在第 1 课起就在读的同一种布局——一个 validity 草稿位图和一个值草稿 buffer——只是可变且超额预留。你 append，它增长；Finish() 把草稿封存为不可变的 ArrayData，并把 buffer 转移出去（没有最后一次拷贝——builder 交出自己的分配然后重置）。

arrow::Int64Builder bld(pool);
for (auto v : values) {
  if (v) bld.Append(*v);      // 设置 validity 位 + 写入值
  else    bld.AppendNull();   // 清除该位；值槽位留作垃圾数据
}
auto maybe = bld.Finish();    // 用草稿 buffer 构建出 ArrayData——是转移，不是拷贝

每一节布局课都对应一个 builder：StringBuilder 拥有三块草稿区（位图、offsets、字符串汤），Append("paris") 写下一个 int32 界标（fencepost）外加 5 个字节；ListBuilder 包着一个子 builder，在列表闭合时追加一个界标；StructBuilder 是一捆共享同一个位图的字段 builder。嵌套构造就是递归 append——与第 2 课的递归布局如出一辙。

关键点 builder 做的是摊销：容量翻倍，所以 append 是 O(1) 摊销、全程总共约 2 次元素拷贝——但最后一次翻倍会短暂地占住 2 倍于你数据的空间。 逃生门是分块：每 N 行 Finish() 一次装进 ChunkedArray，内存浪费就永远不超过一个块。翻倍 = 单一 buffer 的速度；分块 = 有界的富余和更早的可用性。Arrow 自家的写入器两者都用（这正是第 7 课的 max_chunksize，往下一层）。

看它增长

一切之下的 MemoryPool

每块草稿分配都来自一个 arrow::MemoryPool（内存池）——第 3 课介绍过的记账层。它为你做三件事：

  • 对齐分配：64 字节对齐（规范只要求 buffer 填充到 8；64 是为了照顾缓存行和 SIMD 加载——第 5 课的循环形态，在源头就得到保护）。
  • 后端选择：默认内存池可以以 jemalloc 或 mimalloc 为后端（Arrow 的构建版本通常捆绑其一），也可以用普通系统 malloc——在链接/初始化时选择。
  • 记账：pool->bytes_allocated() 让你能实时观察 builder 的翻倍过程，也是引擎按查询限额内存的手段（杀死一个查询，而不是整个进程）。

builder 在构造函数里接收内存池；Finish() 转移出去的 buffer 仍引用同一个池，所以释放也经由同一个池发生。自定义分配器也是从这里插入的——在嵌入 Arrow 时，你的构建任务大概率会遇到 MemoryPool::MakeBuilder 一带的地界。

检索

为什么 Finish() 不拷贝数据？

草稿 buffer 是转移的。

builder 的可变草稿分配通过所有权交接变成数组的不可变 buffer；builder 重置为空。不可变性（第 3 课）从 Finish 才开始——草稿区不受约束，因为没有别人能看到它。

翻倍增长 vs 按 1k 分块，各 append 100 万行。比较最坏情况下的内存浪费。

100 万个槽位 vs 约 1 千个。

翻倍会让容量落在长度的 1× 到 2× 之间，最多约 100 万个槽位是富余；最后一次扩容还需要新旧两份同时存活。分块在固定边界收尾——富余从不超过一个块，代价是 ChunkedArray 的簿记开销。

一个含 3 个元素的列表闭合时，ListBuilder.Append() 写下了什么？

一个 int32 界标。

子元素的 append 进的是子 builder；闭合列表时追加下一个 offsets 条目（child_length）——第 2 课的配方，拆给了两个共享时序的 builder。

规范只要求 8 字节对齐，为什么 Arrow 的 buffer 拿到 64 字节对齐？

缓存行与 SIMD。

规范强制 8 字节对齐/可移植性；内存池向上取整到 64，让 buffer 起点落在缓存行边界上，kernel（第 5 课）里的对齐 SIMD 加载就永远不会跨行。

亲手验证

试一试 — pyarrow（底下就是 C++ builder），5 分钟 
import pyarrow as pa

b = pa.array([10, None, 30])        # Python 列表 → C++ ArrayBuilder 路径
print(b.buffers())

# 从 Python 观察翻倍：
import pyarrow.compute as pc
big = pa.array(range(2**20 + 1))    # 某处的某个 builder 构建的——
print(big.nbytes)                   # …但完成的数组是紧凑的：Finish 后没有富余存活

# 对比分块构造（有界富余策略）：
t = pa.table({"n": range(3_000_000)}, schema=pa.schema([("n", pa.int64())]))
t2 = t.combine_chunks()             # N 次 append → 分块 → 最后一次紧凑拷贝
注意第二个代码块展示的细节：富余只活在 builder 内部——完成的 ArrayData 会被裁剪（如有需要，builder 会在 Finish 时拷贝一次）。2× 膨胀是一种构造期现象。
