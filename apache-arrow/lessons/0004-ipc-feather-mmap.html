IPC, Feather & mmap

Arrow serialization doesn't convert data — it prefixes it with instructions. That's the whole trick.

Lesson 3 ended on the cliffhanger: buffers are just bytes, so what if you never rewrote them? This lesson is that idea made physical — the IPC protocol and the Arrow file format (Feather V2). By the end you'll know why a 40 GB file can "load" instantly.

Encapsulation: metadata + body

An IPC message is two parts. First a metadata block — a serialized Flatbuffer saying "this is a RecordBatch of schema S, with N buffers at these (offset, length) pairs, this many rows". Then the body: the buffers themselves, laid out exactly as they live in RAM (Lesson 1–2 layouts), 8-byte aligned. The metadata doesn't contain data — it contains a buffer manifest: where each buffer starts inside the body block.

Keystone The body is a memcpy of live buffers; the metadata is a manifest pointing into it. No per-row serialization, no parsing values back into objects. Deserialize = read the manifest, wrap the body region in Buffer views. If the body came from an mmap, those views point at page cache — the file is the memory. This is why Arrow IPC is GB/s while JSON/protobuf row formats crawl.

Two containers

■ metadata (Flatbuffer)  ■ body (raw buffers)  ■ footer  ■ magic bytes

Same messages, two shapings. The stream is append-only: read frames as they arrive, no seeking — right shape for sockets (and for Arrow Flight, Lesson 7's territory). The file adds a footer: a Flatbuffer indexing each schema/dictionary/batch block by offset, plus ARROW1 magic bytes at head and tail (check both ends to catch truncated files). Footer ⇒ random access: open_file(...).read_batch(417) seeks straight to batch 417 without touching the other 5 000.

Spec details that matter: every block is length-prefixed and 8-byte aligned (64 recommended, so buffers land on cache lines); a RecordBatch's buffers appear in manifest order — for our Lesson 2 string array: validity, offsets, data — but omitted buffers (all-default validity, remember?) are encoded as zero-length entries, so the manifest always has a slot per buffer even when the buffer is absent.

mmap: the payoff

Open a file with a memory-mapped source (pa.memory_map → pa.ipc.open_file): "reading" returns arrays whose buffers are views into the mapping. No copy, no parse — the OS pages data in lazily as kernels touch it. Consequences you can now derive rather than memorize:

  • "Opening" a 40 GB file is instant; you pay I/O per page actually touched — a filter that reads one column of ten touches ~1/10th.
  • The arrays pin the mapping, exactly like Lesson 3's slices pinned parents: same ownership model, one level up.
  • Writes require a copy — mapped buffers are read-only. Zero-copy is a read-path superpower.

Retrieve it

What's inside an IPC "metadata" block — data, schema, or something else?

A buffer manifest.

A Flatbuffer with the schema reference, row count, and each buffer's (offset, length) into the following body. Values never appear in metadata — they're already bytes in the body.

Why can the file format support read_batch(417) but the stream format can't?

The footer indexes.

The file's footer records every block's offset, so readers can seek. A stream is append-only frames on a pipe — random access is impossible; you read batches in order.

Which Arrow mechanism makes mmap "loading" instant for huge files?

Buffers become views.

Deserialization is just reading the manifest and wrapping body regions in Buffer views — with mmap those regions are page cache. Lazy paging means you only pay for pages actually touched.

A nullable-in-schema column has no nulls in batch 3. What's in its IPC body for validity?

A zero-length buffer.

From Lesson 1: null_count = 0 lets the validity buffer be omitted. IPC encodes that as a zero-length manifest entry — the slot exists, the bytes don't.

Prove it to yourself

Try it — pyarrow, 10 minutes 
import pyarrow as pa, pyarrow.ipc as ipc

table = pa.table({"name": ["al", "paris", None, "hi"], "n": [10, 20, None, 40]})
with ipc.new_file("batch.arrow", table.schema) as w:
    w.write_table(table)

blob = open("batch.arrow", "rb").read()
print(blob[:6], blob[-6:])                     # ARROW1 on both ends?

# now the payoff — zero-copy from disk:
with pa.memory_map("batch.arrow") as src:
    m = ipc.open_file(src)
    t2 = m.read_all()
    print(t2.combine_chunks().column("n").buffers()[1])  # read-only & mmap'd?

# and check the two-container claim:
with ipc.new_stream(open("batch.arrows", "wb"), table.schema) as w:
    w.write_table(table)
print(len(open("batch.arrows","rb").read()) - len(blob),  # footer+magic delta ≈ small
      "extra bytes for the footer")
Bonus: hexdump the file (xxd batch.arrow | head -20) and find the Flatbuffer manifest — the readable fragments — versus the raw body blocks. You are looking at Lesson 1's buffers serialized verbatim.
