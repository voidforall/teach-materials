Buffers & Validity Bitmaps

An Arrow array is not an object graph. It is two slabs of bytes — and once you can read them, every Arrow API becomes a view.

Your mission is to build on libarrow and pyarrow understanding the machine. So we start not with an API, but with bytes. Take the column you've typed a thousand times:

[10, 20, null, 40] (int64)

Ask: what does this look like in memory? Arrow's answer is the foundation of everything else in the course — SIMD scans, zero-copy slices, IPC, the works.

The two-slab layout

That's the entire array. Alongside the buffers, the Array object carries just three integers: length = 4, null_count = 1, offset = 0. In C++ this is literally the arrow::ArrayData struct; pyarrow wraps the same thing.

Keystone Values live in one contiguous buffer, nullness lives in a separate packed bitmap — one bit per value. A null costs 1 bit of overhead, not a tagged pointer or a sentinel value. Separating "is it null" from "what is it" is what lets the values buffer stay dense, regular, and SIMD-scannable.

Reading the bitmap, bit by bit

The bitmap is LSB-first within each byte: slot i's bit lives in byte i ÷ 8, at position i mod 8 — so the first slot is the least significant bit. Set bit = value present; clear bit = null. Our 0b00001101 reads right-to-left: slot 0 ✓, slot 1 ✓, slot 2 null, slot 3 ✓. That matches the column.

Two spec wrinkles worth burning in:

  • If null_count = 0, the validity buffer may be omitted entirely — an all-ones bitmap is implied.
  • The bytes at a null slot in the values buffer are unspecified garbage. Never read them; check the bitmap first.

Drill it

Decode the byte, click the null slots. Get a streak of 5 — the LSB-first direction is the part everyone gets backwards.

Retrieve it

An int32 array of 100 rows, 37 nulls. How many bytes are in its validity bitmap?

13 bytes.

ceil(100 / 8) = 13. The bitmap sizes on length, never on null_count — 37 nulls or 1 null, same 13 bytes.

Bitmap byte 0b01000000. Which slot is null — and what's its index?

Slot 1.

Only bit 1 is clear. Bits index LSB-first, so 0b01000000 → slot 1 null, slots 0 and 2–7 present.

Why does Arrow use a bitmap instead of a reserved null sentinel in the values buffer?

Dense buffers scan fast.

A packed bitmap costs ~1 bit/row and leaves the values buffer uniform: every value the same stride, every type fully representable, vectorized kernels loop over raw memory without per-value null checks interleaved in the data path.

Prove it to yourself

Try it — pyarrow, 5 minutes 
import pyarrow as pa
a = pa.array([10, 20, None, 40], type=pa.int64())
buf = a.buffers()          # [validity, values]
print(buf[0])              # what's the size? is it even there?
print(a.null_count, a.offset)

b = pa.array([1, 2, 3], type=pa.int64())   # no nulls...
print(b.buffers()[0])      # ...so what happened to the validity buffer?
Predict both outputs before running. If the second validity buffer surprises you, re-read the "two spec wrinkles" above.
