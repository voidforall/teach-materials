Zero-Copy Slicing & Buffer Lifetimes

That offset = 0 integer you met in Lesson 1? It's the tip of Arrow's whole ownership model.

You now know the layout recipes. This lesson is about what happens when data moves between views — slices, chunks, languages — and the discovery that in Arrow it usually doesn't move at all.

A slice moves nothing

Take a = pa.array([10, 20, 30, 40]) and slice it: b = a[1:3] (the values [20, 30]). What does b own? Nothing. It's the same two buffers, with the array-level metadata re-pointed:

This is why Slice() (C++) and Python slicing are O(1) in both time and memory — a 10 GB table sliced into a thousand windows allocates nothing. The mechanism composes: a[1:3][1:] just adds offsets; ChunkedArray.slice() narrows a list of zero-copy views; Table.select(['b','a']) reorders metadata only.

One wrinkle to carry from Lesson 1: the array-level offset shifts everything — the values window and the validity bitmap's starting bit. A slice's bitmap doesn't start at bit 0 of the buffer; bit arithmetic is always relative to the offset. That's why library code never reads buffers raw — it goes through the accessor.

Keystone Arrow's sharing model: one immutable allocation, many lightweight views. Buffers are never mutated in place — every "derived" array is new metadata (offset, length, buffers list) over the same bytes. Copying only happens when the result cannot be a window: concatenation, gather/take, filter, cast, chunk-merging.

Who frees the bytes?

Buffers are reference-counted and immutable — in C++, std::shared_ptr<Buffer> handed out by an arrow::MemoryPool; in pyarrow, Python's GC holds a reference on top of Arrow's. A slice keeps its parent's buffers alive; you cannot create a dangling Arrow view. The lifetime rules worth memorizing:

  • Buffers outlive views: a 3-element slice pins the entire 10 GB allocation. Freeing big memory sometimes requires explicitly dropping the parent — or copying the window (combine_chunks(), pa.concat_arrays) to release the overhang. Yes — sometimes you copy on purpose to shrink.
  • Zero-copy bridges: np.asarray(int64_arr) wraps the same buffer when the array is primitive — numpy has no validity bitmap, so a nullable or string array forces a copy. Same deal in C++ wrapping external memory (Buffer::FromWrap-family, or mmap): Arrow references bytes it did not allocate, and frees via callback.
  • Chunks are not windows: a ChunkedArray is just a Python/C++ list of independent arrays. combine_chunks() must copy — N buffers can't become one.

Classify it

For each operation: does it move bytes, or share buffers? Mixed with retrieval from Lessons 1–2 on purpose — interleaving is the point. Streak of 8.

Retrieve it

You slice 100 rows out of a 10 GB table and delete the table's variable. What's still in memory?

All ten gigabytes.

The slice holds references to the parent's buffers — the overhang stays allocated. To keep just the window, materialize a copy and drop the parent.

Why can pa.concat_arrays never be zero-copy?

Two buffers, one result.

The result must be one contiguous buffer; two separate allocations can't be fused by any metadata trick. Every element is copied.

When does np.asarray(arrow_arr) copy?

Nullable or nested.

numpy has no validity bitmap and no variable-length layout. Primitive, no-nulls arrays share the buffer; anything else must be converted into numpy's representation.

A string array sliced to [:3] — what happens to the data soup?

Untouched, overhanging.

The slice re-points offsets/metadata only; bytes for later strings stay in the buffer past the window's end, pinned alive by the slice.

Prove it to yourself

Try it — pyarrow, 5 minutes 
import pyarrow as pa

a = pa.array([10, 20, 30, 40])
b = a[1:3]
print(a.buffers()[1] is b.buffers()[1])   # same Buffer object?

big = pa.array(range(10_000_000))
window = big[9_000_000:]
import sys; print("window len:", len(window))
del big                                    # guess: is the memory freed?
# (check with: import resource; resource.getrusage(...).ru_maxrss)

c = pa.chunked_array([[1, 2], [3, 4]])
print(c.combine_chunks().buffers())        # one values buffer now — at what cost?
The identity check on line 4 is the whole lesson in one True.

Where this goes next

The immutable-buffer model has one more spectacular consequence, and it's the reason Arrow exists as a project and not just a C++ library: if buffers are just bytes, you can serialize them without rewriting them — write the buffers to disk, mmap them back, and the mmapped bytes are the array. That's the IPC / Feather file format, Lesson 4, where zero-copy stops being in-process trivia and becomes cross-process architecture.
