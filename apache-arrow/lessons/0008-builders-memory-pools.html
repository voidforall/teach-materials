Builders & Memory Pools

Buffers are immutable — so how does anything ever get created? Scratch space, geometric growth, and a finish that hands over ownership.

The build arc begins where Lesson 3's rule bites hardest: no buffer is ever mutated, yet data arrives one row at a time. The ArrayBuilder family is Arrow's answer — and it's the C++ machinery you'll actually build on.

A builder is scratch + a handoff

Int64Builder holds the same layout you've read since Lesson 1 — a validity scratch bitmap and a values scratch buffer — but mutable and over-provisioned. You append; it grows; Finish() seals the scratch into an immutable ArrayData and transfers the buffers out (no final copy — the builder hands over its allocations and resets).

arrow::Int64Builder bld(pool);
for (auto v : values) {
  if (v) bld.Append(*v);      // sets validity bit + writes value
  else    bld.AppendNull();   // clears bit; value slot left garbage
}
auto maybe = bld.Finish();    // ArrayData built from scratch buffers — transferred, not copied

Every layout lesson maps to a builder: StringBuilder owns three scratches (bitmap, offsets, soup) and Append("paris") writes one int32 fencepost plus 5 bytes; ListBuilder wraps a child builder and appends a fencepost when the list closes; StructBuilder is a bundle of field builders sharing one bitmap. Nested construction is recursive appends — exactly the recursive layout from Lesson 2.

Keystone Builders amortize: capacity doubles, so appends are O(1) amortized with ~2 element-copies total — but the final doubling momentarily holds 2× your data. The escape is chunking: Finish() every N rows into a ChunkedArray and memory waste never exceeds one chunk. Doubling = speed of a single buffer; chunking = bounded slack and early availability. Arrow's own writers do both (that's max_chunksize from Lesson 7, one layer down).

Watch it grow

The MemoryPool under everything

Every scratch allocation comes from an arrow::MemoryPool — the accounting layer introduced in Lesson 3. Three things it does for you:

  • Aligned allocation: 64-byte aligned (buffer padding to 8 is the spec; 64 keeps cache lines and SIMD loads happy — the Lesson 5 loop shape, protected at the source).
  • Backend choice: the default pool can back onto jemalloc or mimalloc (Arrow builds often bundle one), or plain system malloc — selectable at link/init time.
  • Accounting: pool->bytes_allocated() is how you watch a builder's doublings live, and how engines meter memory per query (kill a query, not the process).

Builders take the pool in their constructor; Finish()'s transferred buffers keep referencing it, so freeing happens through the same pool. This is also where custom allocators plug in — your build mission will likely meet MemoryPool::MakeBuilder-adjacent territory when embedding Arrow.

Retrieve it

Why does Finish() not copy the data?

Scratch buffers transfer.

The builder's mutable scratch allocations become the array's immutable buffers by ownership handoff; the builder resets to empty. Immutability (Lesson 3) starts at Finish — scratch is exempt because nothing else can see it.

Append 1M rows via doubling vs chunked-1k. Compare worst-case memory waste.

1M vs ~1k slots.

Doubling lands capacity between 1× and 2× length, so up to ~1M slots are slack; the last growth also needs old+new alive at once. Chunked finishes at fixed boundaries — slack never exceeds one chunk, at the price of a ChunkedArray's bookkeeping.

What does ListBuilder.Append() write when the list is closed with 3 elements?

One int32 fencepost.

Child appends went to the child builder; closing the list appends the next offsets entry (child_length) — the Lesson 2 recipe, split across two builders sharing timing.

Why do Arrow buffers get 64-byte alignment when the spec requires 8?

Cache lines, SIMD.

Spec mandates 8-byte alignment/portability; the memory pool rounds to 64 so buffer starts sit on cache-line boundaries and aligned SIMD loads in kernels (Lesson 5) never straddle lines.

Prove it to yourself

Try it — pyarrow (the C++ builders underneath), 5 minutes 
import pyarrow as pa

b = pa.array([10, None, 30])        # Python list → C++ ArrayBuilder path
print(b.buffers())

# watch the doubling from Python:
import pyarrow.compute as pc
big = pa.array(range(2**20 + 1))    # built by a builder somewhere —
print(big.nbytes)                   # …but a finished array is tight: no slack survives Finish

# vs. chunked construction (the bounded-slack strategy):
t = pa.table({"n": range(3_000_000)}, schema=pa.schema([("n", pa.int64())]))
t2 = t.combine_chunks()             # N appends → chunked → one tight copy at the end
Note the subtlety the second block shows: slack lives only inside builders — a finished ArrayData is trimmed (the builder copies once at Finish if needed). The 2× blow-up is a construction-time phenomenon.
