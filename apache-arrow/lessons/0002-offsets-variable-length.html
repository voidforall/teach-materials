Offsets & Variable-Length Layout

Strings have no fixed stride — so Arrow stores one contiguous byte soup, plus fenceposts saying where each value begins and ends.

Lesson 1 gave you the fixed-width recipe: one bitmap, one values buffer, stride = type width. But "paris" is 5 bytes and "al" is 2. You can't SIMD-scan a buffer whose stride changes per row. Arrow's answer is the mechanism this whole course keeps reusing: offsets.

Three buffers, one soup

Here is ["al", "paris", null, "hi"] as Arrow lays it out (Variable-size Binary Layout):

Read slot 1 aloud: data[2:7] = "paris". Slot 2 is null — the bitmap says so — but its offsets are still well-formed: [7,7], an empty span. A null string has length 0 by construction, never a garbage span. (Distinct from an empty string "", which is also [k,k] — the bitmap is the only thing distinguishing them.)

Keystone Variable-length = fixed-width offsets + one contiguous soup. The offsets buffer has perfectly regular int32 stride — it is the thing you can vectorize, and the soup never moves. This exact recipe (offsets → child buffer, or offsets → child array) is how Arrow handles utf8, binary, list, and by recursion every nested type.

The generalization you'll actually use

Swap the byte soup for a child array and you have list<T> — the Variable-size List Layout. [[1,2,3], null, [4]] is: bitmap (slot 1 null), offsets [0,3,3,4], and a child int32 array [1,2,3,4]. A list<list<int>>? Just run the recipe again on the child. Nesting costs one offsets buffer per level — no pointers, no per-node allocation, which is exactly why passing nested Arrow data between C++ and Python costs nothing (lesson 4, zero-copy).

Two boundaries worth knowing:

  • int32 offsets cap the soup at 2 GB; beyond that, large_string / large_list use int64 offsets (twice the fencepost tax).
  • string_view (C++17-era layout) instead stores inline pointer+length per row — different tradeoff, appears in DuckDB/Polars territory, not part of the core spec.

Drill it

Extract the value at the requested slot. The fencepost habit — offsets[i] to offsets[i+1], check the bitmap first — should become automatic. Streak of 5.

Retrieve it

A utf8 array of 1000 rows carries how many int32 offsets?

1001 fenceposts.

length + 1, always. n values need n+1 boundaries — like fenceposts and fence panels. 1001 × 4 bytes ≈ 4 KB of pure bookkeeping, regardless of the strings themselves.

A string column of a million tiny strings ("OK", "NO", …) — where does the memory go?

Offsets dominate.

4 bytes of offset tax per row vs ~2 bytes of actual data. Short-string columns are fencepost-dominated; this is the honest cost column, not a pathology to fix (but it's why dictionary encoding exists — Lesson 6).

How do a null string and an empty string differ in the buffers?

The bitmap bit.

Both are a zero-length span [k,k] in the data soup. Only the validity bit differs: clear for null, set for "". If you only look at offsets, you cannot tell them apart.

Layout of [[1,2], [3]] — name every buffer.

Bitmap, offsets, child.

Validity (no nulls → omittable); int32 offsets [0,2,3]; one child int32 array [1,2,3] with its own (omittable) bitmap. Same three-part recipe as strings — only the soup became an array.

Prove it to yourself

Try it — pyarrow, 5 minutes 
import pyarrow as pa
s = pa.array(["al", "paris", None, "hi"])
validity, offsets, data = s.buffers()

import struct
off = struct.unpack("5i", offsets.buffer()[:20])   # n+1 int32 fenceposts
print(off)                                          # predict me: [0, 2, 7, ?, 9]

# bonus: read slot 3 by hand
start, end = off[3], off[4]
print(data.buffer()[start:end])                     # b'hi'?

# and the list generalization:
l = pa.array([[1, 2], None, [4]])
print(l.type, l.flatten())                          # what did flatten() drop?
If off[3] surprises you, reread the null-span rule above. And check l.buffers() — the list's buffers are just bitmap + offsets; the ints live in the child.
