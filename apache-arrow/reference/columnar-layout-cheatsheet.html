Columnar Layout — Buffer Cheat Sheet

Which buffers every Arrow array type carries, and how big each one is.

Every Arrow array is buffers + length + null_count + offset. The buffers are the whole story — the API objects are just views over them. Derived from the columnar format specification.

Universal rules

  • All values are little-endian; buffers are padded to 8 bytes (implementations target 64-byte alignment).
  • validity bitmap: 1 bit per slot, LSB-first — bit i of byte i/8, mask 1 << (i%8). Bit set = value present, 0 = null. Size: ceil(length / 8) bytes.
  • A buffer may be omitted when it can be all-default: validity when null_count = 0, offsets/data when empty.
  • offset (the array-level one) enables zero-copy slicing: a slice is the same buffers with shifted offset/length — no bytes copied.

Beyond one array

  • Dictionary encoding: column = indices array (bitmap + int values) + separate shared payload array. Nulls live in the indices bitmap; slicing keeps the full payload pinned; take gathers indices only. Wins when cardinality ≪ length. Two dictionaries with different payloads/numbering must be unified (re-index = copy) before combine/compare.
  • IPC message: Flatbuffer manifest (buffer offset/length pairs into the body, zero-length entries for omitted buffers) + body = raw buffers verbatim, 8-byte aligned. Stream = append-only frames; file (Feather V2) adds a footer indexing every batch + ARROW1 magic at both ends ⇒ random access. Dictionaries travel as separate messages before the batches that use them (replace or delta).
  • Elementwise kernel validity: output bitmap = bitwise AND of input bitmaps (absent buffer = all-ones). add propagates nulls, coalesce absorbs, aggregates skip. Kernel outputs are always fresh buffers.

Sizes at a glance

  • int64 column, n rows, k nulls → ceil(n/8) + 8n bytes total.
  • string column → 4(n+1) + total_string_bytes (+ bitmap). The 4 bytes/row offset tax is why short strings are offset-dominated.
  • Slicing [2:5] of any array → 0 new bytes.
