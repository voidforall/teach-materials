ClickHouse Cheat Sheet

The whole course compressed to one page: mechanisms, design rules, engine choices, idioms, red flags.

Mechanisms in one line each

  • Speed = vectorized execution over compressed, sorted, immutable column files; bottleneck is memory bandwidth + decompression.
  • Part = one insert block → one immutable sorted directory; merges are k-way sorted merges. Insert in batches ≥ 10k rows.
  • Granule = 8192 rows (default); mark = first ORDER BY value(s) per granule, held in RAM. Reads are whole-granule.
  • Pruning only works on an ORDER BY prefix; everything else needs a skip index or a scan.

Table design decisions

DecisionRule
ORDER BYMost-common equality filters first (selective → less), main time column last. Never a unique id.
PARTITION BYManagement unit only: month/day. Enables DROP PARTITION + TTL. Never high-cardinality.
CodecsDefault LZ4; ZSTD(1–3) for big/cold; Delta/DoubleDelta (monotonic ts/counters), Gorilla (floats), T64 (ints). Sort order is the master codec.
LowCardinality< ~10k distinct strings — always. Not for high-cardinality values.
Skip indexesbloom_filter (high-card equality, non-key), minmax (numeric/time), set(N) (low-card). Help only when correlated with sort order.

Updates & deletes

  • Strategy ladder: append + argMax → merge-fold engine → partition REPLACE/DROP → mutation (repairs only).
  • ALTER … UPDATE/DELETE rewrites whole parts (all columns) — cost ∝ affected part size, async (system.mutations).
  • DELETE FROM … WHERE = lightweight masks; fast to issue, filtered at read, reclaimed at merge. GDPR-rate OK, not OLTP-rate.

MV pipeline recipe

CREATE TABLE rollup ENGINE = AggregatingMergeTree ORDER BY (dim, bucket) AS
SELECT dim, bucket, sumState(m) AS m_sum, uniqState(u) AS u_uniq FROM src GROUP BY dim, bucket;
CREATE MATERIALIZED VIEW rollup_mv TO rollup AS
SELECT dim, bucket, sumState(m) AS m_sum, uniqState(u) AS u_uniq FROM src GROUP BY dim, bucket;
-- read: SELECT dim, sum(m_sum), uniq(u_uniq) FROM rollup GROUP BY dim;

MV = per-insert-block trigger; no history recompute — backfill manually.

Joins & lookups

  • Hash join: right side in RAM — project only needed columns; joins run left→right; ANY LEFT JOIN for dimensions.
  • dictGet('d','attr',key) — in-memory map refreshed from Postgres/HTTP; enrich at ingest via MV whenever possible.
  • Denormalize by default; storage is nearly free, joins are not.

Use / don't use

  • Use when: append-heavy + scan-style analytics + eventual consistency OK — event analytics, logs/observability, tick data, feature stores, dashboard backends.
  • Don't when: OLTP, continuously mutable state, heavy ad-hoc multi-join relational algebra, strong consistency needs — keep Postgres/warehouse; mirror into CH for analytics.

Ops quick hits

  • Batch inserts (≥10k rows); watch system.parts for part-count health.
  • Per-query guardrails: SETTINGS max_execution_time, max_memory_usage.
  • Inspect marks: system.parts; compression: system.columns; mutations: system.mutations.
  • TTL for retention + partition drops for bulk lifecycle.
