ClickHouse 速查表

整门课压缩成一页：机制、设计规则、引擎选择、惯用法、红旗。

机制各一行

  • 速度 = 在压缩、有序、不可变的列文件上向量化执行；瓶颈是内存带宽 + 解压。
  • Part = 一个插入块 → 一个不可变有序目录；合并是 k 路有序归并。插入批次 ≥ 1 万行。
  • Granule = 8192 行（默认）；mark = 每个 granule 的首个 ORDER BY 值，常驻内存。读取以整 granule 为单位。
  • 剪枝只对 ORDER BY 前缀有效；其他列要么跳数索引、要么全扫。

表设计决策

决策规则
ORDER BY最常用的等值过滤在前（选择性高→低），主时间列最后。绝不按唯一 id。
PARTITION BY只作管理单元：月/天。成就 DROP PARTITION + TTL。绝不按高基数分区。
编解码器默认 LZ4；大而冷的列用 ZSTD(1–3)；Delta/DoubleDelta（单调时间戳/计数器）、Gorilla（浮点）、T64（整数）。排序序是主编解码器。
LowCardinality不同值少于约 1 万的字符串——尽管用。高基数值不用。
跳数索引bloom_filter（非键高基数等值）、minmax（数值/时间）、set(N)（低基数）。只有与排序序相关时才有用。

引擎选择器

负载引擎读侧职责
默认 / 追加式事实表MergeTree普通查询；每键最新用 argMax。
Upssert 的实体ReplacingMergeTree(ver)argMax(ver) GROUP BY key（大表避免 FINAL）。
可加预聚合SummingMergeTreeGROUP BY + sum（存在部分聚合行）。
MV 汇总目标AggregatingMergeTree-Merge 组合子（uniq/quantile 状态可折叠）。
频繁整行更新VersionedCollapsing(sign, ver)插 +1 与 −1 行；少见，最后手段。

更新与删除

  • 策略阶梯：追加 + argMax → 合并折叠引擎 → 分区 REPLACE/DROP → mutation（只做修复）。
  • ALTER … UPDATE/DELETE 重写整个 part（全部列）——代价 ∝ 受影响 part 大小，异步（system.mutations）。
  • DELETE FROM … WHERE = 轻量掩码；下发快，读取时过滤、合并时回收。GDPR 频率可以，OLTP 频率不行。

MV 流水线配方

CREATE TABLE rollup ENGINE = AggregatingMergeTree ORDER BY (dim, bucket) AS
SELECT dim, bucket, sumState(m) AS m_sum, uniqState(u) AS u_uniq FROM src GROUP BY dim, bucket;
CREATE MATERIALIZED VIEW rollup_mv TO rollup AS
SELECT dim, bucket, sumState(m) AS m_sum, uniqState(u) AS u_uniq FROM src GROUP BY dim, bucket;
-- 读取：SELECT dim, sum(m_sum), uniq(u_uniq) FROM rollup GROUP BY dim;

MV = 逐插入块触发；不重算历史——回填要手动。

Join 与查找

  • Hash join：右表进内存——只投影需要的列；join 从左到右执行；维度表用 ANY LEFT JOIN。
  • dictGet('d','attr',key)——从 Postgres/HTTP 刷新的内存映射；尽可能用 MV 在摄取时富化。
  • 默认反规范化；存储近乎免费，join 不是。

SQL 惯用法

任务惯用法
每键最新argMax(col, ts) GROUP BY key
比率 / 条件聚合countIf(c) / count(); sumIf(x, c)
去重计数uniq（近似）/ uniqExact / uniqCombined
分位数quantiles(0.5, 0.99)(x)
Top 项topK(10)(x)
数组展开为行arrayJoin(arr)
漏斗windowFunnel(t)(ts, e1, e2, …)
留存retention(c1, c2, …)
体量审计system.columns：压缩 vs 未压缩字节

用 / 不用

  • 用：追加为主 + 扫描式分析 + 可接受最终一致性——事件分析、日志/可观测性、tick 数据、特征库、仪表盘后端。
  • 不用：OLTP、持续可变状态、重型即席多表 join、强一致需求——留在 Postgres/数仓，镜像进 CH 做分析。

运维速记

  • 批量插入（≥1 万行）；用 system.parts 监控 part 数健康度。
  • 逐查询护栏：SETTINGS max_execution_time, max_memory_usage。
  • 看 marks：system.parts；压缩：system.columns；mutation：system.mutations。
  • 留存用 TTL；批量生命周期用分区删除。
