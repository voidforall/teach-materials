Joins & Dictionaries

ClickHouse joins are fine — until the right table stops fitting in memory. The whole art is keeping the right side small, or avoiding the join entirely.

The default: hash join, right table in RAM

SELECT … FROM events e JOIN users u ON e.user_id = u.id builds a hash table of users (the right side) in memory, then streams the left side. Rules of thumb:

  • Right table ≤ a few GB: fine. Keep only needed columns in the right side (subquery projecting columns beats joining the wide table).
  • Multiple joins execute left to right, each output becoming the next left side — order matters for memory.
  • ANY LEFT JOIN: first match only — for dimension lookups where duplicates on the right are a data bug, it's cheaper and safer.
  • Big-vs-big joins: possible (partial/grace join via join_algorithm settings that spill to disk) but you're fighting the engine's grain.

Dictionaries: point lookups without joins

A dictionary is a key→attributes map loaded from Postgres/MySQL/HTTP/another CH table, refreshed on a schedule or on invalidation, held in memory with several layouts (hash_array, cached, complex_key_*). Access it directly in SQL:

SELECT dictGet('users_dict', 'plan', user_id) AS plan, count()
FROM events GROUP BY plan;

This is ClickHouse's answer to "join a small-ish dimension that lives elsewhere": no join machinery, no right-table scan, microsecond lookups, and the source of truth stays in the OLTP database. Also great for enriching at insert time via MVs — enrich once at ingest, never join at query time.

Keystone Join strategy ladder: enrich-at-ingest (MV + dictGet) > dictGet at query time > hash join with small projected right side > grace/partial join (last resort). ClickHouse is a scan engine, not a relational algebra machine — denormalize by default.
Anti-pattern Star-schema loyalty: normalizing events into facts + dimensions and joining 4 dimensions at query time, every time. In ClickHouse you pay per join per query. Flatten at ingest: each event row carries its dimension snapshot (plan, country) — storage is nearly free at these compression ratios.
Q1: Why project columns in a subquery on the right side of a join?

The right table is materialized as an in-memory hash table — column projection shrinks it directly, often the difference between fitting and OOM.

Q2: Dimension table lives in Postgres and changes hourly. Query-time join or dictionary?

Dictionary with lifetime/invalidation refresh: dictGet avoids join machinery and streams from source; hourly staleness is usually acceptable.

Q3: Why is denormalization cheaper in ClickHouse than in a row store?

Repeated dimension values compress to almost nothing (dictionary/low-cardinality encoding + sort adjacency), while per-query joins cost real memory and time every execution.
