Mutations, Deletes & the Update Anti-Pattern

ClickHouse can update and delete — it just charges you list price. Knowing that price is what separates users from victims.

ALTER TABLE t UPDATE status = 'x' WHERE … and ALTER TABLE t DELETE WHERE … are mutations: asynchronous commands that rewrite every part containing matching rows — all columns, whole files. Cost model:

  • Mutation cost ≈ data volume of affected parts, not number of matching rows. A WHERE matching 10 rows in a month-old 500 GB partition still rewrites that partition's parts.
  • They queue and run in the background; check system.mutations (is_done) — your query doesn't wait, but your disk I/O does.

Lightweight DELETE

DELETE FROM t WHERE … writes delete masks (row-level tombstones) instead of rewriting immediately — fast to issue; affected rows are filtered at read time, and physically reclaimed at merges. Good for GDPR-style "delete this user's rows" at moderate rates. It's still not an OLTP delete path.

The idiomatic alternatives (in order of preference)

  1. Append + read-time resolution: insert a new versioned row; queries pick the latest with argMax (lesson 9). Updates become cheap inserts.
  2. Replacing/VersionedCollapsing engines (lesson 5) if the read-side ergonomics justify it.
  3. Partition lifecycle: partition by unit-of-work (day/month), overwrite a bad day with INSERT into a staging table + REPLACE PARTITION, expire with DROP PARTITION + TTL.
  4. Mutations — for genuine one-off data repairs.
Keystone ClickHouse data is write-once; "update" is one of four strategies — append+argMax, merge-fold engine, partition swap, or the expensive mutation. If your workload updates rows continuously by primary identity, that's an OLTP workload and belongs in Postgres (possibly synced into ClickHouse for analytics).
Anti-pattern Running scheduled ALTER TABLE … UPDATE jobs as a normal part of the pipeline ("we update statuses every 10 minutes"). You now have a permanent background-rewrite treadmill competing with merges and queries. Redesign as appends.
Q1: Why is a mutation matching 3 rows potentially the most expensive statement your cluster runs today?

It rewrites every part (all columns) that contains matching rows — potentially the whole table if the predicate hits old, large parts.

Q2: Lightweight DELETE issues instantly. Where did the cost go?

To read time (masked rows filtered per scan) and to future merges (physical reclamation). Nothing in an immutable store is free — it's deferred, not removed.

Q3: Pipeline needs to fix "status" on yesterday's misloaded data daily. Best mechanism?

Partition by day; load corrected day into a staging table and atomically REPLACE PARTITION. No mutation, no rewrite of other days.
