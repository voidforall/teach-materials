物化视图与增量聚合

ClickHouse 的物化视图不是 Postgres 那种存储查询计划——它是插入触发器。这个差异就是本课的全部。

当行落入源表时，MV 的 SELECT 只在刚插入的块上运行，转换结果插入目标表。不扫历史、不重算——数据库内部的逐块流处理。

经典模式：用聚合状态做汇总

CREATE TABLE events_raw (…) ENGINE = MergeTree ORDER BY (user_id, ts);

CREATE TABLE events_1m
ENGINE = AggregatingMergeTree
ORDER BY (toStartOfMinute(ts), user_id) AS
SELECT
  toStartOfMinute(ts) AS minute,
  user_id,
  sumState(amount)   AS amount_sum,
  uniqState(session) AS sessions
FROM events_raw
GROUP BY minute, user_id;

CREATE MATERIALIZED VIEW events_1m_mv TO events_1m AS
SELECT toStartOfMinute(ts) AS minute, user_id,
       sumState(amount) AS amount_sum, uniqState(session) AS sessions
FROM events_raw GROUP BY minute, user_id;

读回时配对应的 -Merge 组合子：

SELECT minute, sum(amount_sum) AS amount, uniq(sessions) AS users
FROM events_1m GROUP BY minute;

-State 后缀存可合并的部分状态（sum+count、HLL sketch、分位数 sketch……）；-Merge 后缀在查询时合并状态。这让聚合跨时间可结合：今天算的分钟聚合与明年算的无损合并。SummingMergeTree 的普通数字对 uniq、quantile 这类非可加指标做不到——状态可以。

核心要点 MV = 逐插入块的变换；-State = 可合并部分聚合；AggregatingMergeTree = 合并时折叠状态的目标表。三者把原始洪流变成预聚合、可任意加深 的汇总层——这是 ClickHouse 的招牌架构。

运维事实

  • MV 可以链式级联（原始 → 每分钟 → 每小时）：每一层是从下一层读的另一个 MV。
  • MV 会略微拖慢插入，且旧版本出错时可能静默丢行——监控流水线，保持变换零异常。
  • 手动回填：用同样的 SELECT 带日期边界插入目标表。MV 只覆盖它创建之后的插入。
  • 使用 TO target_table，显式掌控目标表的 schema、ORDER BY 和 TTL。
问 1：给 MV 加了一个改变计算的列，历史会被重算吗？

不会。MV 只处理新插入块。历史数据需要手动回填插入目标表。

问 2：MV 目标里为什么用 uniqState 而不是 uniq？

uniq 不可加——每分钟计数不能相加。State 形式存 sketch；uniq(Merge) 无损合并 sketch。

问 3：这里 AggregatingMergeTree 引擎贡献了什么？

part 合并时按键合并聚合状态，保持目标表小巧、查询时合并便宜。

练习 在纸上为"每秒请求数 → 每小时、去重客户端数 + p99 延迟"画一个两层汇总——建表 DDL、MV、以及用对组合子的最终查询。然后对照速查表。
