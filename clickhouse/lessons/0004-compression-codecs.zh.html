压缩、编解码器与 LowCardinality

ClickHouse 在磁盘上比行存常态领先 10–100×。这个比例是设计出来的——而设计者是你。

压缩是查询加速器，不只是省磁盘：磁盘字节少，解压和流过内存的字节就少。两层叠加：

第一层：专用编解码器（先变换再压缩）

  • CODEC(Delta(n))——存差值；单调计数器、时间戳。
  • CODEC(DoubleDelta)——差值的差值；缓慢变化的单调序列（时间戳/自增 id 收益最大）。
  • CODEC(Gorilla)——异或编码的浮点；监控指标值。
  • CODEC(T64)——打包 ≤64 位整数中有意义的位。

它们包在通用编解码器外：ts DateTime CODEC(DoubleDelta, ZSTD(1))。通用层（默认 LZ4，要比例用 ZSTD(n)）再压缩已规律化的字节。

第二层：LowCardinality——类型系统里的字典编码

LowCardinality(String) 把每个值存成指向 part 内字典的 8 位（自动加宽）索引。不同值少于约 1 万的列（国家、状态、事件名）又小又快——比较变成整数比较。这是 ClickHouse 最接近免费午餐的东西；大胆用，但别用于高基数字符串（字典成了死重）。

核心要点 排序序是主编解码器。Delta/DoubleDelta 只在相邻值可预测时有效——而这正是 ORDER BY 对键组内"类时间"列的保证。压缩策略是第 3 课 ORDER BY 决定的下游。

体量直觉

  • 行存里约 1 KB 的原始事件行 → ClickHouse 键对齐排序 + ZSTD 后通常每行 10–100 字节。
  • 自查：SELECT name, formatReadableSize(sum(data_compressed_bytes)) AS disk, formatReadableSize(sum(data_uncompressed_bytes)) AS raw, round(sum(data_uncompressed_bytes)/sum(data_compressed_bytes), 1) AS ratio FROM system.columns WHERE table = 'events' GROUP BY name ORDER BY disk DESC。
反模式 给所有列无脑上 ZSTD(22)。最高级 ZSTD 解压慢得多；默认 LZ4 通常在扫描延迟上获胜。重 ZSTD 留给冷、大、少查的列——并用 system.columns 实测，别凭感觉。
问 1：为什么 DoubleDelta 对 ORDER BY 中的时间戳列有效？

在同一个键组内时间戳单调递增且步长相当规律；二阶差分近乎常数（常为零），压缩后几乎不占空间。

问 2：LowCardinality 什么时候有害？

高基数字符串：per-part 字典膨胀，查找无收益，合并还要为统一字典付费。粗略上限：约 1 万个不同值。

问 3：切到 ZSTD(19) 后查询延迟上升，为什么？

解压在扫描路径上；极端 ZSTD 级别用解压速度换比例，字节更少但扫描更慢。
