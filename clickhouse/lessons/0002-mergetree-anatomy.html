MergeTree Anatomy: Parts & Granules

Everything in a MergeTree table — speed, mutation cost, index behavior — follows from two units of storage: the part and the granule.

MergeTree is the engine behind ~95% of real ClickHouse tables. It is an LSM-flavored columnar store: inserts create immutable sorted parts; background threads continually merge parts into larger ones. Unlike a classic LSM it has no memtable flush or WAL-per-tx semantics — inserts arrive in blocks of tens of thousands to millions of rows and go straight to a new part.

The part

  • Each INSERT of a block produces one part (directory) — one compressed file per column, plus a sparse primary index ("marks") per part.
  • Parts are sorted by the ORDER BY key. Merges are k-way merges of sorted runs — cheap, sequential, and they keep part count low.
  • Consequence: insert in large batches. One row-per-insert produces one tiny part each — the classic "too many parts" death.

The granule

Inside a part, each column file is divided into granules of index_granularity = 8192 rows by default. The primary index stores, per granule, the first value of each ORDER BY column — one "mark" per granule, held in memory.

A query like WHERE site = 'kaggle' AND ts >= today() - 7 binary-searches the marks, selects granules whose key ranges intersect the predicate, and decompresses only those. Note the subtlety: ClickHouse reads whole granules, then filters precisely inside them. A predicate on a non-first key column still scans lots of granules — that's the next lesson's problem.

Keystone Inserts create sorted parts; merges keep part count low; the sparse index maps 8192-row granules to key ranges in memory. Read amplification, mutation cost, and index selectivity are all granule-and-part arithmetic.
Q1: Why is one-row-per-INSERT catastrophic in MergeTree?

Each insert creates a part; unbounded part count explodes merge load and open files ("too many parts"). Batch inserts: at least thousands of rows, ideally 100k+.

Q2: A query matches 3 rows out of 8 billion, keyed on a column that is 3rd in ORDER BY. How many granules can it skip, at best?

Almost none — the marks can't prune on a non-prefix key, so it effectively scans the whole table (or needs a skip index).

Q3: What exactly does one mark contain?

The first value of each ORDER BY-column in a granule (plus the file offsets needed to read it).
