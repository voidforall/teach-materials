Why ClickHouse Is Fast

You already know columnar OLAP. ClickHouse's edge is not "columnar" — it's what it refuses to be.

Your mission is to know when to reach for ClickHouse and when not to. That judgment starts with a precise picture of where the speed comes from. Every columnar database scans columns; ClickHouse's differentiators are a set of design commitments that trade OLTP niceties for aggregate scan throughput.

Commitment 1: vectorized execution, not per-row interpretation

Most OLAP engines compile or interpret plans per row or per batch of objects. ClickHouse processes data in columns of contiguous values, thousands at a time, with SIMD-friendly inner loops and runtime code specialization (it generates and compiles query pipelines at runtime). A sum(amount) is literally a tight loop over an array of numbers — the CPU does 4–16 values per instruction.

Consequence: expression evaluation is fast enough that the bottleneck moves to memory bandwidth and decompression. Which leads to commitment 2.

Commitment 2: data is stored compressed, and sorted

Columns are compressed on disk with general codecs (LZ4 default, ZSTD opt-in) plus per-column specialized codecs (Delta, DoubleDelta, Gorilla — lesson 4). Sorting data by the primary key makes similar values adjacent, which is what makes compression ratios of 10–100× routine. Scans read few bytes because (a) only needed columns are read, (b) they're compressed, and (c) the sparse primary index skips most granules entirely (lesson 2).

Commitment 3: shared-nothing, single-table-first

ClickHouse scales by sharding one big table across nodes; it is a query engine over sorted, immutable column files, not a transactional store. Immutable files are what make zero-copy reads, cheap merges, and lock-free parallel scans possible. Almost everything ClickHouse is bad at (fast updates, deletes, ACID transactions — lesson 6) falls out of this choice.

Keystone ClickHouse = vectorized execution over compressed, sorted, immutable column files. Fast scans, fast aggregations, terrible point-mutation ergonomics — all three facts have the same root.

The mental benchmark

The canonical workload where this stack wins: aggregate a few columns over hundreds of millions of rows, filtered by a selective prefix of the sort key. E.g. "daily revenue by country for the last 30 days" over 2 years of events — reads a few GB, answers in a second. The canonical losing workload: SELECT * WHERE user_id = ? returning one row, on a table sorted by timestamp. It works, but you're paying the wrong engine to do it.

Q1: A columnar MPP database already scans only needed columns. Name two ClickHouse-specific mechanisms that reduce bytes read further.

Compression (general + specialized codecs) and the sparse primary index selecting only relevant granules.

Both depend on the table being sorted — sorting clusters similar values (compression) and gives the index something to prune with.

Q2: Why is update-in-place fundamentally at odds with ClickHouse storage?

Part files are immutable; "updates" are asynchronous background rewrites (mutations). In-place mutation would break lock-free scans and merge assumptions.

Q3: Where does the bottleneck sit in a well-designed ClickHouse scan?

Memory bandwidth and decompression speed — not expression evaluation, which vectorization makes cheap.

The second aggregates ~30M rows in well under a second — that's commitments 1–3 working together.
