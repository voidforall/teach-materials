The MergeTree Family

Replacing, Summing, Aggregating, Collapsing — they all share one trick: fix things up during the merge. Understand that trick and the whole family is one idea.

Plain MergeTree never deduplicates or folds anything — rows inserted twice stay twice. The family variants add an on-merge policy: when parts merge, rows sharing the ORDER BY key are combined according to the engine's rule. Queries always see all parts, so before merges happen you can still see un-folded rows — the family engines are eventually consistent, not magically exact.

The catalog

  • ReplacingMergeTree(ver) — keeps the row with the max version per key; deduplication of upserted rows. "Replacing" only happens at merge time: query with FINAL or dedupe yourself (argMax — lesson 9).
  • SummingMergeTree — sums numeric columns per key. Classic for pre-aggregated facts: insert per-minute rows, reads still need GROUP BY + sum() because partials exist.
  • AggregatingMergeTree — stores partial aggregate states (sumState, uniqState, …) and merges them. The backbone of materialized-view pipelines — lesson 7.
  • CollapsingMergeTree(sign) — rows with sign = −1 cancel the matching sign = +1 row. Turns "updates" into insert-two-rows (state + inverse state). VersionedCollapsingMergeTree adds a version so cancellation works regardless of insert order.
Keystone Every family engine is MergeTree + a merge-time row-combining rule. None of them guarantee correctness at read time — your queries must tolerate partially-merged data (GROUP BY sums are fine; "latest row per key" needs argMax or FINAL).

Choosing (decision order)

  1. Default: plain MergeTree + dedupe/aggregation logic in the query (argMax, sum). Simplest, most flexible.
  2. Repeated upserts of entities → ReplacingMergeTree, read with argMax per key.
  3. High-volume additive metrics → SummingMergeTree or (better) plain + MV into AggregatingMergeTree.
  4. Frequently-mutated entities with strict accounting → VersionedCollapsing. Rarely the first choice — sign bookkeeping in the ingestion path is error-prone.
Anti-pattern SELECT * FROM t FINAL on large tables as the default read path. FINAL forces on-the-fly merging of your data at query time — it can be orders of magnitude slower than an argMax GROUP BY that exploits the same version column.
Q1: Rows were re-inserted 5 minutes ago; ReplacingMergeTree hasn't merged that part yet. What does count() show?

Both copies. Replacement is merge-time only; reads see un-folded rows. Dedupe at read time with argMax(version) GROUP BY key, or accept FINAL's cost.

Q2: Why do SummingMergeTree queries still need GROUP BY + sum?

Because partial rows may exist in not-yet-merged parts; summing already-summed values in different parts is still correct only if you aggregate by key again.

Q3: What does the sign = −1 row do in CollapsingMergeTree?

It cancels an earlier +1 row with the same key at merge time — deleting/updating becomes an insert of an inverse record.
