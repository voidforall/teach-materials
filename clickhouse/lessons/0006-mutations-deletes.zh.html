Mutation、删除与更新反模式

ClickHouse 能更新也能删除——只是按标价收费。知道这个价格，你就从受害者变成了用户。

ALTER TABLE t UPDATE status = 'x' WHERE … 和 ALTER TABLE t DELETE WHERE … 是 mutation：异步命令，重写每个包含匹配行的 part——所有列、整个文件。成本模型：

  • Mutation 代价 ≈ 受影响 part 的数据量，而不是匹配行数。WHERE 在一个存了一个月的 500 GB 分区里命中 10 行，也要重写该分区的 part。
  • 它们排队后台执行；查 system.mutations（is_done）——查询不用等，但磁盘 I/O 要等。

轻量删除（Lightweight DELETE）

DELETE FROM t WHERE … 写入删除掩码（行级墓碑）而非立即重写——下发很快；匹配行在读取时被过滤，合并时物理回收。适合 GDPR 式"删除该用户所有行"的中等频率场景。它仍不是 OLTP 删除路径。

惯用替代方案（按优先级）

  1. 追加 + 读时裁决：插入一条带版本的新行；查询用 argMax 取最新（第 9 课）。更新变成廉价插入。
  2. Replacing / VersionedCollapsing 引擎（第 5 课），如果读侧收益说得清。
  3. 分区生命周期：按工作单元（天/月）分区，坏的一天用暂存表 INSERT + REPLACE PARTITION 原子替换，用 DROP PARTITION + TTL 过期。
  4. Mutation——留给真正的一次性数据修复。
核心要点 ClickHouse 数据是一次性写入的；"更新"是四种策略之一——追加+argMax、合并折叠引擎、分区替换、或昂贵的 mutation。如果你的负载在按主标识持续更新行，那是 OLTP 负载，应该放进 Postgres（再同步进 ClickHouse 做分析）。
反模式 把定时 ALTER TABLE … UPDATE 当流水线的常规环节（"每 10 分钟刷一次状态"）。你就有了一台永久后台重写跑步机，和合并、查询抢资源。重新设计为追加。
问 1：为什么匹配 3 行的 mutation 可能是今天集群里最贵的语句？

它要重写每个包含匹配行的 part（全部列）——若谓词命中又老又大的 part，可能等于重写整表。

问 2：轻量删除瞬间完成。成本去哪了？

转到读取时（每次扫描过滤被掩蔽的行）和未来的合并（物理回收）。不可变存储里没有免费操作——只是延期，不是消失。

问 3：流水线每天要修"昨天加载坏的数据的 status"。最佳机制？

按天分区；把修正后的一天载入暂存表，原子 REPLACE PARTITION。不用 mutation，不重写其他天。
