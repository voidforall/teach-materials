ORDER BY 设计、分区与跳数索引

在 ClickHouse 里你不是给查询建索引，而是围绕查询设计表。ORDER BY 是你做出的杠杆率最高的决定。

没有可以事后补建的二级 B-tree 索引。ORDER BY 键决定：哪些谓词能剪枝 granule、列压缩得好不好（相邻相似性）、以及合并行为。设计规则：

核心要点 ORDER BY = 最常用的过滤列，按实际选择性从高到低排列，主时间列通常放最后。所有高频过滤维度都应进键；典型事件表用 ORDER BY (user_id, event, timestamp) 或 (site_id, timestamp)——除非只按时间查，否则绝不要只用 (timestamp)。

分区是为了管理，不是为了速度

PARTITION BY toYYYYMM(event_date) 把表按分区组织 part。按分区表达式剪枝很粗（月粒度），但删分区是 ClickHouse 里最廉价的删除：ALTER TABLE t DROP PARTITION '2024-01'——瞬间完成、零重写。分区用于 TTL 过期和批量数据生命周期；不要按高基数码（user_id！）分区——数百个分区 × 各自的 part 会毁掉合并。

给非键列加跳数索引

当高频谓词进不了键（访问模式太多）时，加 data skipping index。它不指向行——它按 granule 区间存元数据，让引擎跳过整个 granule：

  • INDEX idx_user user_id TYPE bloom_filter GRANULARITY 4——成员测试；高基数非键列的等值/IN 查找。
  • TYPE minmax——数值/时间列的区间（对与键序相关的列特别有效）。
  • TYPE set(N)——每区间最多 N 个不同值，适合低基数列。

跳数索引有摄取成本，而且只有当数据与排序序相关时才有效——对随机散布的值，bloom filter 什么都跳不掉。

反模式 照搬 OLTP 习惯：ORDER BY id（或不写）然后"以后再加索引"。没有以后。按唯一 id 排序的表压缩差、剪枝无——两头皆输。

示例

查询："用户 U 最近 30 天的事件，按类型"（99% 流量）+ "网站 S 今天所有事件"。

CREATE TABLE events (
  user_id UInt64,
  site_id UInt32,
  event LowCardinality(String),
  ts DateTime,
  payload String CODEC(ZSTD(3))
) ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (user_id, event, ts)
INDEX idx_site site_id TYPE bloom_filter GRANULARITY 4;

用户在前的键让 99% 的查询只读少数 granule；bloom 索引救活网站查询；月分区提供廉价 TTL。

问 1：为什么时间通常放 ORDER BY 最后而不是最前？

查询几乎总带等值维度（用户、网站）+ 时间范围。键前缀剪枝要求等值列在前，时间范围再在其中剪枝。时间放第一会让所有非时间过滤失效。

问 2：什么时候 DROP PARTITION 是正确的"删除"？

整单位的数据生命周期：保留窗口、重新导入坏数据。它是纯元数据操作、瞬时完成；而 mutation 要重写 part。

问 3：user_id 上的 bloom_filter 跳数索引什么都跳不掉。最可能的原因？

user_id 取值与排序序不相关——每个 granule 的值域都"含一切"，无从排除。（或者它本来就是键列。）
