Materialized Views & Incremental Aggregation

A ClickHouse materialized view is not a stored query plan like in Postgres — it's an insert trigger. That difference is the whole lesson.

When rows land in the source table, the MV's SELECT runs on the inserted block only, and the transformed result is inserted into a target table. No scans of history, no recompute — per-block stream processing inside the database.

The canonical pattern: rollup with aggregate states

CREATE TABLE events_raw (…) ENGINE = MergeTree ORDER BY (user_id, ts);

CREATE TABLE events_1m
ENGINE = AggregatingMergeTree
ORDER BY (toStartOfMinute(ts), user_id) AS
SELECT
  toStartOfMinute(ts) AS minute,
  user_id,
  sumState(amount)   AS amount_sum,
  uniqState(session) AS sessions
FROM events_raw
GROUP BY minute, user_id;

CREATE MATERIALIZED VIEW events_1m_mv TO events_1m AS
SELECT toStartOfMinute(ts) AS minute, user_id,
       sumState(amount) AS amount_sum, uniqState(session) AS sessions
FROM events_raw GROUP BY minute, user_id;

Read it back with the matching -Merge combinators:

SELECT minute, sum(amount_sum) AS amount, uniq(sessions) AS users
FROM events_1m GROUP BY minute;

The -State suffix stores a mergeable partial state (sum + count, HLL sketch, quantile sketch…); the -Merge suffix combines states at query time. This is what makes aggregation associative across time: a minute-aggregate computed today merges losslessly with one computed next year. SummingMergeTree's plain numbers can't do that for non-additive metrics like uniq or quantile — states can.

Keystone MV = per-insert-block transform; -State = mergeable partial aggregates; AggregatingMergeTree = target that folds states on merge. Together they turn a raw firehose into pre-aggregated, arbitrarily-deep rollups — the signature ClickHouse architecture.

Operational truths

  • MVs chain (raw → per-minute → per-hour): each layer is another MV reading from the layer below.
  • MVs slow inserts slightly and can silently drop rows on errors in old versions — monitor system.distributed-style pipelines and keep transforms exception-free.
  • Backfill manually: run the same SELECT with date bounds and insert into the target. The MV only covers inserts made after its creation.
  • Use TO target_table so you control the target's schema, ORDER BY, and TTL explicitly.
Q1: You add a column-changing computation to an MV. Does history get recomputed?

No. MVs process only new insert blocks. Historical data needs a manual backfill insert into the target.

Q2: Why uniqState rather than uniq in the MV target?

uniq isn't additive — you can't merge per-minute counts by summing. The -State form stores a sketch; uniq(-Merge) combines sketches losslessly.

Q3: What does the AggregatingMergeTree engine contribute here?

It merges equal-key rows by combining their aggregate states at part-merge time, keeping the target small and query-time merging cheap.
