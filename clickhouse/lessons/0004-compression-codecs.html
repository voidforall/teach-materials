Compression, Codecs & LowCardinality

ClickHouse routinely beats row stores 10–100× on disk. That ratio is designed, not accidental — and you are the designer.

Compression is a query accelerator, not just a disk saver: fewer bytes on disk means fewer bytes to decompress and stream through memory. Two layers stack:

Layer 1: specialized codecs (transform before compression)

  • CODEC(Delta(n)) — store differences; monotonic counters, timestamps.
  • CODEC(DoubleDelta) — differences of differences; slowly-changing monotonic series (biggest wins on timestamps/ids).
  • CODEC(Gorilla) — XOR-encoded floats; metrics gauge values.
  • CODEC(T64) — packs the meaningful bits of ≤64-bit ints.

These wrap a general codec: ts DateTime CODEC(DoubleDelta, ZSTD(1)). The general codec (LZ4 default, ZSTD(n) for more ratio) then compresses already-regularized bytes.

Layer 2: LowCardinality — dictionary encoding in the type system

LowCardinality(String) stores each value as an 8-bit (auto-widening) index into a per-part dictionary. Columns with < ~10k distinct values (country, status, event name) get smaller and faster — comparisons become integer comparisons. It's the closest thing ClickHouse has to a free lunch; use it aggressively, but not for high-cardinality strings (the dictionary becomes dead weight).

Keystone Sort order is the master codec. Delta/DoubleDelta only work when consecutive values are predictable — which is exactly what ORDER BY guarantees for time-ish columns within a key group. Compression strategy is downstream of the ORDER BY decision from lesson 3.

Sizing intuition

  • Raw event row ~1 KB in a row store → commonly 10–100 bytes/row in ClickHouse after key-aligned sorting + ZSTD.
  • Check yourself: SELECT name, formatReadableSize(sum(data_compressed_bytes)) AS disk, formatReadableSize(sum(data_uncompressed_bytes)) AS raw, round(sum(data_uncompressed_bytes)/sum(data_compressed_bytes), 1) AS ratio FROM system.columns WHERE table = 'events' GROUP BY name ORDER BY disk DESC.
Anti-pattern Blanket ZSTD(22) on every column. Max-level ZSTD is dramatically slower to decompress; LZ4-default usually wins on scan latency. Reserve heavy ZSTD for cold, huge, rarely-queried columns — and measure with system.columns, not vibes.
Q1: Why does DoubleDelta help a timestamp column that is already in the ORDER BY?

Within a key group timestamps are monotonically increasing with fairly regular steps; the second difference is near-constant (often zero), which compresses to almost nothing.

Q2: When does LowCardinality hurt?

High-cardinality strings: the per-part dictionary grows huge, lookups gain nothing, and merges pay to unify dictionaries. Rough ceiling: ~10k distinct values.

Q3: Query latency is up after switching to ZSTD(19). Why?

Decompression is on the scan path; extreme ZSTD levels trade decompression speed for ratio, so fewer bytes still means slower scans.
