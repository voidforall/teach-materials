ORDER BY Design, Partitioning & Skip Indexes

In ClickHouse you don't index queries — you design the table around the queries. ORDER BY is the single highest-leverage decision you make.

There is no secondary B-tree index to add later. The ORDER BY key determines: which predicates can prune granules, how well columns compress (adjacent similarity), and how merges behave. Design rule:

Keystone ORDER BY = your most common filter(s), ordered from most-selective-in-practice to least, with the main time column usually last. Every dimension you filter by frequently belongs in the key; a typical event table uses ORDER BY (user_id, event, timestamp) or (site_id, timestamp) — never just (timestamp) unless you only ever query time ranges.

Partitioning is for management, not for speed

PARTITION BY toYYYYMM(event_date) splits the table into partitioned sets of parts. Pruning on the partition expression is coarse (month-granular) but dropping a partition is the cheapest delete in ClickHouse: ALTER TABLE t DROP PARTITION '2024-01' — instant, no rewrite. Use partitions for TTL expiry and bulk data lifecycle; don't partition by anything high-cardinality (user_id!) — hundreds of partitions × parts each will wreck merges.

Skip indexes for non-key columns

When a frequent predicate can't be in the key (too many access patterns), add a data skipping index. It doesn't point at rows — it stores per-granule-range metadata so the engine can skip whole granules:

  • INDEX idx_user user_id TYPE bloom_filter GRANULARITY 4 — membership test; equality/IN lookups on high-cardinality non-key columns.
  • TYPE minmax — ranges of numeric/time columns (great for correlated columns already implied by the key order).
  • TYPE set(N) — up to N distinct values per range, for low-cardinality columns.

Skip indexes cost read time (on ingest, mostly) and help only when data is correlated with the sort order — a bloom filter over randomly-scattered values skips nothing.

Anti-pattern Copying an OLTP habit: ORDER BY id (or leaving it off) and "adding an index later". There is no later. A table sorted by a unique id compresses poorly and prunes never — the worst of both worlds.

Worked example

Query: "events for user U in the last 30 days, by type" (99% of traffic) + "all events for site S today".

CREATE TABLE events (
  user_id UInt64,
  site_id UInt32,
  event LowCardinality(String),
  ts DateTime,
  payload String CODEC(ZSTD(3))
) ENGINE = MergeTree
PARTITION BY toYYYYMM(ts)
ORDER BY (user_id, event, ts)
INDEX idx_site site_id TYPE bloom_filter GRANULARITY 4;

User-first key makes the 99% query read a handful of granules; bloom index rescues the site query; monthly partitions give cheap TTL.

Q1: Why does time usually go last in ORDER BY, not first?

Queries almost always carry an equality dimension (user, site) plus a time range. Key-prefix pruning needs the equality columns first; the time range then prunes within them. Time-first defeats every non-time filter.

Q2: When is DROP PARTITION the right "delete"?

Whole-unit data lifecycle: retention windows, re-ingesting a bad load. It's metadata-only and instant, versus mutations which rewrite parts.

Q3: A bloom_filter skip index on user_id skips nothing. Most likely reason?

user_id values are uncorrelated with the sort order — every granule's range contains "everything", so no granule can be excluded. (Or it's already the key column.)
