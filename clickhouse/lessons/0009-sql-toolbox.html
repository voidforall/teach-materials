The SQL Toolbox

ClickHouse SQL is analytics-first: aggregates you can merge, arrays as first-class citizens, and argMax doing the job three subqueries used to.

argMax — "latest row per key" in one pass

SELECT user_id, argMax(status, updated_at) AS status,
       argMax(balance, updated_at)          AS balance
FROM ledger GROUP BY user_id;

One aggregate, no window functions, no FINAL, no self-join. This is the idiomatic way to read append-only/versioned tables (lessons 5–6). Pair columns with the same updated_at ordering column and they stay consistent.

Combinators — modifiers on every aggregate

  • sumIf(x, cond), countIf(cond) — conditional aggregation replaces CASE-SUM; countIf(a) / count() is a one-line rate.
  • uniq/uniqExact — approximate (fast, fixed memory) vs exact; uniqCombined in between.
  • quantile(0.99)(latency_ms) — sketches; quantiles(0.5, 0.99)(…) for several at once.
  • -State/-Merge/-MergeState — partial aggregates for MV pipelines (lesson 7).
  • groupUniqArray, topK(10), any(last(x)) — the ones you'll reach for weekly.

Arrays as first-class citizens

Arrays arrive naturally (JSON fields, funnel steps) and ClickHouse has a mini query language over them:

SELECT user_id,
  arrayFilter(x -> x.event = 'signup', events)  AS signups,
  arraySort(x -> x.ts, events)[1]               AS first_event,
  length(arrayDistinct(arrayMap(x -> x.page, events))) AS pages_seen
FROM user_sessions;

arrayJoin is the special one: it unrolls one array column into multiple rows — turning nested data into flat rows that normal aggregates can chew on. Funnels: windowFunnel (ordered event sequences within a session) and retention (cohort matrix) are built-in, scan-based implementations of analyses you'd otherwise write as five-stage scripts.

Keystone ClickHouse pushes analytics into aggregates: combinator suffixes for conditions/states, arrays with lambdas for nested data, argMax for latest-per-key, windowFunnel/retention for behavioral analytics. The instinct to port complex warehouse SQL (window functions over CTEs) is often the wrong one — there's usually a one-aggregate idiom.

Also worth knowing

  • Window functions (OVER/PARTITION BY) exist — for running totals and rankings — but are usually slower than an aggregate idiom when one exists.
  • WITH supports expressions and named subqueries (CTEs).
  • SETTINGS per query: max_execution_time, max_memory_usage, join_use_nulls — analytics queries should carry their own guardrails.
  • sample on tables with SAMPLE BY in the key: statistically valid subsetting at granule granularity.
Q1: Compute "7-day retention" without window functions or joins. What's in your toolbox?

retention(cond1, cond2, …) — the built-in cohort aggregate takes first-event + return-event conditions and returns the retention matrix directly.

Q2: Why prefer countIf over SUM(CASE WHEN …)?

Semantically identical, but the combinator is the native vectorized form — shorter, and no branchy inner loop.

Q3: What does arrayJoin do that arrayMap cannot?

It changes row multiplicity — explodes one row with an array into N rows — while arrayMap stays within the row. Only arrayJoin lets downstream GROUP BYs see elements individually.
