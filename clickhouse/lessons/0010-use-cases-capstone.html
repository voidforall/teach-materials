Use Cases & Capstone

The course ends where your mission began: when does ClickHouse win, when does it lose, and how do you design for a real workload end to end?

Wins — the pattern behind every green case

Common shape: append-heavy write volume + scan-style analytical reads + tolerance for eventual consistency.

  • Product/event analytics: funnels, retention, cohorts — windowFunnel/retention over billions of events (lesson 9).
  • Logs, traces & observability: the reason ClickHouse quietly runs under many SaaS "Log Explorer" products. Huge append-only streams, time-ranged scans, TTL expiry by partition. (Notably: this space competes with object-storage engines too — compare with your real retention/latency needs.)
  • Market/tick data & fintech telemetry: ordered by (symbol, ts), DoubleDelta/Gorilla codecs, per-instrument range scans; tick history at banks and exchanges is a classic.
  • Feature stores / ML metadata: batch materialization of point-in-time features from event logs.
  • General-purpose OLAP serving UI dashboards: sub-second aggregation at scale, replacing nightly pre-aggregations.

Losses — respect the red flags

  • OLTP: row-at-audit transactions, point reads/writes by primary key → Postgres/MySQL. ClickHouse has no real transactions, and point CRUD is its worst path.
  • Continuously mutable state: shopping carts, account balances updated in place → OLTP + sync into CH for analytics.
  • Heavy, ad-hoc relational algebra: large multi-table joins with complex planning → a warehouse (Snowflake/BigQuery) or DuckDB for single-node.
  • Strong consistency / distributed ACID requirements.
Keystone The decision question is not "is it big data?" but "is the workload append-and-scan?" If yes → ClickHouse, and design = lessons 2–8 (key, partition, codecs, MVs, dict/denormalize). If no → pick the tool whose commitments match, and let ClickHouse serve the analytical mirror of that data.

Capstone

Design end-to-end for this workload — then compare notes with the agent:

Capstone task

Workload: a fintech app ingesting 50k payment-events/sec (fields: event_time, user_id, merchant_id, country, amount, status, device). Queries: (1) hourly revenue + uniq payers per country, last 90 days; (2) single-user last 90 days statement (rare); (3) fraud dashboard: per-merchant decline rate, p99 latency, last 24h; (4) GDPR: delete all rows for a user on request; (5) 90-day retention.

Deliver: DDL for every table (engine, ORDER BY, PARTITION, codecs, TTL), the MV pipeline with -State combinators, the read queries for (1)–(3), and how you satisfy (4) without a mutation treadmill.

Spoiler checkpoints: user_id first in the key (query 2); MV → AggregatingMergeTree per (country, hour) and (merchant, hour) with uniqState/quantileState; lightweight DELETE for GDPR at request rates; monthly → no, daily or monthly partition + TTL for retention. Argue your own choices first, then have the agent grill them.

Final check: name the five decisions that make up a ClickHouse table design.

ORDER BY key, partitioning, codecs + LowCardinality, engine choice (MergeTree family), and the MV/rollup layer — plus the update strategy (append vs the four mutation paths).
